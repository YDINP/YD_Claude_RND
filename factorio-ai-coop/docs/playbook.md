# 배치 패턴과 비율

에이전트가 기계를 "놓을" 수는 있어도 **어디에 놓아야 돌아가는지**는 모른다. 이 문서는
그 지식을 좌표로 옮겨 적은 것이다. 신뢰도를 표시했다 — 🟢는 공식 위키, 🟡는 커뮤니티
관행, ⚠는 미확인이라 코드에 넣기 전에 게임에서 실측해야 하는 것.

좌표 규약: `(dx, dy)`, +x=동, +y=남. 원점은 기준 엔티티의 좌상단 타일.

## 채굴기 → 화로 직결 🟢

버너 채굴기는 **내부 저장고가 없고, 바라보는 방향의 바로 앞 칸에 산출물을 떨군다.**
화로는 어느 면으로든 받으므로 그 칸을 덮기만 하면 방향은 상관없다. 둘 다 2×2다.

| 채굴기 방향 | 화로 오프셋 |
|---|---|
| East (4) | `(+2, 0)` |
| West (12) | `(-2, 0)` |
| South (8) | `(0, +2)` |
| North (0) | `(0, -2)` |

**비율 함정** 🟢: 버너 채굴기는 0.25 광석/초를 내고 돌 화로는 0.3125 광석/초를 먹는다.
1:1로 붙이면 화로가 80%만 돈다. 초반에는 그냥 1:1로 붙이는 게 관행이다.

## 석탄 채굴기 두 대 마주보기 🟢

**석탄 광맥 위에서만** 의미가 있다. 두 버너 채굴기를 서로 마주보게 놓으면 각자 캔 석탄을
상대에게 급유해 반영구로 돈다. A를 `(0,0)` East, B를 `(+2,0)` West.

철광석에 같은 배치를 하면 아무 이득이 없다 — 그냥 두 대가 따로 캘 뿐이다. 에이전트가
오해하기 쉬운 지점.

## 전력 라인 🟢 (배치 순서) / ⚠ (커넥터 정확 좌표)

```
[물] — [오프쇼어펌프 1×2] — [파이프] — [보일러 2×3] — [파이프] — [증기기관 3×5] — [증기기관] ...
```

- 오프쇼어 펌프는 **육지에 놓되 물에 인접**해야 하고, 물을 등지게 놓아야 파이프가 육지로
  뻗는다. 물 타일을 찾아 인접 육지에서 4방향으로 `can_place_entity`를 시도하는 수밖에 없다
  (공식 헬퍼 없음 ⚠).
- **보일러 : 증기기관 = 1 : 2** 🟢 — 보일러가 60 증기/초를 만들고 기관이 30 증기/초를 먹는다.
- 보일러는 **0.45 석탄/초**를 태운다. 연료를 넣어야 한다.
- 2.0에서 오프쇼어 펌프 산출이 1200 물/초로 올랐다. 초반에 펌프는 하나로 충분하다.
  1.1 가이드의 "1펌프:20보일러" 비율은 **2.0에서 무효**다.
- 파이프 커넥터의 정확한 서브타일 좌표는 위키에 없다 ⚠. 인접 배치 후 연결 여부를
  실측하는 편이 낫다.

## 인서터 🟢

**바라보는 방향의 반대 칸에서 집어, 바라보는 방향 칸에 놓는다.** 1×1.
롱암은 앞뒤 2칸.

⚠ **버너 인서터는 자기 연료가 따로 필요하다.** 화로에 석탄을 넣어도 인서터가 굶으면
아무것도 옮겨지지 않는다. "화로엔 석탄 넣었는데 왜 안 되지"의 정체가 이것이다.

## 랩 셀 🟢 (크기) / 🟡 (배치 관행)

랩은 3×3, 60kW. 최소 구성은 `[상자] — [인서터] — [랩]`.
랩 원점 `(0,0)`일 때 동쪽에서 공급하면 인서터 `(-1,+1)` East, 상자/벨트 `(-2,+1)`.

## 조립기 셀 🟢 (크기) / 🟡 (배치 관행)

조립기 1은 3×3, 가동 75kW, 제작속도 0.5, **액체 레시피 불가**.

```
[입력벨트/상자] — [인서터1] — [조립기 3×3] — [인서터2] — [출력벨트/상자]
```

조립기 원점 `(0,0)`: 입력 인서터 `(-1,+1)`, 출력 인서터 `(+3,+1)`,
입력 `(-2,+1)`, 출력 `(+4,+1)`.

**조립기는 전력만으로는 절대 안 돈다.** `set_recipe`로 레시피를 지정해야 한다.

## 에이전트가 빠지기 쉬운 함정 🟢

| 실수 | 증상 |
|---|---|
| 화로·드릴·버너인서터의 연료를 **각각** 안 넣음 | 빨간 "연료 없음", 완전 정지 |
| 버너 인서터 연료만 깜빡 | 기계는 멀쩡한데 아이템이 안 옮겨짐 |
| 인서터 방향 반대 | 아무 동작 없음 또는 반대로 옮김 |
| 전력 미연결 / 부족 | 빨간 아이콘, 느려지거나 정지 |
| 물 없는 곳에 펌프 | 배치 자체가 거부됨 |
| 파이프 정렬 안 맞음 | 유체가 안 흐름 |
| 조립기에 레시피 미지정 | 전력이 있어도 영원히 안 돎 |
| 목적지 가득 참 | "목적지가 가득 참" 경고, 라인 정지 |

보일러에 연료가 5개 이상이면 인서터가 투입을 멈추는데, 이건 정상 동작이지 고장이 아니다.

## 표준 빌드 오더 🟢🟡

| 시간 | 할 일 |
|---|---|
| 0~2분 | 근처 자원 확인, 손채굴 |
| 2~5분 | 돌 화로 + 버너 채굴기 → 철판 자동 생산. **철광석 손채굴은 여기서 끝**, 석탄·돌은 계속 손으로 |
| 5~15분 | 채굴기+화로 세트 2~3개로 확장. 기어·회로는 아직 손제작 |
| 15~30분 | 펌프→보일러→증기기관으로 전력. 조립기 1 확보 |
| 30~60분 | 조립기로 기어·회로 자동화 → 빨간 과학팩 → 랩 → 첫 연구 |

전기 채굴기 전환은 보통 60분 이후다. 초반 1시간은 버너로 버틴다.

## 확장할 때의 수치 🟢

앞의 배치 패턴이 "하나를 어떻게 놓는가"라면, 여기는 "몇 개를 놓는가"다. 에이전트가
계속 늘려도 되는지 판단하려면 이쪽이 필요하다.

### 채굴기 : 화로 🟢 (공식 수치로 계산)

| 조합 | 산출/소비 | 비율 |
|---|---|---|
| 버너 채굴기 → 돌 화로 | 0.25 / 0.3125 | **드릴 5 : 화로 4** |
| 전기 채굴기 → 돌 화로 | 0.5 / 0.3125 | **드릴 5 : 화로 8** |
| 전기 채굴기 → 강철 화로 | 0.5 / 0.625 | **드릴 5 : 화로 4** |

돌 화로 하나를 꽉 채우려면 버너 드릴이 1.25대 필요하다. 그래서 초반에 드릴과 화로를
1:1로 붙이면 화로가 80%만 돈다 — 손해는 아니지만, **화로를 드릴보다 적게** 두는 게
맞다. 반대로 화로가 드릴보다 많으면 그냥 노는 화로다.

옐로 벨트(15개/초) 하나를 채우려면 전기 채굴기 30대, 그 판금을 만들려면 강철 화로
24대가 든다.

### 전력 🟢

- **보일러 1 : 증기기관 2** (보일러 60 증기/초, 기관 30 증기/초)
- **오프쇼어펌프 1 : 보일러 200 : 증기기관 400** (펌프 1200 물/초 ÷ 보일러 6 물/초)
- 보일러 하나가 석탄 **0.45개/초**, 화로 하나가 **0.0225개/초**를 태운다. 보일러 하나가
  화로 스무 대분의 석탄을 먹는다.

1.1의 "펌프 1 : 보일러 20"은 2.0에서 무효다. 구버전 가이드를 따라가면 물 공급을
스무 배로 과대설계한다.

### 엔티티 크기 🟢

| 엔티티 | 타일 | 비고 |
|---|---|---|
| 돌/강철 화로 | 2×2 | |
| 전기 화로 | 3×3 | 업그레이드 시 자리가 커진다 |
| 조립기 1/2/3 | 3×3 | 전 등급 동일 |
| 버너 채굴기 | 2×2 | |
| 전기 채굴기 | 3×3 | 채굴 범위 5×5 |
| 보일러 | 2×3 | |
| 증기기관 | 3×5 | |
| 오프쇼어펌프 | 1×2 | |
| 인서터 / 전봇대 / 벨트 | 1×1 | |

**화로는 2×2인데 전기 화로는 3×3이다.** 화로를 3타일 간격으로 붙여 놓으면 나중에
전기 화로로 못 바꾼다. 처음부터 **4타일 간격**으로 놓으면 그 자리에서 교체된다.

### 여백과 도달거리 🟢

| 항목 | 값 |
|---|---|
| 인서터 도달거리 | 1타일 (롱암 2타일) |
| small-electric-pole | 공급 5×5, 배선 7.5타일 |
| 지하 벨트 최대 거리 | 옐로 4 / 레드 6 / 블루 8 |
| 제련 열 최소 폭 | 5타일 (벨트1 + 인서터1 + 화로2 + 인서터1) |
| 전기 화로 열 최소 폭 | 7타일 |

### 메인 버스 🟡 (커뮤니티 관행)

- 벨트 **4개 묶음마다 2칸 여유**. 12레인이면 폭 16타일.
- 버스와 생산 블록 사이 최소 3칸, 권장 6~10칸.
- 버스가 이득인 구간은 **과학팩 자동화 전후**다. 그 전엔 과하고, 기차망으로 넘어가면
  의미가 줄어든다.
- city block(32타일 배수, 보통 96×96)은 **초반에 과잉설계**다 ⚠. 기차가 필요해지기
  전에는 버스가 더 빠르다.

### 빨간 과학팩 🟢 (레시피) / 🟡 (대수)

철 기어 1 + 구리판 1 → 과학팩 1, **제작 5초**. 조립기 1은 제작속도 0.5라 실제 10초.
기어는 0.5초 레시피라, **기어 조립기 1대가 과학팩 조립기 8~10대를 감당**한다 🟡
(제작시간 비율 1:10에서 도출, 위키에 직접 적힌 값은 아님).

초반에는 벨트 없이 인서터로 기어 조립기 → 과학팩 조립기 → 랩을 직결해도 충분하다.

### 초보가 흔히 지는 방식 🟢🟡

1. **화로 한두 대에 몰아넣기** — 드릴 공급을 못 따라가 광석만 쌓인다. 우리가 겪은 그것.
2. **석탄 수동 보급** — 손으로 채워주는 순간 그 기계는 자동이 아니다.
3. **노란 인서터 하나로 고처리량 라인** — 인서터가 벨트를 못 따라간다.
4. **계획 없는 스파게티** — 초반부터 철·구리·석탄·돌 레인을 나란히 깔아두면 나중에 싸다.
5. **고립된 생산 섬을 여러 개** — 자원을 공유 못 해 전부 반쯤 논다.

## 손으로 나르지 않기 🟢

초반 공장이 느린 이유는 기계가 모자라서가 아니라 **사람이 광석을 나르기**
때문이다. 아래 셋은 벨트도 연구도 없이 그걸 없앤다.

### 채굴기 -> 화로 직결 🟢

채굴기는 내부 저장고가 없어서 캐자마자 **바라보는 방향 앞 칸**에 떨군다.
그 칸에 재료를 받을 수 있는 기계가 있으면 바닥에 흘리지 않고 **그 안으로
직접 넣는다**. 인서터가 필요 없다.

채굴기가 (0,0)-(1,1)을 차지하고 남쪽을 보면 화로는 (0,2)-(1,3). 출력면
2칸 폭과 화로 2칸 폭이 완전히 겹쳐야 한다.

> **함정** 🟢 채굴기는 **광석만** 떨군다. 화로의 석탄은 절대 넣어주지
> 않는다. 직결해놓고 연료를 잊으면 멀쩡해 보이는 채로 아무것도 안 나온다.

북쪽을 볼 때만 벨트의 어느 레인에 떨어지는지가 다른 알려진 버그가 있지만,
화로는 2칸을 다 덮으므로 무관하다.

### 석탄 자급쌍 🟢

석탄 광맥 위에 채굴기 두 대를 **서로 마주보게** 놓으면, 각자 캔 석탄이
상대의 연료함으로 직행해 둘이 서로를 영원히 먹인다. 연료함이 50개씩이라
실질 버퍼가 100개다.

```
[채굴기 A ->][<- 채굴기 B]     A는 East, B는 West, 2타일 간격
```

> 가득 차면 **멈춘다**. 무한 생산이 아니라 «저절로 채워지는 연료 은행»이다.
> 잉여를 빼내려면 한쪽 출구를 상자로 돌리거나 버너 인서터를 붙여야 한다.

⚠ 사용자가 말한 «4대 순환»(핀휠) 배치는 출처를 찾지 못했다. 2대 쌍을 두 벌
놓는 것은 확인된 방법이고, 4-way 순환은 게임에서 실측하기 전에는 코드에
넣지 않는다.

**광석에는 쓰지 마라.** 철광석은 연료가 아니라서 상대의 연료함에 들어가지
못하고 그대로 막힌다.

### 버너 인서터의 leeching 🟡

버너 인서터는 자기 연료가 떨어지면 **자기가 나르던 것**에서 연료를 떼어
쓴다. 그래서 «석탄을 나르는 인서터»는 따로 연료를 줄 필요가 없다.
판금을 나르는 인서터는 해당되지 않으므로 석탄을 따로 넣어줘야 한다.

⚠ 정확한 발동 조건은 공개되지 않았다. 커뮤니티 실증이 여럿 있어 전제로
삼되, 인서터가 굶어 멈추는지는 실측으로 확인할 것.

### 연료 자동 삽입 한도 5 🟢

인서터는 대상의 연료가 5개를 넘으면 더 넣지 않는다. 50개까지 안 찬다고
고장으로 오인하면 안 된다. (손으로 넣을 때는 이 한도가 없다.)

### 보일러는 손으로 못 먹인다 🟢

보일러는 **0.45 석탄/초**를 태운다. 20개를 넣으면 **44초** 버틴다. 인서터와
상자 없이는 발전소가 계속 꺼진다.

### 발전소 배관 🟢 (실측)

게임에 임시로 세워 `fluidbox.get_pipe_connections()` 를 읽은 값이다. 어림으로
좌표를 재면 반드시 어긋난다.

| 엔티티 | 연결구 |
|---|---|
| 오프쇼어 펌프 | 자기 칸에서 **바라보는 반대쪽 한 칸**으로 물을 내보낸다 |
| 보일러 (2×3) | 물 연결구가 중심 **옆구리 양쪽 한 칸**(축은 바라보는 방향에 수직), 증기 출구는 **바라보는 쪽 두 칸 앞** |
| 증기기관 (3×5) | 증기 연결구가 **긴 축 양끝 두 칸**. 기관끼리도 증기를 넘긴다 |

> **함정 하나** ⚠ 2×3, 3×5 처럼 변의 길이가 짝수/홀수로 섞인 엔티티는
> **중심 좌표가 축마다 .0 이거나 .5 여야 한다.** 계산한 자리를 게임이 반 칸
> 밀어 놓으므로, 놓은 뒤 `entity.position` 을 다시 읽어야 한다. 요청한
> 좌표를 그대로 믿으면 연결구가 반 칸 빗나가고, 밖에서 보면 멀쩡한
> 발전소가 선다.

> **함정 둘** 🟢 배관이 다 맞아도 **전봇대가 없으면 0와트**다. 기관 상태가
> `not_plugged_in_electric_network` 으로 나오고, 증기는 가득 차 있다.
> 실측: 펌프 working / 보일러 working(물 199, 증기 1) / 기관 증기 200,
> 발전량 0. 발전소는 전봇대까지 세워야 «완성»이다.

> **함정 셋** ⚠ 유체망 id(`get_fluid_system_id`)는 틱이 지나야 갱신된다.
> 세운 그 명령 안에서 연결 여부를 확인할 수 없으므로, 연결구 좌표가 서로를
> 향하는지로 판정해야 한다.

### 전기화 순서 🟢

**채굴기가 먼저다.** 전기 채굴기는 90kW에 채굴 0.5/초로 버너의 두 배고,
`automation-science-pack 25`면 열린다. 전기 화로는 `advanced material
processing 2`까지 가야 하는 최후반 업그레이드라 한참 뒤다.

증기기관 하나(900kW)로 전기 채굴기 10대, 전기 화로 5대, 랩 15대.

## 광맥 위에 어떻게 세우는가 (2026-09-18 리서치 + 이 맵 실측)

### 매장량은 균일하지 않다 — 이 맵 실측, 반경 250

| 광석 | 칸 수 | 최소 | 최대 | 평균 | 광맥 크기 |
|------|------:|-----:|-----:|-----:|-----------|
| 석탄 | 546 | 7 | 7,596 | 1,511 | 39×305 |
| 철광석 | 617 | 1 | 1,674 | 565 | 32×34 |
| 구리광석 | 362 | 1 | 2,397 | 878 | 28×21 |
| 돌 | 199 | 4 | 1,892 | 632 | 19×16 |

같은 광맥 안에서 천 배가 넘게 차이 난다. 게임이 돌려주는 엔티티 목록은
광맥의 **바깥 테두리부터** 나오므로, «놓을 수 있는 첫 칸»에 세우면 거의
언제나 제일 얇은 곳에 세우게 된다. 매장량 1짜리 칸의 버너 채굴기는 4초를
산다.

버너 채굴기는 **2×2를 캔다**(크기 = 채굴 범위). 그 네 칸의 합이 이 자리의
수명이고, 0.25/s 로 나누면 초가 나온다. 1,674개면 111분짜리다.

### 숙련자들의 배치 (출처: 공식 위키 + 포럼)

| 항목 | 수치 | 신뢰도 |
|------|------|--------|
| 버너 채굴기 크기 = 채굴 범위 | 2×2 | 공식 |
| 버너 채굴기 속도 / 연료 슬롯 | 0.25/s / 50개 | 공식 |
| 마주보기 자가급유 간격 | **0칸(정확히 인접)**, 서로를 향하게 | 커뮤니티 |
| 자가급유 루프가 가득 차는 시간 | 약 3분 | 커뮤니티 |
| 전기 채굴기 크기 / 채굴 범위 | 3×3 / 5×5 | 공식 |
| 전기 채굴기 속도 | 0.5/s (우라늄 0.25) | 공식 |
| 노란 벨트 처리량 | 15개/s (레인 1개) | 공식 |
| 벨트 양쪽 채굴기 간격 | **0칸(빈틈 없이)** | 커뮤니티 컨센서스 |
| 노란 벨트 1개를 채우는 채굴기 수 | 20~30대 (채굴 생산성 연구에 따라) | 편차 있음 |
| 전봇대 배치 | 최대 공급 범위보다 **1칸 짧게** | 커뮤니티 |
| 채굴기→화로 직결 간격 | **0칸(직접 인접)** | 커뮤니티 |

### 직결 비율을 고쳐야 한다

버너 드릴 0.25/s (철광석 실측 0.2625/s) vs 돌 화로 0.2857/s.
**드릴이 병목이다.** 직결이면 화로는 3.8초마다 0.3초씩 깜빡이며 논다.

두 비율은 **다른 질문에 대한 답이다.** 헷갈리면 둘 다 틀린다:

- **처리량 비율은 5 : 4.** 드릴 5대(1.25/s)가 화로 4대(1.25/s)를 꽉 채운다.
  상자나 벨트를 거쳐 광석이 자유롭게 섞일 때 쓰는 값이다.
- **직결 배치는 1 : 1.** 드릴 하나의 산출 칸이 화로 하나이므로 물리적으로
  1:1이 강제되고, 화로는 80%만 돈다(3.8초마다 0.3초 깜빡임). 화로를 더
  붙일 자리가 아예 없다.

우리는 직결하므로 **배치는 1:1**, 다만 **전체 규모를 볼 때는 5:4**로
계산한다. 195대가 27대를 바라보고 있으면 어느 쪽 기준으로도 5~6배 과잉이다.

초반 표준 구성(한 출처 기준): 석탄 4~6대, 철 7~9대, 구리 2대, 돌 1~2대.

### 통로는 우리 규칙이지 게임의 관행이 아니다

리서치 결과: **「N칸마다 M칸을 비운다」는 표준 관행은 없다.** 숙련자들은
빈틈 없이 밀집시키고, 광산 안을 걸어다니지 않는다(차량으로 통과하거나
바깥으로 돌아간다). 캐릭터가 건물 위를 못 걷는 것은 버그가 아니라 의도된
동작이라고 공식 확인되었고, 그래서 `Squeak Through` 같은 모드가 있다.

우리는 **여덟 칸마다 한 줄을 비운다**(`LANE_EVERY = 8`). 이것은 채굴 밀도를
희생하는 의도적 선택이다 — 사람이 관찰자로 들어와 직접 손을 대야 하는
프로젝트이기 때문이다. 밀도를 최우선으로 삼는 순간 사람이 자기 공장에
못 들어간다.

### 연료 자동화 (전기 이전)

1. **드릴↔드릴 마주보기**: 석탄 광맥 위에서만. 인서터도 자원도 안 든다.
2. **버너 인서터 + 혼합 벨트**: 철광석과 석탄을 50:50으로 흘리면, 집는
   쪽 버너 인서터가 벨트의 석탄을 자기 연료로 가져다 쓴다.
   ⚠ **화로에서 꺼내는 쪽 인서터는 화로 안 석탄을 못 훔친다.** 입력 쪽만
   통하는 트릭이다. 화로 연료는 따로 넣어줘야 한다.
3. 인서터가 한 번에 채우는 연료는 **5개 정도**(관찰 기반, 확실하지 않음).

## 전기 없이 자동화되는 것 (2026-09-18 리서치 + 실측)

### 연구 없이 이미 만들 수 있는 것 — 게임에 물어 확인

```
burner-inserter   enabled=true      transport-belt  enabled=true
iron-gear-wheel   enabled=true
assembling-machine-1   enabled=false (automation 연구, 빨간팩 10개)
electric-mining-drill  enabled=false (같은 이름의 연구, 빨간팩 25개)
long-handed-inserter   enabled=false (automation 연구에 딸려옴)
```

**버너 인서터와 벨트는 처음부터 만들 수 있다.** 전기도 연구도 필요 없다.

### 급유 인서터는 영구 기관이다

```
[석탄 상자] → [버너 인서터] → [기계]
```

버너 인서터는 **자기가 나르는 물건이 연료일 때만** 그중 일부를 떼어 자기
연료로 쓴다. 그래서:

- 석탄을 나르는 인서터 → **영원히 자급한다.** 한 번 세우면 끝.
- 광석·철판을 나르는 인서터 → 자급 안 된다. 화로 연료 슬롯에서 훔쳐오지도
  못한다. **손이 계속 간다.**

규모: 인서터 처리량 0.79개/s, 버너 채굴기 한 대의 연료 소비 0.0375개/s
(150kW ÷ 석탄 4MJ). **인서터 한 대가 채굴기 스물한 대분을 감당한다.**
기계가 굶는다면 처리량 한계가 아니라 인서터가 없는 것이다.

### 인서터 방향 — 실측 (2026-09-18)

`direction` 은 **집는 쪽**이다. 놓는 쪽이 아니다.

| direction | 집는 칸 | 놓는 칸 |
|-----------|---------|---------|
| north (0) | (0, −1) | (0, +1.2) |
| east (4) | (+1, 0) | (−1.2, 0) |
| south (8) | (0, +1) | (0, −1.2) |
| west (12) | (−1, 0) | (+1.2, 0) |

상자에서 기계로 옮기려면 인서터가 **상자를 향해** 서야 한다.

자리는 기계의 `bounding_box` 에서 잰다 — 인서터는 half+0.5, 상자는 half+1.5.
크기를 하드코딩하지 않으니 2×2 드릴에도 화로에도 그대로 맞는다.

### 전기 화로는 없다

바닐라 초반에 전기로 돌아가는 화로는 **없다.** 돌 화로도 강철 화로도 석탄을
먹는다. 채굴기를 전기화해도 화로 연료 문제는 그대로 남는다 — 다만 채굴기가
안 쓰게 된 석탄이 화로로 돌아가는 여유가 생긴다.

### 연구 갈림길

`electric-mining-drill` 과 `automation` 은 **형제 기술**이다. 둘 다 선행이
`automation-science-pack` 하나뿐이라, 순서를 고를 수 있다.

| 연구 | 빨간팩 | 얻는 것 |
|------|-------:|---------|
| automation | 10 | 조립기 1호, 롱암 인서터 |
| military | 10 | 건 터렛, 총알 |
| logistics | 20 | 지하 벨트, 분배기 |
| electric-mining-drill | 25 | 전기 채굴기 (0.5/s, 연료 불필요) |

조립기 1호는 **전기 전용**(75kW)이다. 그리고 조립기 1호 한 대가 만드는
과학팩 0.1개/s 는 **랩 한 대의 소비량과 정확히 같다.**

### 참고: AI가 Factorio를 하는 기존 연구

**Factorio Learning Environment** (arXiv:2503.09617, 2025). 목표 설계가
두 축이다 — 연속 지표인 **Production Score**(원광에서 정제품으로 갈수록
지수적으로 커지는 가치 합)와 이산 사다리인 **Milestones**(처음 만든 아이템
종류, 처음 끝낸 연구). 우리 `mission.py` 의 사다리와 같은 발상이고, 논문이
지적하는 LLM 에이전트의 최대 약점도 **공간 추론**이다 — 우리가 배관과
전봇대에서 겪은 것과 같은 자리다.

## 벨트 물류 (2026-09-18)

### 왜 벨트인가

내내 같은 두 숫자가 병목이었다: **캔 광석이 갈 데가 없어 선 채굴기**와,
**받을 것이 없어 선 화로.** 둘은 같은 문제의 두 얼굴이고, 사람 넷이 그
사이를 걸어서 메우는 것으로는 절대 못 따라간다(지난 판에서 112대 대 54대로
벌어졌다).

벨트 한 줄이 둘을 동시에 없앤다. 그리고 한 번 깔면 손이 다시 갈 일이 없다.

### 최소 구조

```
[채굴기] → [벨트][벨트][벨트] → [인서터] → [화로]
```

**채굴기는 벨트에 직접 떨군다.** 인서터가 필요한 곳은 화로 쪽 하나뿐이다.
이걸 모르면 양쪽에 인서터를 달게 되고, 그 하나가 손이 계속 가는 자리가 된다
(광석을 나르는 인서터는 자가 급유가 안 된다).

### 수치

| 항목 | 값 |
|------|-----|
| 노란 벨트 레시피 | 철판 1 + 철기어 1 → **2개**, 연구 불필요 |
| 처리량 | 15개/s (두 레인 합) |
| 벨트 이동 속도 | 1.875타일/s |
| 버너 채굴기 산출 | 0.25개/s |
| **벨트 하나가 감당하는 버너 채굴기** | **60대** |

처리량이 병목이 되는 일은 초반에 없다. 벨트가 모자라서가 아니라 **안 깔아서**
막힌다.

### 우리 규칙

- `BELT_REACH = 40` — 이보다 멀면 벨트값이 손으로 나르는 값을 넘는다.
- `BELT_SPARE = 4` — 중간에 모자라 끊긴 벨트는 안 깐 것과 같고, 이미 쓴
  자재만 사라진다. 여유분을 쥐고 출발한다.
- 길은 ㄱ 자로 꺾는다. 벨트는 직진과 직각 회전만 하므로 그것으로 충분하고,
  꺾는 순서(x 먼저 / y 먼저)를 둘 다 시험해서 되는 쪽을 쓴다.
- 한 칸이 막혔다고 줄 전체를 버리지 않는다. 끊긴 자리는 다음 점검에서 같은
  길로 다시 시도한다.
- 화로 하나에 벨트 여러 줄을 물리지 않는다. 짝은 한 번씩만 쓴다.

### 아직 안 한 것

- 벨트 양쪽에 채굴기를 두 줄로 세우는 밀집 배치 (전기 채굴기 단계)
- 석탄과 광석을 한 벨트에 섞어 흘려 입력 인서터가 연료를 훔치게 하는 트릭
- 지하 벨트로 통로 밑을 지나가기 (logistics 연구는 이미 끝남)

## 제련 블록 — 고수들은 어떻게 세우는가

사용자 지시로 실제 사례 사진을 모아 «보고» 정했다. 근거 사진은
`docs/reference/` 에 있다.

### 모양

`reference/smelting-column.jpg` (alt-f4.blog #56) 에서 잰 것:

```
    ─────────────  광석 벨트
    ↑ 인서터
    ■■  ■■  ■■  ■■   화로 줄 0
    ↓ 인서터
    ─────────────  판금 벨트   <- 두 줄이 이 하나를 같이 쓴다
    ↑ 인서터
    ■■  ■■  ■■  ■■   화로 줄 1
    ↓ 인서터
    ─────────────  광석 벨트
```

세로로 세어보면 화로 중심 사이가 정확히 다섯 칸이다:

| 칸 | 무엇 |
|----|------|
| y, y+1 | 줄 0 화로 (2x2) |
| y+2 | 인서터 |
| y+3 | 판금 벨트 |
| y+4 | 인서터 |
| y+5, y+6 | 줄 1 화로 |

가로로는 화로 사이에 **한 칸을 비운다**(중심 간격 3). 사진의 왼쪽은 돌화로
(2x2), 가운데는 강철화로, 오른쪽은 전기로(3x3)인데 **같은 자리에** 들어가
있다. 붙여 놓았다면 전기로로 바꿀 때 줄을 통째로 걷어야 한다.

우리 `furnace_seat` 의 값이 여기서 나왔다: pitch 3, aisle 5, gap 9.

### 몇 대가 필요한가

`reference/smelting-ratio.jpg` (Steam 가이드 "Everything To Do With Smelting"):

| 벨트 | 포화에 필요한 돌화로 | 한 줄당 |
|------|--------------------|---------|
| 노란 벨트 (15/s) | 48대 | 24대 |
| 빨간 벨트 (30/s) | 96대 | 48대 |
| 파란 벨트 (45/s) | 140대 | 70대 |

우리 블록은 한 줄 12대 = 블록당 24대다. 두 블록이면 노란 벨트 하나를 채운다.

### 석탄 자급쌍

`reference/coal-self-feeding.png` 이 우리가 세우는 것과 같은 모양이다 —
버너 채굴기 둘이 마주보고 서로의 연료칸에 넣는다. 출력 상자가 없으므로 캔
석탄은 전부 연료칸에 쌓이고, 한 칸(50개)이 차면 멈춘다.

**그러니 이 쌍은 구조물이 아니라 창고다.** 25개를 남기고 덜어 가는 것이
사용법이고, 덜어 가는 것이 곧 되살리는 일이다. 한 대가 태우는 것은 초당
0.0375개인데 캐는 것은 0.25개이니, 25개면 다시 가득 찰 때까지 멈추지 않는다.

### 빨간 과학 블록

`reference/red-science-block.png` (Steam 가이드). 랩을 두 줄로 세 대씩 놓고,
과학팩 벨트가 그 줄을 **감싸고 돈다**. 인서터가 벨트 양쪽에서 랩에 넣는다.
조립기는 모서리에 앉아 벨트에 얹기만 한다.

숫자 - 조립기1은 초당 0.1개를 만들고 랩 한 대가 그만큼 먹는다. 즉 **1:1**이
계산상 맞는다. 다만 실전에서는 랩이 잠깐 비는 것보다 조립기가 잠깐 노는 쪽이
싸다고 보아 1:4~1:8 로 쓰는 사람이 많다(가이드 본문). 우리는 랩이 셋이므로
조립기 셋이 계산값이고, 하나로 시작해도 연구가 끊기지는 않는다.

### 메인 버스 (아직 안 함)

`reference/main-bus.png` (wiki Tutorial:Main bus). 벨트 네 줄마다 두 칸을
비우고, 조립 라인은 버스와 **수직**으로 붙인다. 우리는 아직 벨트가 0개라
여기까지 못 갔다. 제련 블록을 줄로 세운 이유가 이것이다 - 줄이어야 잇는다.

## 전기를 먼 데서 끌어오기

출처: wiki.factorio.com (Electric pole / Mining / Boiler). 전부 Normal 품질.

| | 전선 도달 | 공급 범위 | 재료 | 해금 |
|---|---|---|---|---|
| 소형 전봇대 | 7.5 | 5x5 | 목재1 + 구리판1 | 처음부터 |
| 중형 전봇대 | 9 | 7x7 | 구리판1 + 철판2 + 강철판2 | 전력분배1 |
| 대형 전봇대 | **32** | 4x4 | 구리판2 + 철판4 + 강철판5 | 전력분배1 |
| 변전소 | 18 | 18x18 | 구리판5 + 철판10 + 강철판10 + 회로5 | 전력분배2 |

**132타일을 잇는 데 소형은 19개, 대형은 5개다.** 다만 대형은 강철이 들고
강철은 강철제련 연구가 필요하다. 이 판(2026-09-18)에서는 연구가 셋뿐이고
강철도 중형/대형 전봇대도 전부 잠겨 있어서, **지금은 소형 19개가 유일한
답이다**. 나중에 전력분배1이 열리면 같은 거리를 다섯 개로 줄일 수 있다.

전선 규칙 두 가지: 도달거리가 다른 둘을 이으면 **짧은 쪽**이 적용되고,
전봇대 하나에 최대 다섯 개까지 이어진다.

### 발전소 비율

| | 비율 | 근거 |
|---|---|---|
| 보일러 : 증기기관 | **1 : 2** | 보일러 60증기/초 ÷ 기관 30증기/초 |
| 오프쇼어펌프 : 보일러 | **1 : 200** | 펌프 1200물/초 ÷ 보일러 6물/초 |

오프쇼어펌프는 전력을 쓰지 않는다. 즉 펌프는 하나면 넉넉하고, 우리가 펌프를
다섯 개나 지어둔 것은 전부 낭비였다.

### 증기기관 한 대(900kW)로 돌릴 수 있는 것

| | 소비 | 몇 대 |
|---|---|---|
| 랩 | 60kW | 15대 |
| 조립기1 | 75kW | 12대 |
| 전기 채굴기 | 90kW | 10대 |

다른 소비처가 없다고 볼 때의 이론값이다. 우리 랩은 셋이니 **기관 한 대면
충분하다** - 그래서 전선은 여섯 대가 있는 먼 발전소가 아니라 가까운 쪽(한
대짜리)으로 잇는 것이 맞다.

### 채굴기

| | 크기 | 캐는 범위 | 속도 |
|---|---|---|---|
| 버너 채굴기 | 2x2 | **2x2 (자기 크기와 같다)** | 0.25/s |
| 전기 채굴기 | 3x3 | 5x5 (사방 한 칸씩 더) | 0.5/s |
| 대형 채굴기 | 5x5 | 13x13 | 2.5/s |

버너 채굴기가 제 크기만큼만 캔다는 것이 `richness()` 가 2x2 네 칸만 더하는
근거다. 전기 채굴기로 바꾸면 같은 자리에서 범위가 5x5 로 넓어지고 속도가
두 배가 된다 - 얇은 자리를 옮겨다니는 일이 그만큼 줄어든다.

`reference/burner-drill-to-chest.png` — 위키가 보여주는 버너 채굴기의 기본
출력: 떨구는 칸에 상자 하나. 우리는 상자 대신 화로를 놓는다(상자는 차면 다시
막히고, 안에 든 광석은 누가 날라야 사다리에 오른다).

## 오프닝 — 얼마나 지을 것인가

리서치 원문은 `reference/opening-research.md`. 신뢰도는 거기 등급대로.

### 빨간 과학팩 열 개가 문이다

Automation 연구에 필요한 것은 **빨간 과학팩 열 개**뿐이고, 손으로 만들어도
된다(게임 공식값). 그 하나가 로지스틱도 전기 채굴기도 터렛도 전부 연다.

| | |
|---|---|
| 빨간 과학팩 1개 | 철기어 1 + 구리판 1 = 철광석 2 + 구리광석 1 |
| 열 개 | 철광석 20 + 구리광석 10 |

우리는 철광석 1,700개를 쌓아두고 이 열 개를 한 번도 안 만들었다. 조립기는
팩을 «계속» 대기 위한 것이지 첫 열 개를 위한 것이 아니다 - 첫 열 개는 손이
더 빠르다.

### 버너 시대에 몇 대면 되는가

| 무엇 | 권장 | 우리(2026-09-18) |
|------|------|------------------|
| 철 채굴기 + 화로 | 20쌍 | — |
| 구리 | 5~10쌍 | — |
| 석탄 | 10대+ | 48대 |
| 돌 | 4대 | — |
| **합계 채굴기** | **40대 안팎** | **161대** |

네 배에서 여덟 배다. 그러고도 과학팩은 0개였다.

### 숙련자들이 한목소리로 경고하는 것

- 체인 앞이 광석 부족인데 **뒤만 늘리지 마라**
- 양쪽으로 동시에 벌리지 말고 **한쪽을 먼저** 끝내라
- **과학팩이 밀려 쌓일 때만** 랩을 늘려라 (반대로 랩부터 늘리면 안 된다)
- **전력이 안정되기 전에** 과학을 확장하지 마라

우리가 한 일이 정확히 이 네 가지의 반대였다.

### 순서

```
채굴기1 + 화로1
  -> 석탄/돌 자급
  -> 랩 1~2대 + 손으로 만든 팩 10개  (automation 해금)
  -> 조립기 등장. 기어 조립기 + 과학팩 조립기 + 인서터로 랩에 연결
  -> 오프쇼어펌프1 + 보일러1 + 증기기관2   (비율 1:2, 공식)
  -> 전기 채굴기 전환
  -> 로지스틱 연구 -> 벨트 자동화
```

전기로 넘어가는 판단 기준은 대수가 아니라 **전력망이 섰는가**이다.

## 소비성 재료 — 연료와 탄약 🟢

> 사용자: "2명한테 주기적으로 전체적으로 연료채우게 시켜"
> 사용자: "항상 연료랑 탄약같이 소비성재료들은 넉넉하게 넣어둘 것."

**둘을 상설로 붙인다.** 기본은 foxtrot·echo.

```
python scripts/upkeep_patrol.py --agents foxtrot,echo --every 150
```

**그 둘에게 다른 일을 얹지 않는다.** 얹으면 순찰이 그 일 뒤에 줄을 서고,
그 사이에 줄 끝의 팔이 굶는다. 반장이 손으로 몰 때 특히 그렇다.

**문턱은 둘이다** (`bridge/settings.py`).

| | 언제 가는가 | 얼마나 붓는가 |
|---|---|---|
| 석탄 | `COAL_LOW` 20 | `COAL_FULL` 50 (연료칸 한 스택) |
| 탄창 | `AMMO_LOW` 25 | `AMMO_FULL` 100 |

하나로 쓰면 채우자마자 또 가거나, 빈 뒤에야 간다. 떨어진 «뒤에» 채우면
그 사이 멈춰 있던 시간이 그대로 손해다.

**급한 순서** (`upkeep.URGENCY`)

```
포탑 > 인서터 > 보일러 > 화로 > 채굴기
```

포탑은 비어 있으면 장식이고, 장식인 것을 모르고 지나가면 그날 전멸한다
(19회차). 줄 끝의 «팔»이 굶으면 그 뒤의 채굴기가 전부 선다 — 팔 하나가
채굴기 열넷보다 급하다.

**실측(16회차)** — 이 규칙이 없던 날.

```
철 인서터    no_fuel  연료=0
구리 인서터  no_fuel  연료=0
철밭         14대 중 10대 waiting_for_space_in_destination
구리밭       16대 전부  waiting_for_space_in_destination
```

서른 대가 캔 것이 벨트에 꽉 찬 채 멈췄다. 아무것도 「실패」하지 않았으므로
아무도 몰랐다. 조용한 정지가 시끄러운 실패보다 비싸다.

## 출구는 몇 개여야 하는가 🟢 (16회차 실측)

```
버너 인서터   0.6 개/초 옮긴다
버너 채굴기   0.25 개/초 캔다
      ->      출구 하나에 채굴기 «두 대»
```

**실측(석탄밭)** — 채굴기 10대에 출구 하나였을 때.

```
벨트       칸마다 8개로 포화
채굴기     10대 중 6대 waiting_for_space_in_destination
실제 산출  0.6개/초   <- 캘 수 있는 2.5개/초의 4분의 1
상자       13개
```

온 맵이 석탄을 기다렸다. **병목은 «문»이지 «광부»가 아니다.** 이 상태에서
채굴기를 늘리면 늘어나는 것은 「기다리는 채굴기 수」뿐이다.

**출구 내는 자리** — 줄 양옆은 채굴기가 꽉 채우므로, 출구는 줄 «끝»
바깥에 낸다. 벨트를 두세 칸 더 늘리고 그 옆에 붙인다.

```
y=12   상자   상자
y=13   팔     팔      dir=8 (남쪽 벨트에서 집는다)
y=14   ---- 벨트 ----
y=15   팔     팔      dir=0 (북쪽 벨트에서 집는다)
y=16   상자   상자
       x=-73  x=-72
```

**화로로 받으면 더 낫다.** 상자는 누가 비워야 하지만 화로는 광석을 판으로
바꾼다. 다만 화로를 «광맥 위»에 세우면 나중에 채굴기 자리를 먹으므로,
벨트를 제련구역까지 끌고 가서 거기 세운다.

> 사용자: "위치가 철광석지대에 바로 만들면 나중에 채굴기를 늘릴 수 없으니,
> 벨트를 늘려서 화로구역(제련구역)까지 이어지게해서 만드는게 나음."

### 출구는 광맥 «밖»에 🟢 (사용자 지적, 16회차)

> "벨트를 늘려서(이후 채굴기를 늘릴 수 있기떄문에) 석탄지를 벗어나서
> 상자에 모았으면 더 좋을듯."

광맥 위에 놓은 상자·화로 한 칸은 «나중에 못 세울 채굴기 한 대»다.

```
벨트 한 칸    철판 0.5장
채굴기 한 대  철판 9장 + 돌 5
```

벨트를 늘려 광맥 밖으로 나가는 편이 열여덟 배 싸다. 그러니 줄은 광맥을
가로질러 «끝까지» 깔고, 출구(팔+상자)와 화로는 광석이 없는 칸에 세운다.

실측(석탄밭): 광맥이 `y=12` 에서 `x=-66` 까지 간다. 출구를 `x=-73,-72` 에
냈더니 상자 여덟 칸이 광맥 위에 앉았다 — 채굴기 네 대 자리다. `x=-65`
밖으로 옮기고 벨트를 열 칸 늘렸다.

**광맥 끝을 재는 법** — 테두리 상자가 아니라 «출구를 낼 줄»에서 잰다.
밭은 둥글어서 가운데 줄이 가장 멀리 간다.

## 여는 순서 🟢 (사용자 지시)

> "시작했을때 제일 우선으로 할거는 채굴기를 만들어서 광석마다 배치해서
> 생산효율을 올리는게 콜드스타트의 지점이야. 그렇게 생산자동화가 된다면
> 나오는 광석들로 재련 및 유통, 조립과정을 거쳐서 포탑으로 방어선을
> 구축한 뒤에 베이스를 점점 자동화 및 고도화 진행해야해."

```
1  콜드스타트   손으로 «채굴기 몇 대분»만 캔다. 그 이상은 낭비다
2  생산자동화   채굴기를 광맥«마다» 세운다. 여기가 지렛대다
3  재련.유통    벨트 -> 제련구역. 광맥 위에는 아무것도 세우지 않는다
4  조립         조립기계로 옮긴다. 사람이 만들면 사람이 묶인다
5  방어선       포탑: 테두리 + 밭 초소 + 안쪽
6  고도화       그 다음에 넓힌다
```

**왜 채굴기가 먼저인가 — 이것이 유일한 지수 구간이다.**

```
버너 채굴기 한 대 = 철판 9 + 돌 5
한 대가 초당 0.25개를 캔다 = 사람 손의 여러 배이고, 사람과 달리 묶이지 않는다
```

손으로 사백 개를 캐는 동안 채굴기 넉 대면 같은 것을 캐고 사람은 다른
일을 한다. 그러니 손채굴은 «첫 화로 한 대와 첫 채굴기 넉 대» 분량에서
멈춘다 - 철광석 40 + 돌 25 면 된다.

17회차에는 이것을 거꾸로 했다. 연구 사슬을 앞세우고 손으로 220개씩
캐게 했더니, 다섯 사람이 두 시간 동안 묶여 있었고 밭도 방어도 못 지었다.

**그래도 시계는 두 개다** (17회차 전멸에서 산 값).

```
공해   화나게 하는 것.  pollution_reach / slack
확장   가까워지는 것.   enemy_expansion, 쿨다운 4분
```

17회차는 공해가 **0** 인 채로 전멸했다 - 확산 비율 0.02 라 한 청크를
채우기 전에 흩어진다. 적은 공해와 무관하게 걸어와 92칸까지 밀고 들어와
웜을 세웠다. 그러니 4단계(방어선)를 «공해가 없으니 괜찮다»로 미루면
안 된다. `scripts/health.py` 가 매 점검마다 둥지 거리와 웜을 센다.

| 판 | 포탑 | 결과 |
|---|---|---|
| 19회차 | 8대, 만재 | 자리가 틀려 한 마리도 못 잡음 |
| 16회차 | 12대, 탄약 45발 | 빈 땅을 지킴. 밭에서 둘 사망 |
| 17회차 | 0대 | 연구 사슬이 169분 동안 안 끝남. 전원 사망 |

## 계획은 내기 «전에» 확인한다 🟢 (한 세션에 세 번 틀림)

> 사용자: "같은 실수 3번째면 코드로 막아"

하나가 지어야 할 것을 나머지가 쓰도록, 여럿에게 «동시에» 일을 던진 실수.

```
급유를 채굴기가 서기 전에   -> nothing with an inventory at 39,-37   x16
출구를 벨트가 닿기 전에     -> 팔 열 개가 벨트에서 두 칸 떨어져 섬
입고를 창고가 서기 전에     -> 돌 100을 든 채 서 있고, 고리는 돌을 기다림
```

셋째가 제일 비쌌다. 증식 고리가 돌 스무 개를 기다리는 동안, 바로 옆에
백 개를 든 사람이 서 있었다.

**적어두는 것으로는 안 막혔다.** 이 문서에 이미
「앞사람이 끝난 것을 게임에 물어 확인하고 뒷사람을 보낸다」가 있었다.

```python
from orders import submit
submit(ai, "hotel", plan)                 # 없는 것을 가리키면 OrderError
submit(ai, "hotel", plan, strict=False)   # 경고만 하고 보낸다
```

`insert` `take` `demolish` 처럼 «이미 거기 있는 것»을 건드리는 단계마다
그 자리를 게임에 한 번에 묻는다. 같은 계획이 «먼저 짓는» 자리는 찬 것으로
치므로, 상자를 세우고 곧바로 채우는 멀쩡한 계획은 그대로 통과한다.
칸 모서리와 엔티티 가운데의 0.5 어긋남도 같은 자리로 본다.

조용히 보내면 그 계획은 한 줄씩 무너지는데, 그것은 오류로 «기록될 뿐»
아무도 안 본다. 보내기 전에 막는 편이 싸다.


## 세운 것과 «도는 것»은 다른 일이다

18회차에서 사용자가 물었다:

> "분명 내가 채굴기로 스타트하라고 해서 채굴기까지 설치했는데 왜 아직도
> 손채굴을 하고있는거지?"

실측하니 채굴기 열여섯 대가 서 있었고, **열여섯 대 전부 멈춰 있었다.**

```
-7,-118  waiting_for_space_in_destination  tgt=-  ground=1
49,-97   no_fuel                                  fuel=0
```

버너 채굴기는 받을 것이 없으면 «땅에» 떨군다. 그 한 무더기가 차면 그
자리로 끝이다. 그래서 여덟 대는 광맥 위에 서서 광석 한 무더기를 내고
멈췄고, 여덟 대는 석탄밭 위에 서서 석탄이 없어 멈췄다. 생산량은 0이었고,
사람들은 그 옆에서 손으로 캤다.

「채굴기를 세웠다」는 숫자는 늘었는데 광석은 한 톨도 안 늘었다.

> **떨굴 곳 없는 채굴기는 없는 채굴기다.** 석탄밭 위에서 연료가 없어 선
> 채굴기도 마찬가지다.

### 그래서 `scripts/grow.py` 는 당번이 둘이다

| 당번 | 하는 일 | 순서 |
|------|---------|------|
| `unload` | 들고만 있는 것을 창고에 푼다 | 0 |
| `tend` | 멈춘 채굴기에 상자와 연료를 준다 | 1 |
| `sow` | 새 채굴기를 세운다 | 2 |

`tend` 가 «먼저»다. 세우는 것보다 세워 둔 것을 돌리는 편이 언제나 싸다 —
재료가 안 들고, 이미 광맥 위에 서 있다.

그리고 `tend` 는 이 고리가 **기억하는 것이 아니라 게임이 말하는 것**을
본다(`status == waiting_for_space_in_destination / no_fuel`). 그래야 남이
세워 두고 간 채굴기도 같이 살아난다 — 위 열여섯 대가 그랬다.

### 「있나」와 «받아 주나»는 다른 질문이다

첫 판에서 `tend` 가 상자를 한 개도 안 세웠다. 떨구는 칸을 반경 1.6으로
「뭔가 있나」 물었더니, 그 칸에서 1.4칸 떨어진 **채굴기 자신**이 잡혔다.

떨구는 칸은 채굴기 코앞이다. 그 자리를 물을 때는 「무엇이든 있나」가
아니라 «받아 줄 것(container/transport-belt)이 있나»를 물어야 한다.

### 고리는 저장소 안에 산다

이 고리는 한 번 `/tmp/grow18b.py` 로 띄웠다가 조용히 죽었다. 뒤이어 그
파일을 고치려던 heredoc 이 `FileNotFoundError` 로 끝났는데, 로그가 비어
있으니 아무도 몰랐다. 그 사이 사람들은 계속 손으로 캤다.

> 상시로 도는 것은 `scripts/` 안에 둔다. 임시 폴더는 사라지고, 사라진
> 것은 조용히 사라진다.


## 모두가 바쁜 것과 «필요한 모든 일이 되고 있는 것»은 다르다

18회차는 62분에 `gun-turret` 연구를 끝냈다. 세 판 만에 처음이다. 그리고
포탑을 한 대도 못 세우고 전원 사망했다.

```
연구 gun-turret  완료        포탑 0대     탄약 0발
창고 철판 1354 · 구리판 38   적 51마리 / 웜 4기
시체 8구, 전부 «기지 안»
```

그 판에서 고리가 셋 돌았다 — 증식, 유통, 발전. 여덟 명이 모두 바빴다.
그 셋 어디에도 「포탑을 세운다」가 없었다.

재료가 모자란 게 아니었다. 철판 1354면 포탑 서른 대다. 없었던 것은
**그 일을 맡은 사람**이다.

> 사람이 다 배정됐다고 일이 다 배정된 것은 아니다. 배치표를 볼 때는
> 「누가 노는가」가 아니라 «무엇이 비었는가»를 본다.

### 기다리는 동안 논다는 선택지는 없다

포탑은 연구가 필요하다. **탄약은 필요 없다.** `firearm-magazine` 은
철판 넷이면 처음부터 만들 수 있었는데, 62분 동안 한 발도 안 만들었다.

연구가 끝난 그 순간에 필요한 것은 결정이 아니라 «이미 만들어 둔 것»이다.
그래서 `guard.py` 는 연구 전에도 할 일이 있다.

| 상태 | 하는 일 |
|------|---------|
| 연구 전 | 탄약을 만들어 쌓는다 |
| 연구 후 | 포탑을 세우고 «그 자리에서» 탄약을 넣는다 |

### 채우는 당번과 «만드는» 당번은 다르다

보급 순찰(`upkeep`)은 있었다. 그런데 순찰은 채울 뿐 만들지 않는다.
세상에 탄약이 0발이면 순찰은 아무 일도 안 하고, 그 침묵이 「이상 없음」
으로 읽힌다.

채굴기에서 겪은 「세우는 당번은 있는데 돌리는 당번이 없다」와 같은
모양이다. 당번을 나눌 때는 사슬의 «양 끝»을 확인한다.


## 문턱 밑에 숨은 교착

19회차는 402분 동안 멈춰 있었다. 아무도 안 죽었고 오류도 없었다.

```
채굴기 4대   전부 정지 (상자 가득, 밭에 철광석 5658 적체)
화로  8대    status=27(full_output), recipe=stone-brick
창고         철판 0 · 돌 150 · 탄약 48
```

순서는 이랬다. 보급 순찰이 창고에 철광석이 없자 「있는 광석으로 바꿔
준다」는 규칙에 따라 **돌**을 넣었다. 화로 여덟 대가 벽돌 굽기로 전직했고,
결과칸에는 이전 철판이 여섯 장 남아 있었다. 벽돌을 뱉을 칸이 없으니
영구 정지다.

유통 고리에는 화로를 비우는 당번이 있었다. 그런데 조건이 「판 열 장
이상」이었다. **여섯 장짜리 교착은 문턱 밑에 있어서 보이지 않았다.**

> 문턱은 «값어치 없는 걸음»을 막으라고 둔 것이지, 멈춘 기계를 못 본 척
> 하라고 둔 것이 아니다.

고친 것 둘:

- 화로의 `status` 를 읽는다. `full_output` 이면 양과 무관하게 비우고,
  원료칸의 «남의 광석»까지 꺼낸다. 결과칸만 비우면 다음 순번에 또 같은
  것을 굽다가 또 막힌다.
- 대체 광석에서 돌을 뺐다(`tests/upkeep_ore.py`). 돌은 철의 대체재가
  아니라 그 화로의 «일을 바꾸는 것»이다. 빈 화로가 잘못 채운 화로보다
  낫다.

### 곁들여 - 기계는 「무엇을 가졌나」보다 «왜 섰나»를 안다

이 교착은 재고만 봐서는 안 보인다. 화로에 광석도 있고 연료도 46이나
있었다. `status` 를 물었을 때에야 `full_output` 이 나왔다.

점검이 세는 것은 양이 아니라 «멈춤»이어야 한다.

## 판은 씨앗 운에 맡기지 않는다

16.17.18.19회차가 모두 둥지가 걸어올 수 있는 거리에서 시작했다. 19회차는
402분 만에 적 74마리가 51타일까지 들어왔고, 그때 포탑은 0대였다.

`config/map-gen-settings.json` 을 둔다.

| 항목 | 값 | 이유 |
|------|-----|------|
| `starting_area` | 4 | 둥지 없는 반경을 넓힌다 |
| `enemy-base` frequency/size | 0.5 | 둥지 수와 크기를 줄인다 |
| 광석 frequency/size/richness | 1.5 | 콜드스타트를 짧게 |
| `water` | 1.5 | 물이 159칸 떨어진 판을 줄인다 |

방어 사슬이 한 시간 반짜리인 동안은, 그 한 시간 반을 «살아서» 보낼 수
있는 판에서 시작해야 한다. 사슬을 짧게 만드는 것과 시간을 버는 것은
둘 다 해야 하는 일이다.


## 지도는 «걸어서» 연다

20회차에서 정찰을 보낸 뒤, 지도가 잘 안 넓어지길래 `force.chart` 로
기지 둘레를 통째로 그렸다. 청크는 196 -> 2068 로 늘었고 둥지 스물한
곳의 좌표가 한 번에 나왔다.

사용자가 그 자리에서 막았다:

> "맵을 직접 열기보단, 캐릭터가 이동해서 안개가 걷히는 부분만 체크가
> 되어야함. 다음부턴 그러지마셈"

맞는 말이다. `chart` 로 얻은 지도는 **아무도 가 보지 않은 지도**다.
그것을 허용하면 정찰이라는 일 자체가 없어지고, 그러면:

- 「여기까지는 안전하다」는 말의 근거가 사라진다. 발로 밟아 본 것과
  좌표만 아는 것은 다르다
- 정찰병이 도중에 무엇을 만나는지(웜, 무리, 지형, 물)를 영영 모른다
- 무엇보다, 사람이 화면에서 보는 것과 우리가 아는 것이 어긋난다

> **우리가 아는 것은 누군가 발로 밟은 만큼이다.**

`scripts/scout.py` 에서 `reveal()` 을 걷어냈다. 지도를 여는 API 는
이 저장소에서 쓰지 않는다.

### 곁들여 - 그래서 정찰은 «도착을 확인»해야 한다

같은 판에서 정찰 로그가 420칸까지 갔다고 찍었는데 실제로 열린 지도는
170~250칸이었다. 길찾기가 먼 목표를 포기하면 에이전트는 그냥 한가해지고,
이 고리는 한가해진 것을 도착으로 읽었다.

발로 밟은 만큼만 안다면, 어디까지 밟았는지는 «발»에게 물어야 한다
(`ai.list()` 의 x, y).

## 기준점이 둘이면 줄은 반드시 흩어진다 🟢 (20회차, 사용자 지적)

사용자가 사진을 보내며 물었다.

> "화로사이에 벨트가 왜있는거임?"

화로와 화로 사이 빈칸마다 벨트가 한 칸씩 박혀 있었다. 아무 데도 안 닿는
토막들이다. 누가 잘못 깔아서가 아니라, **같은 땅에 계획이 둘**이었다.

| | 어디를 보고 있었나 |
|---|---|
| 모드 `belts.lua` | 제련 구역 (25,14). 화로 줄은 `smelt.y` 와 `smelt.y+5`, 그 사이로 들어오는 벨트 y=11, 나가는 벨트 y=16 |
| `grow.py` | `--smelt=40,0` 을 받아 y=0,5,10,15,20 에 화로를 뿌렸다 |

모드는 «비워 둔 줄»에 화로가 올 줄 알고 길을 냈고, grow 는 그 길 위에
화로를 세웠다. 모드는 남은 빈칸으로 길을 이으려 했고 - 그래서 토막이
남았다.

이 교훈은 **이 문서에 이미 적혀 있었다.** 적어 두는 것과 «그것을 못
틀리게 만드는 것»은 다른 일이다.

그래서 「화로를 어디에 세워도 되는가」를 인자가 아니라 모드 구역에서
답하도록 `scripts/rows.py` 한 곳에 모았다. 테스트(`tests/smelt_rows.py`)가
두 곳의 숫자가 어긋나면 잡는다.

### 곁들여 - 맞물려야 하는 곳에서 여백은 어긋남이다

줄의 첫 칸을 구역 테두리에서 «한 칸 들여» 시작했다. 안전해 보이는
여백이었는데, 그 한 칸이 위상을 바꿨다.

`belts.lua` 의 out_arms 는 `smelt.x + FURNACE_PITCH * n` 에 선다. 화로가
그 x 에 없으면 팔은 화로가 아니라 화로 «사이 빈칸»을 집는다.

> 실측: 이미 선 화로 마흔 대는 x=40,43,... 이고 40 - 25 = 15 로 모드의
> 위상과 정확히 맞는다. 26 부터 세었다면 마흔 대 전부를 「틀린 자리」로
> 판정했을 것이다.

## 「막혔다」는 결론이 아니라 질문이다 🟢 (20회차, 사용자 지시)

> "배치해야하는데 다른건물이 막고있다면 해당 건물이 무엇인지 왜거기
> 설치되어있는지 체크해서 해당건물을 재설치할것인지, 배치를 새롭게
> 다시 구성할것인지 시도해"

지금까지 「막혔다」는 한 마디였다. 그 한 마디 뒤에 아주 다른 것들이
숨어 있었고, 같은 말로 부르는 바람에 전부 같은 대접을 받았다.

| 막은 것 | 왜 거기 있나 | 무엇을 할 것인가 |
|---|---|---|
| 전봇대 | 자리는 뜻이 아니다. 닿기만 하면 된다 | **비켜 세운다** |
| 우리 상자 | 벨트가 오기 전의 임시 출구였다 | **비우고 걷는다** |
| 채굴기·화로·터렛 | 제 일을 하고 있다 | **길을 다시 그린다** |
| 광맥·물·절벽 | 우리가 놓은 것이 아니다 | **길을 다시 그린다** |

`scripts/blocked.py` 가 이 표다. 이름만 보면 목록을 영원히 늘려야 하지만,
«자리에 매여 있나»로 물으면 새 건물이 생겨도 규칙이 그대로 선다.

### 곁들여 - 「막았다」고 «먼저 찾은 것»을 적으면 안 된다

`field` 흐름이 한 칸에서 멈추며 `why="iron-ore"` 를 남겼다. 벨트는 광맥
위에 깔리므로 광맥은 애초에 방해가 아니다. 실제로 막은 것은 그 칸을
덮고 있던 버너 채굴기였고, 광맥은 그저 «먼저 찾힌» 것이었다.

로그가 사람을 엉뚱한 곳으로 보낸다. 무엇이 막았는지 찾을 때는 «막을 수
없는 것»부터 걸러야 한다.

## 못 하는 일은 «아무것도 안 한 것»으로 끝나야 한다 🔴 (20회차, 사용자 지적)

> "전선 재배치했는데 그때문에 화로쪽 전선 전력연결이 끊김"

전봇대가 길을 막고 있어 옆으로 비켜 세우려 했다. 순서는 «걷고 나서
세우기»였다. 그 사이에 같은 계획의 벨트가 새 자리를 차지했고, 세우기가
조용히 실패했고, 걷은 자리에는 구멍만 남았다.

> 실측: (32,0) 과 (32,2) 가 사라졌다. 전력망 1개 → 2개, 굶는 것 12.

순서를 뒤집으면 실패해도 손해가 없다. 새것이 먼저 서면 그 순간부터
전기는 두 길로 흐르고, 그 다음에 옛것을 걷는다. 세우기가 실패하면
옛것이 그대로 있으니 «아무 일도 일어나지 않은» 상태로 남는다.

### 곁들여 - 줄 안에서 한 칸을 고를 때 너그러움은 오작동이다

`demolish` 의 기본 반경은 1.5 다. 사람이 「저거 치워」라고 가리킬 때는
그 너그러움이 맞다 - 반 칸 어긋나게 찍어도 알아들어야 한다.

그런데 벨트 한 줄을 돌릴 때는 정반대다. 옆 칸에도 벨트가 있으므로 반경
1.5 는 «이웃»을 집는다.

> 실측: 차선 y=11 의 x=38..51 열네 칸이 통째로 사라졌다. 걷기는 열네 번
> 됐고 세우기는 한 번도 안 됐다. 급전 팔 다섯이 집을 것을 잃었다.

## 벨트가 아는 것은 «자기가 어디로 보내는가»뿐이다 🟢 (20회차, 사용자 지적)

> "여기도 재배치하면서 벨트연결제대로안됨"

이어 붙이는 길의 방향을 «지나온 쪽»으로 적었다. 꺾이는 칸이 계속 서쪽을
보았고, 본선은 기둥으로 안 꺾인 채 빈 땅으로 나갔다.

> 실측: y=-2 줄이 x=28 까지 전부 서쪽. (27,-2) 에는 아무것도 없다.

방향은 «다음 칸»이 정한다. 어디서 왔는지는 그 칸의 일이 아니다.

### 곁들여 - 돌리는 일은 세우는 일이 아니다

모드는 «돌려라»(`turn`)와 «세워라»를 구분해서 준다. 그런데 `flow.py` 는
둘 다 `build` 로 처리했다. 이미 벨트가 선 칸에 `build` 는 못 하므로 그
칸은 영원히 「할 일」로 남고, 순번마다 같은 칸이 다시 배당된다.

> 실측: golf 과 alpha 가 (25,11) 과 (39,11) 을 수십 번 받았다. 그 칸의
> 벨트는 전부 서쪽, 계획은 동쪽이었다. 두 사람이 여섯 칸만 돌며 아무것도
> 안 하고 있었다.

## 눈으로 찾은 것은 다음에도 눈으로 찾아야 한다 🟢 (20회차, 사용자 지시)

> "벨트랑 인서터 잘 배치되었는지, 방향은 맞는지 체크하고 검수할것"

이 회차의 잘못된 배치는 전부 «사진»으로 한 건씩 잡혔다. 화로 사이에 낀
벨트 토막, 상자 하나만 받던 팔, 벨트에서 집어 벨트에 놓던 팔, 허공을 보고
끝나던 본선. 전부 사람이 화면을 보고 찾아 준 것이다.

그래서 «묻는 법»을 코드로 옮겼다(`scripts/proof.py`). 한 칸이 스스로
대답할 수 있는 질문은 셋뿐이다.

| | 물어야 할 것 |
|---|---|
| 벨트 | 나에게 «들어오는 것»이 있나 / 나에게서 «나가는 곳»이 있나 |
| 팔 | 집을 것이 있나 / 놓을 데가 있나 / 그 둘이 «뜻이 있는 쌍»인가 |
| 화로 | 나를 «채우는» 팔이 있나 / 나를 «비우는» 팔이 있나 |

첫 실행이 곧바로 찾아낸 것: 팔 35대 중 20대가 일을 안 했고, 벨트 133칸
중 12칸에 아무것도 안 들어왔고, 화로 49대 중 42대에 꺼내 줄 팔이 없었다.

### 곁들여 - 둘 다 맞고, 묻는 말이 달랐을 뿐이다

검수는 「팔 열일곱이 굶는다」고 했고 `mains` 는 「먹는 것들이 전부 받고
있다」고 했다. 둘 다 옳았다 - 그 팔들은 버너 인서터고, 전기가 아니라
석탄을 태운다. `is_connected_to_electric_network()` 는 그들에게 언제나
거짓이다.

인서터라고 다 같은 인서터가 아니다. 전기를 먹는 것은 망을 묻고, 태우는
것은 연료칸을 묻는다.

## 덮이지 않아서 굶는 것과 전기가 안 와서 굶는 것 🟡 (20회차, 사용자 지적)

> "전선이 불필요하게 과도하게 깔린 부분 발생함. 이거 정리하고 로직개선할 것."

> 실측: 전봇대 39 대, 전기를 먹는 것 17 개. 그중 열넷이 없어도 되는
> 것이었다. 제련줄 한 구간에만 열아홉 대가 서 있었다.

원인은 `mains.cover()` 였다. 굶는 것을 만나면 덮을 자리를 세우는데 «이미
덮고 있는 전봇대»를 안 봤다. 전력망이 둘로 갈라져 있던 동안 제련줄 쪽이
계속 「굶는다」고 나왔고, 고리는 그때마다 덮개를 한 겹씩 더 씌웠다.

선이 안 이어진 것이 원인인데 엉뚱한 약을 쓴 것이다. 그래서 순서도
바로잡았다 - **끊긴 곳을 잇는 것이 언제나 먼저다.** 갈라진 망에 전봇대를
더 세우면 그 전봇대는 발전기 없는 쪽에 붙는다. 세울수록 굶는 것이 는다.

### 곁들여 - 걷을 때 팩토리오는 다시 이어 주지 않는다

전봇대를 세울 때는 둘레의 것들과 자동으로 이어진다. 그런데 걷을 때는
남은 것들끼리 다시 잇지 않는다. 가운데 한 대가 양옆을 이어 주고 있었다면,
그 한 대를 걷는 순간 양옆은 «거리가 닿아도» 끊긴다.

그래서 `scripts/thin.py` 는 적게 걷고(한 번에 여섯 대), `mains` 로 다시
잇는다. 낙관을 고치는 대신 낙관이 틀려도 스스로 바로잡히게 했다.

## 약속을 지키느라 일을 못 하면 약속이 틀린 것이다 🟢 (20회차)

> 실측: 창고 상자 셋이 «전부» 빈칸 0.
> `iron-plate 1016 + copper-plate 2100 / stone 1600 / coal 1600`
> → "창고 iron-plate,stone 칸이 찼다 - 그것은 안 나른다"

찬 칸에 억지로 넣으려 드는 것을 막은 것까지는 옳았다. 그런데 선반 하나가
찼다고 창고 «전체»가 찬 것은 아니다. 옆 상자가 비어 있으면 거기 넣으면
된다 - 「제자리」는 사람이 찾기 쉬우라고 둔 약속이지 지켜야 할 법이 아니다.

제자리를 «먼저» 보고, 찼을 때만 빈 곳으로 간다. 아무 데나 넣기 시작하면
다음에 그것을 찾는 걸음이 길어지기 때문이다.

### 곁들여 - 선반 자리는 «규칙»이 아니라 «사실»이다

구리판을 `(dx, dy+6)` 에서 찾게 두었는데 거기엔 상자가 없었다. 구리판은
철판과 «같은 상자»에 있었다. `take` 가 조용히 실패하고, `craft` 는 구리판이
없어 조용히 실패하고, `build` 는 손에 없는 것을 세우려다 조용히 실패한다.
로그에는 「인서터 11개」가 네 번 찍혔고 세상의 인서터는 일곱 대 그대로였다.

`scripts/shelf.py` 가 「그 물건이 실제로 어느 상자에 있나」를 게임에 묻는다.

## 끝에 문을 내지 말고 줄을 따라 «집집마다» 낸다 🟢 (20회차, 사용자 지적)

> "벨트에 철판 쌓이니까 물류 상자쪽에도 인서터와 벨트 연결해서 상자에
> 자동으로 들어가도록 로직 추가해줘"

깐 길과 «그 길에서 내리는 일»은 다른 일이다. 길 끝에 팔이 없으면 실린
것은 거기까지 가서 멈추고, 뒤엣것이 밀려 줄 전체가 선다. 화로 결과칸이
가득 차 막히던 것과 똑같은 모양이 벨트 위에서 재현된다.

끝에 팔 하나를 세웠더니 사용자가 다시 짚었다.

> "이러면 상단1개박스에만 들어가니까 이것도 채굴기 벨트들처럼 쭉 이어서
> 상자마다 들어갈 수 있도록 배치해"

맞다. 상자 하나를 채우면 팔은 멈추고 뒤엣것은 그대로 밀린다. 상자가
셋인데 받는 곳이 하나면 창고는 삼분의 일만 창고다.

그래서 `scripts/sink.py` 는 상자를 «줄»로 본다. 나란히 선 상자들을 한
무리로 묶고, 그 줄과 나란히 두 칸 떨어진 자리에 벨트를 깔고, 상자마다
팔을 하나씩 세우고, **본선에서 그 기둥까지 ㄱ 자로 붙인다.** 마지막을
빠뜨리면 다 깔아 놓고 아무것도 안 실리는 빈 기둥이 남는다.

생긴 것이 같다고 하는 일이 같은 것은 아니다 - 밭의 상자도 줄지어 서
있지만 그쪽은 채굴기의 출구고, 밀어내면 채굴기가 갈 곳을 잃는다.

## 고정한 수는 판이 커질수록 작아진다 🟢 (20회차, 사용자 지적)

> "화로가 전부 철판으로 구성되어있는데, 구리판도 같이 나눠서 하면
> 좋을듯. 아니면 구리판용 화로를 늘리던가"

구리 화로를 「줄 끝 두 대」로 박아 두었다. 화로가 여섯 대일 때는
삼분의 일이던 것이 마흔 대가 되자 스무 분의 일이 됐다.

> 실측: 밭 상자 철광석 16289 · 구리광 9213 (구리가 36%)
> 화로 40 대 중 구리 2 대 (구리가 5%)

캐는 비율과 녹이는 비율이 이만큼 어긋나면 한쪽은 밭에 쌓이고 다른 쪽은

이유는 한쪽 밭이 잠깐 비어도 그쪽 화로를 전부 끄지 않기 위해서다 -
다시 켜는 데 한 바퀴가 든다.

## 늘리는 것 «자체»가 물결을 불러들인다 🔴 (20회차, 사용자 지시)

> "공습은 공해농도가짙을수록 더 많고 쌘애들이 오니까 이점 유의하고.
> 채굴기는 너무막 늘리기보단 병목/부족 현상이 없을정도로 천천히
> 늘려가는게 좋음."

여섯이 죽은 직후 처음으로 공해를 재 봤다. 스무 회차 동안 한 번도 안 본
지표였다.

```
기지 둘레 공해 합   32,731
가장 짙은 칸        258  at (80,-16)   <- 사람들이 죽은 바로 그 동쪽 밭
진화도              0.2219
누적 배출           238,187
```

공해 봉우리가 **정확히 사람들이 죽은 자리**였다. 우연이 아니다.

버너 채굴기는 전기 채굴기와 달리 제 몸으로 석탄을 태운다. 181대를 세워
놓으면 굴뚝 181개가 선 것과 같다. 공해는 퍼져서 둥지에 닿고, 둥지는
«공해가 오는 쪽»으로 물결을 보낸다.

    많이 캐려고 늘린 것이 «많이 맞는» 이유가 된다.

### 그래서 재료가 있다고 늘리지 않는다

`grow.py` 는 「판금과 석탄이 있으면 늘린다」였다. 그것은 늘릴 «능력»을
보는 것이지 늘릴 «이유»를 보는 것이 아니다. 이유는 셋 중 하나여야 한다.

| 무엇이 모자란가 | 무엇을 늘리나 |
|---|---|
| 화로가 굶는다 **&& 밭에 광석이 없다** | 채굴기 |
| 밭에 광석이 쌓인다 | 화로 |
| 둘 다 아니다 | **아무것도** |

### 곁들여 - 굶는다고 캐는 쪽이 모자란 것은 아니다

    실측: 굶는 화로 8대. 그런데 밭 상자에 쌓인 광석 88,677.

캔 것이 산더미인데 화로가 굶는다면 모자란 것은 채굴기가 아니라 «나르는
길»이다. 그때 채굴기를 늘리면 산더미가 커지고 공해가 짙어질 뿐이다.

「굶는다」는 증상이고, 증상만 보고 약을 쓰면 엉뚱한 곳을 고친다. 이
저장소가 「전선이 안 이어졌는데 덮개를 더 씌운」 것과 같은 실수다.

## 콜드스타트에서 배운 네 가지 🔴 (21회차)

새 판을 열고 채굴기 넉 대까지 가는 데 네 번 막혔다. 네 번 다 «있으니까
됐다»고 판단하고 넘어간 것이었다.

### 1. 맨 앞에 두어야 할 것을 뒤로 미루면 뒤엣것도 같이 못 온다

판이 생기자마자 백칠십을 「발전 사슬 몫」으로 떼어 두었다.

    실측: 화로 8대 전부 원료 없음, 노는 사람 6명, 판 80.
          그 80이 전부 몫으로 묶여 있었다.

채굴기가 없으면 광석이 없고, 광석이 없으면 판도 안 는다. 떼어 둔 몫은
영영 안 채워지고 채굴기도 영영 안 선다. **몫을 떼는 데도 «때»가 있다** -
채굴기 열두 대가 설 때까지는 안 뗀다.

같은 이유로 방어선 문턱도 때를 가린다. 공해가 옅으면 물결을 부를 일이
없고, 그때 「방어선부터」를 고집하면 첫 채굴기조차 못 선다.

    지킬 것이 없을 때 「지키고 나서 하라」는 말은 «하지 말라»는 말이다.

### 2. 모두가 먹는 것을 아무도 안 챙기면, 굶는 것은 전부다

손으로 끊는 매듭 목록에 **철광석이 빠져 있었다.** 돌·석탄·구리는 끊어
주면서 정작 모든 것이 먹는 철은 안 끊었다.

    실측: 채굴기 3대, 노는 사람 7명, 철판 0. 구리판만 56 이 쌓였다.

채굴기도 벨트도 상자도 포탑도 철판으로 만든다. 가장 굵은 매듭이었는데
목록에 없어서 아무도 손대지 않았다.

### 3. 「있다」와 «충분하다»는 다른 말이다

손 끊기가 「그 밭에 채굴기가 하나라도 있으면」 건너뛰었다.

    실측: 철밭에 채굴기 3대. 손 끊기는 «있으니까» 건너뛰었고,
          화로 여섯은 빈 채였고, 노는 사람이 여섯이었다.

버너 채굴기 한 대는 초당 0.25 를 캔다. 세 대면 0.75 - 화로 여섯을
먹이기에 턱없다. 여섯 대가 설 때까지는 손도 같이 거든다.

### 4. 명부를 가르면 일과 손이 어긋난다

고리마다 사람을 갈라 맡겼다. `grow` 에 넷, `haul` 에 넷.

    실측: 석탄 0 으로 화로 여섯이 섰는데, grow 의 일꾼 넷은 전부 바쁘고
          노는 둘은 «운반 소속»이라 석탄 매듭에 손을 못 댔다.

일이 있는 고리에는 손이 없고, 손이 있는 고리에는 일이 없었다. 고리마다
`idle()` 로 «지금 한가한 사람»을 고르므로 명부가 겹쳐도 서로 밟지 않는다.
겹치자 바로 풀렸다 - 화로 굶음 6대→3대, 일하는 사람 3명→7명.

    명부는 «누가 할 수 있나»지 «누구 것인가»가 아니다.

## 한결같은 거절은 자리가 아니라 «눈»을 의심하라

발전 사슬이 물가 스물한 곳에서 «전부» 같은 말로 거절당했다.

    no shore with room for a whole power block   x 21

자리가 정말 없다면 곳마다 사정이 달라야 한다. 한결같다는 것은 «찾는
방식»이 한결같이 틀렸다는 뜻이다. 세 겹이었고, 셋 다 「없다」가 아니라
「안 봤다」였다.

### 격자가 둘인 판에서 한 격자만 더듬으면 못 찾는 게 아니라 안 찾은 것이다

기준점은 늘 타일 가운데(x.5, y.5)다. 거기에 정수를 더해 훑으면 나오는
자리도 전부 x.5, y.5 다. 그런데 3x2 보일러는 «한 축이 .0» 이어야 앉는다.

    반 칸 격자에서 놓을 수 있는 자리     4
    온전한 칸 격자에서 놓을 수 있는 자리 12

앉을 수 있는 열두 자리를 단 한 칸도 후보로 못 올리고 있었다. 크기가
홀짝으로 갈리는 판에서는 반 칸씩 가야 두 격자가 모두 걸린다.

### 「놓인다」와 «쓸모 있다»는 다른 말이다

자리 찾기가 놓이는 방향을 하나 찾으면 곧장 멈췄다. 그런데 펌프는
바라보는 쪽 반대 칸으로 물을 내보내고, 그 칸이 호수면 보일러가 붙을
데가 없다.

    펌프(57.5,-33.5) 출구(56.5,-33.5) = 물
    언저리에 보일러 12자리, 맞물린 것 0

물가에서 «물을 등지는 방향»은 넷 중 하나뿐이다. 먼저 걸린 방향에서
멈추면 그 하나를 영영 못 본다. 후보는 네 방향 모두 올리고, 거르는 일은
«쓸모»로 한다 - 출구 칸에 관이 놓이는가.

거르는 질문도 고쳐 물어야 한다. 「여기가 물인가」를 타일 이름으로
따지면 판이 바뀔 때 또 틀린다. «관이 놓이는가»는 어느 판에서도 같은
뜻이다. **답을 고치지 말고 질문을 옮겨라.**

### 다섯 그루가 방어선 전체를 막을 수 있다

위 둘을 고치니 보일러는 다섯 곳에 앉는데 기관이 한 곳도 못 앉았다.

    기관이 앉을 수 있는 자리    0
    나무 다섯을 치우면        160

나무 다섯 그루가 발전소를, 그러니까 연구소와 포탑과 방어선 전체를
막고 서 있었다. 막힌 것의 크기와 막은 것의 크기는 아무 상관이 없다.

    「막혔다」는 결론이 아니라 질문이다 - 무엇이 막았나, 치울 수 있나.

## 비율은 안심을 주고, 남은 수는 일을 준다

포탑 보고가 「건물 95%가 사거리 안 - 지킬 만큼은 지켜졌다」였다.

위키(Enemies)는 벌레가 목표까지 최단 경로로 가며, 우회할 길이 있으면
«장애물을 거들떠보지 않고» 돌아간다고 적는다. 그러면 사거리 밖에 남은
건물은 「아직 못 덮은 몫」이 아니라 그리로 곧장 난 **열린 문**이다.

    20회차: 38%를 「38% 지켜짐」으로 읽었다.
            실제 뜻은 「62%로 가는 뒷문이 늘 열려 있다」였다.
            포탑 55대 중 53대가 서로 사거리 안 - 간격은 멀쩡했다.
            틀린 것은 사슬의 «길이»였다.

그래서 남은 채수를 적는다. 95%는 거의 닫힌 것이 아니다. 열린 것이다.
자세한 조사는 `docs/defence.md`.

## 외울 것은 「+0.5」가 아니라 «중심을 찍는다»였다

벨트를 한 칸씩 걷어내다가 배운 것이 있었다.

    계획이 말하는 (28,-2) = 타일 모서리
    벨트가 실제로 선 자리 = (28.5,-1.5) = 타일 가운데
    한 칸을 가리키려면 그 칸의 «가운데»를 가리켜야 한다.

맞는 말이었다. 그런데 그것을 「좌표에 0.5 를 더한다」로 외웠고, 화로를
옮길 때 그대로 썼다. 걷기가 매번 헛돌았다. 같은 이사 명령을 세 번
되풀이했는데 화로는 한 대도 안 움직였고, 로그는 세 번 다 「옮겼다」고
찍혀 있었다.

    화로 position  (-45.0, 10.0)            <- «정수»다
    바운딩박스     (-45.7,9.3)-(-44.3,10.7)
    radius 0.4 로 (-45,10)     -> 1개
    radius 0.4 로 (-44.5,10.5) -> 0개

크기가 홀수 칸이면 중심이 타일 가운데에 오고, 짝수 칸이면 타일
«모서리»에 온다.

    1x1 (벨트.팔.나무.전봇대) : 중심 = 정수 + 0.5
    2x2 (화로.포탑)           : 중심 = 정수 그대로
    3x2 (보일러)              : 한 축은 +0.5, 다른 축은 정수

규칙으로 외운 것은 그 규칙이 «어디서 왔는지»를 같이 외우지 않으면
반대쪽에서 정확히 틀린다. 외울 것은 보정값이 아니라 뜻이었다.

    가리킬 곳은 그 건물의 «중심»이고, 중심이 어디인가는 «크기»가 정한다.

같은 뿌리에서 나온 것이 또 있다. 3x2 보일러가 물가 스물한 곳에서 거절당한
것도, 기준점에 «정수만» 더해 훑느라 반 칸 격자만 보았기 때문이었다.

## 한 군데를 고치면 같은 모양을 «전부» 찾아야 한다

포탑이 일곱 대에서 안 늘었다. 그런데 화면에는 매 순번 이렇게 찍혔다.

    guard: "포탑 1대 (테두리) + 탄약 20발씩"
    서 있는 포탑 7대
    alpha 가방 {gun-turret: 1}, bravo 가방 {gun-turret: 1}

만들어진 포탑이 가방에 쌓이는 동안 「세웠다」고 보고되고 있었다.
`craft ... wait: False` 는 「만들라고 시켰다」이지 «만들어졌다»가 아니다.
포탑은 8초가 걸리는데, 자리가 가까우면 걸어가는 데 그만큼 안 걸린다.

문제는 이 함정을 «이미 한 번 고쳤다»는 것이다. 바로 앞에서 탄약이 같은
이유로 비어 있었고, 그때 탄약만 고치고 바로 두 줄 위의 포탑은 안 고쳤다.

    고친 기억은 남고 고장은 남았다.

찾아보니 같은 모양이 넷 더 있었다 - 상자.화로.채굴기.벨트. 그 중 하나는
제작과 세우기 사이에 «걸음조차 없었다».

고치는 값은 싸다. 제작 큐는 선입선출이므로 «묶음의 마지막»만 기다리면
앞의 것도 끝나 있다. 기다리는 값을 한 번만 치르고 전부가 안전해진다.

    한 곳에서 찾은 함정은 «이름»으로 기억하고, 그 이름으로 저장소를 훑어라.

## 한 번 참이 되면 다시 거짓이 안 되는 값은 «순서»를 못 정한다

포탑이 둘에서 아홉이 되도록 덮인 비율은 11%에서 안 움직였다. 세우기는
매 순번 됐는데 «덮이지는» 않았다.

포탑이 어디에 섰는지 보니 전부 한 구역이었다.

    구역   건물   덮임
     1      5채     7     <- 발전소+연구소
     2     86채     2     <- 본진
     3     13채     1
     4      1채     1

순서를 정하는 식이 이랬다.

    (covers(g) > 0,  -worth(g),  covers(g)/len(g))

「맨몸인 구역이 먼저」라는 뜻으로 쓴 첫 항은 포탑이 0대인 동안에만
산다. 구역마다 한 대씩 서고 나면 전부 True 가 되어 무력해지고, 남는
것은 값어치뿐인데 값어치는 «변하지 않는다». 연구소가 있는 다섯 채짜리
구역이 영원히 1순위가 된 까닭이다.

세 번째 항이 정답이었지만 세 번째라서 닿지 못했다.

    순서를 정하는 값은 일이 진행되면 «같이 변해야» 한다.
    채우면 오르고, 오르면 뒤로 물러나는 값이어야 한다.

덮인 비율이 그렇다. 첫 항으로 올리자 본진(86채 중 2채)이 1순위가 됐다.

같은 모양을 조심할 것: 「~가 있는가」, 「~를 해 봤는가」처럼 한 번
참이 되면 영영 참인 조건을 정렬 맨 앞에 두면, 그 뒤의 기준들이 일을
못 한다.

## 한 점과 반경으로 묻는 것은 「그 크기를 안다」는 가정이다

회수 스크립트가 «돌아가고 있는» 제련 기둥을 걷으라고 내놓았다.

    죽은 것으로 나온 것: y=33 벨트 27칸, y=34.37.39 팔 각 12개
    그 줄은 지금 화로 스물셋을 먹이고 있는 줄이었다.

팔이 집는 칸에 무엇이 있는지를 `position=p, radius=0.4` 로 물었기
때문이다. 팔의 pickup_position 은 타일 가운데인데, 2x2 화로의 중심은
타일 «모서리»다 - 0.707 떨어져 있어서 안 잡힌다. 그래서 멀쩡히 일하는
팔이 전부 「집을 것도 놓을 데도 없다」로 나왔다.

반경을 0.8 로 넓히면 이번엔 맞는다. 그런데 3x2 보일러에서는 또 다르고,
5x3 증기기관에서는 또 다르다.

    칸으로 물으면 크기를 몰라도 된다.

    area = {{floor(x), floor(y)}, {floor(x)+1, floor(y)+1}}

무엇이 몇 칸을 먹든 그 칸을 덮고 있으면 잡힌다. 고치고 나니 살아 있는
칸이 376에서 416으로, 죽은 칸이 59에서 19로 바뀌었다.

이 저장소에서 «크기와 중심» 문제로 틀린 것이 이번이 셋째다.
벨트(1x1)에서 «가운데를 찍어라»를 배웠고, 화로(2x2)에서 그 규칙이
반대로 틀렸고, 여기서는 «묻는 방식» 자체가 틀렸다.

    좌표를 다룰 때 크기를 가정하지 말고, 가정하지 않아도 되는 질문을 골라라.

## 한가함은 «할 수 있나»고 가까움은 «언제 되나»다

고리들이 일꾼을 고를 때 「누가 한가한가」만 물었다. 실측(21회차):

    석탄밭(y=-19)에 채굴기를 세우라는 명령이 남쪽 y=104 에 있던 사람에게
    갔다. 120타일이다.

걸어가는 데만 순번이 여럿 들고, 그동안 그 일은 「시킨 것」으로 남아
다시 시키지도 않는다. 밖에서 보면 명령은 «나갔고» 결과는 안 온다 -
이 저장소가 여러 번 겪은 「시켰다 ≠ 됐다」가 거리에서 또 나온 것이다.

무리는 y=-19 부터 y=104 까지 150타일에 퍼져 있다. 명부가 여덟인데
그 중 누구를 보낼지는 «공짜로» 고를 수 있고, 공짜로 고를 수 있는 것을
안 고르면 그만큼 느려진다.

    idle(ai, names, near=(x, y))   # 가까운 사람부터

기준점은 창고다 - 거의 모든 계획이 재료를 집으러 창고에서 시작한다.

## 시험장인지는 「어디에 붙었나」가 아니라 «거기 무엇이 사는가»로 안다

21회차. 고칠 것이 있어 시험 묶음을 통째로 돌렸다. 세 개가 «돌아가는
게임»에 대고 돌았다.

    mcp_test    명부에서 bravo 를 지웠다   (시험이 끝나며 지우는 것이 맞다)
    persistence alpha 를 (18,11) 로 걷게 했다 - 기지에서 75칸
    smoke       「적대적 입력을 견디나」가 RCON 을 끊어 보급 순찰을 죽였다

셋 다 시험으로서는 «정확히 옳게» 동작했다. 시험장이 아닌 곳에서 돌았을
뿐이다. 그리고 그 사실은 어느 출력에도 안 적혔다 - 시험은 자기가 어디에
붙었는지 모르기 때문이다.

포트로는 못 가린다. `start-test-server.sh` 가 27015 를 «뺏어» 쓰므로
시험장과 본판이 같은 번호다. 주소로 묻는 한 답은 늘 같다.

그래서 세상에 묻는다. 갓 만든 판은 비어 있고 어리다.

    건물 628개 · 412분 -> 시험장이 아니다

`tests/sandbox.py` 의 `require_sandbox(ai)` 가 그것을 묻고, 아니면
시험이 «시작하기 전에» 선다. 정말 본판에 돌려야 하면 손으로
`AI_BRIDGE_ALLOW_LIVE=1` 을 켠다 - 손으로만 켜지는 것은 실수로 안 켜진다.

## 모양을 지키려는 시험이 «철자»를 지키면, 고칠 때마다 시험이 운다

같은 날, `stitch` 에 `guard` 인자를 하나 더 붙였다. 벨트 시험 둘이
한꺼번에 빨개졌다.

    찾는 것: return stitch(surface, force, tiles), best_gap, best_turn
    실제로 : return stitch(surface, force, tiles, guard), best_gap, best_turn

시험이 지키려던 것은 「길이 반드시 `stitch` 를 거친다」였는데, 지키고
있던 것은 «그 줄의 철자»였다. 코드는 멀쩡했고 시험이 어제에 묶여 있었다.

화로 줄을 12에서 18로 늘린 날에도 같은 일이 났다. `agent_test` 넷이
`range(52, 52+36, 3)` 을 박아 두고 있었다. 배치가 틀린 것이 아니라
시험이 어제 숫자를 붙들고 있었다.

    지키려는 것이 «모양»이면, 숫자와 철자는 상수에서 끌어와야 한다.

고친 뒤에는 `FURNACE_ROW` 를 몇으로 바꾸든 시험이 따라온다. 그리고
`bridge/settings.py` 의 `FURNACE_ROW = 12` 가 `plots.lua` 의 18 을 못
따라가고 있던 것도 그 김에 드러났다 - 한 군데를 고치면 같은 모양을
«전부» 찾아야 한다는 것을, 이번에는 시험이 대신 찾아 주었다.

## 스스로 넓히지 못하는 창고는 언젠가 반드시 기지를 멈춘다

21회차, 사용자가 물었다: "지금 작업 어디까지 진행됨?" 고리 여섯 개가
전부 헛돌고 있었다.

    창고     상자 3개 · 빈 칸 0   · 석탄 48
    창고 밖  상자 48개 · 빈 칸 708 · 석탄 10,847
    가방 안  철상자 38개

창고를 넓힐 상자 서른여덟 개가 «가방 안에» 있었다. 아무도 그것을 세울
일이라고 생각하지 않았다. 창고 크기는 아무 고리의 일도 아니었다.

번진 자리가 넷이다. haul 은 내려놓을 데가 없어 멈췄고, grow 는 창고
상자 «안만» 세어 석탄 48 로 읽고 멈춘 채굴기 스물여덟 대를 백 순번 넘게
그냥 두었고, 채굴기는 둘 데가 없어 스물아홉 중 스물여덟이 섰고, 화로는
그 뒤에서 굶었다.

    「창고에 없다」에는 답이 둘이다. 정말 없거나, 못 들어오거나.
    못 들어오는 것을 «없는 것»으로 읽으면 더 캐게 된다.

`scripts/depot.py` 가 이 한 가지만 한다 - 빈 칸이 마르면 선반 줄을
옆으로 늘린다. 한 번 돌려 상자 3개가 9개가 되자 빈 칸이 0에서 192가
됐다. 그리고 `grow.stock()` 은 이제 창고 «밖» 석탄도 따로 세어,
「굶었다」와 「막혔다」를 다른 말로 찍는다.

## 「깔라고 시켰다」를 「깔렸다」로 읽은 자리가 또 있었다 - 이번엔 벨트

21회차. `line_guard` 를 넣고 재시작한 뒤 flow.py 가 이렇게 찍었다.

    charlie: ore 14칸 (-55,44) 부터 - {'transport-belt': 11}
      채굴기 9대를 벨트 쪽으로 돌렸다

재시작 전에는 `echo: ore 1칸 (-57,58) 부터 - {}` 가 되풀이됐으니 분명
나아진 것이었다. 그래서 「벨트 꼬임이 해결됐다」고 말했다. 사용자가
답했다 - "벨트꼬임 아직인디".

세상에 물어보니 521칸 중 마주 선 것이 네 쌍이었다.

    y=58  x -77~-56 동(22칸) | -55 서(1칸) | -54~-45 동(10칸) | -44~-15 서(30칸)

`line_guard` 는 제 일을 했다. 같은 «칸»을 두 줄이 뺏는 일은 사라졌다.
대신 같은 «줄»을 나눠 가지면서 서로 반대로 깔렸다. 살아 있는 뺏기가
죽은 이음매로 바뀌었을 뿐, 흐르지 않기는 마찬가지였다.

    칸을 안 뺏는 것만으로는 모자라다. 줄도 안 뺏어야 한다.

파수꾼을 `route_for` 안으로 옮겼다. 길을 내는 모든 흐름이 거기를
지나므로 부르는 쪽에서 빠뜨릴 수가 없다 - 실제로 "ore" 말고 넷은 전부
빠져 있었다.

그리고 더 큰 것: **꼬였는지를 재는 것이 그때까지 하나도 없었다.**
health.py 는 포화와 굶음은 셌지만 방향은 안 봤다. 재지 않는 것은 언제나
괜찮아 보인다. `scripts/knots.py` 가 이제 그것을 세고, health.py 가
매번 부른다.

꼬임에는 세 가지가 있고 고치는 법이 다르다.

    역주행  곧은 줄 한가운데 한 칸만 거꾸로 - 양옆에 맞춘다
    홀로    뒤가 빈 한 칸이 남의 줄에 박혀 있다 - 옛 계획의 부스러기, 걷는다
    이음매  긴 줄 둘이 마주 달려왔다 - 여기는 답이 하나가 아니다

앞의 둘은 `--fix` 가 고친다. 이음매는 «무엇을 어디로 보내려던 것인가»를
알아야 정할 수 있어서 적기만 한다. 이번 이음매의 답은 우회로였다 -
동쪽에서 온 줄을 y=57 로 올려 서쪽으로 보내고 (-53,58) 에 «직각으로»
내려꽂았다. 마주 서면 멈추지만 직각으로 들어오면 팩토리오가 받아 준다.

## 임시로 둔 것을 안 걷으면, 임시가 아니라 «지형»이 된다

사용자가 짚었다 - "채굴기쪽에 벨트연결할거면 상자는 없애야지"

    벨트로 떨구는 채굴기   6대   <- 그 여섯 대 곁에 상자 15개가 그대로
    상자로 떨구는 채굴기  20대

상자는 「벨트가 아직 없을 때의 임시 출구」였다. 벨트가 오면 그 자리는
벨트 것인데, 남은 상자가 세 가지를 한다. 운반 당번이 헛걸음을 하고,
길찾기가 그 칸을 피해 돌아가고, 돌아간 길이 또 한 줄 깔린다.

모드에는 `LIFTABLE` 이 이미 있었다 - 벨트 «자리에» 앉은 상자는 걷는다.
그런데 임시 출구는 벨트 자리에 있지 않다. 채굴기 «옆»에 있다. 그래서
아무 규칙에도 안 걸렸고, 열다섯 개가 지형이 되었다.

`scripts/unbox.py` 가 그것만 걷는다. 팔이 붙은 상자(적재소의 은행)와
창고 상자는 건드리지 않는다 - 그 둘은 임시가 아니다.

## 한 줄이 다른 줄을 먹는 데 필요한 것은 «한 칸을 돌릴 권리»뿐이다

`others_guard` 를 넣고 배포했는데 사용자가 말했다 - "벨트가 점점
이상해지는데". 재 보니 이음매가 순번마다 걸어 다녔다.

    18:42  (-56,58) 동(26칸) <-> (-55,58) 서(41칸)
    18:45  (-55,58) 동(27칸) <-> (-54,58) 서(40칸)

벨트는 530칸에서 629칸으로 늘었다. 한 줄이 다른 줄을 한 칸씩 먹으면서
둘 다 영원히 깔고 있었다.

두 구멍이 있었다.

1. 파수꾼은 «길찾기»만 막는다. 이미 계획에 들어 있던 칸은 순번마다
   `missing` 이 「방향이 다르다」며 남의 벨트를 돌려놨다. 길은 피해 갔는데
   손은 그대로 뺏고 있었다.

2. 고정 좌표로 나는 줄(적재소 급전/배출, 제련 급전/배출)은 길찾기를
   안 거치므로 `storage.lines` 에 «없다». 없는 것은 피할 수 없다.

        길찾기가 피할 수 있으려면 «그 줄이 있다고 적혀 있어야» 한다.

둘 다 막았다. `own_lane()` 이 고정 줄도 제 땅을 적고, `in_a_run()` 이
「뒤에서 같은 방향의 벨트가 밀어 넣고 있는」 벨트는 못 돌리게 한다.
돌아가는 줄은 안 건드린다. 혼자 선 벨트는 옛 부스러기이니 돌려도 된다.

## 벨트를 「몇 칸 깔았나」로 재면 늘 잘하고 있는 것처럼 보인다

사용자가 시켰다 - "벨트물류부터 우선 검수좀해봐"

629칸이 «스무 덩어리»로 끊겨 있었다. 그리고 가장 큰 두 덩어리가 물건을
한 개도 안 나르고 있었다.

    칸수  실림  채굴기  넣는팔  빼는팔
     257    0      0       1       6   들어오는 것이 없다
     116    0      0       0      14   팔 열넷이 빈 벨트를 본다
      79   74      0      12       0   채우기만 하고 뺄 데가 없다
      10   10      7       0       0   채굴기 일곱이 채우는데 출구 0
       9    9      6       0       0   같은 모양

«채우는 줄»과 «비우는 줄»이 서로 안 이어져 있었다. 어느 쪽도 고장 난
데가 없다. 벨트는 멀쩡하고 팔도 멀쩡하고 채굴기도 멀쩡한데, 팔 스물이
굶고 채굴기 열셋이 「둘 곳이 없다」로 서 있었다.

그리고 끊긴 틈은 전부 한 칸에서 다섯 칸이었다.

    (-77,55) 남  채굴기 7대가 채우는 10칸 -> 3칸 건너 (-77,58)
    (-40,56) 서  꽉 찬 79칸            -> 2칸 건너 (-40,58)
    (-56,103)·(-69,-9) -> 1칸

    끊긴 것은 「길이 없다」가 아니라 «한 칸이 없다» 였다.

그때까지 재던 것은 꼬임(마주 섬)과 포화였다. 둘 다 0이어도 이 상태는
멀쩡해 보인다 - 섬은 꼬이지도 않고 포화되지도 않는다. 재야 했던 것은
«덩어리마다 들어오는 것과 나가는 것이 있는가» 였다.

`scripts/lines.py` 가 그것을 센다. 그리고 `--stitch` 가 가까운 틈을
잇는다 - 막다른 끝이 이미 가리키는 방향으로 «먼저» 가므로 그 칸은 돌릴
필요가 없고, 돌리지 않은 칸은 남의 줄과 싸우지 않는다.

첫 열두 칸을 잇자 죽어 있던 257칸이 276칸이 되면서 채굴기 열 대가 붙고
스물두 칸에 물건이 실렸다.

## 꽉 차는 벨트에 필요한 것은 벨트가 아니라 «문»이다

사용자가 짚었다 - "철판/구리판 등 화로에서 나오는애들이 지금 상자로
안들어가는듯". 그리고 같은 말에 "상자가 좀 모자란거같은데".

`lines.py` 가 이미 그것을 세고 있었다.

    칸수  실림  채굴기  넣는팔  빼는팔   무엇이 모자란가
      79    74      0      12       0   나가는 데가 없다 - 꽉 찬다
      60    54      1       6       0   나가는 데가 없다 - 꽉 찬다

화로 스물넷이 판금을 내고, 팔 열둘이 그것을 벨트에 얹고, 벨트는 꽉 찬
채로 선다. 그 줄에는 상자가 «한 개도» 없었다.

`sink.py` 가 이 교훈을 이미 한 번 배웠는데 - 「깐 길과 그 길에서 내리는
일은 다른 일이다」 - `sink.py` 는 «있는 상자»를 벨트에 잇는 도구다.
상자가 아예 없는 줄에는 쓸 것이 없었다.

    배운 교훈이 「그 도구가 다루는 모양」 안에서만 살아 있으면,
    모양이 조금 다른 자리에서 같은 고장이 처음처럼 난다.

`scripts/bank.py` 가 상자부터 세운다. 벨트 옆에 팔, 그 옆에 상자. 줄
끝에 문 하나가 아니라 «줄을 따라» 낸다 - 상자 하나가 차면 그 팔은 멈추고
뒤엣것은 그대로 밀리기 때문이다.

문 여섯 개를 내자 철판이 상자로 들어가기 시작했고 79칸 줄이
「나가는 데가 없다」에서 「이어져 있다」로 바뀌었다.

그리고 기준점이 또 둘이었다.

    모드가 아는 depot   (-56, 58)   <- 벨트가 향하는 곳
    스크립트의 --depot  (-55, 10)   <- haul.depot.py 가 쓰는 선반

그래서 `sink.py --depot=-55,10` 은 아무 말도 안 하고 아무 일도 안 했다.
그 자리에는 벨트가 한 칸도 없다. 「대답이 없다」를 「할 일이 없다」로
읽으면 안 된다 - 물어본 자리가 틀린 것일 수 있다.

## 이어졌나만 물으면 «어디로 이어졌나»를 영영 안 묻게 된다

사용자가 짚었다 - "아직 광석들이 상자로들어감. 화로로직행연결해야함"

그때 `lines.py` 는 덩어리 스물을 여덟으로 줄여 놓고 「이어져 있다」를
찍고 있었다. `knots.py` 는 마주 선 자리 0곳이었다. 그런데 광석은 화로에
한 톨도 안 갔다.

채굴기마다 «캔 것이 어디서 멈추나»를 따라가 보니 답이 나왔다.

    끝 (-45,58)  채굴기 10대   <- 창고 상자
    끝 (-1,56)   채굴기  6대   <- 화로 쪽
    끝 상자/땅   채굴기  3대

그리고 더 나쁜 것이 있었다. 창고가 «스스로에게 되먹이고» 있었다.

    y=62 배출줄 -동-> x=-45 -북-> y=58 급전줄 -동-> 창고상자 -팔-> y=62 ...

광석이 창고를 빙빙 돌았다. 끊긴 데가 한 군데도 없는 «완벽한 고리»였다.
이음매도 없고 포화도 아니고 섬도 아니다 - 어느 검사에도 안 걸린다.

    흐름은 「끊겼나」로만 재면 안 된다. 「돌고 있나」도 재야 한다.

`lines.py` 에 `where_ore_goes()` 를 넣었다. 채굴기가 떨구는 칸에서
흐름을 그대로 따라가 «멈추는 칸»을 센다. 상자로 끝나면 상자로 가는
것이고, 화로 줄에서 끝나면 화로로 가는 것이다.

## 빽빽한 밭은 지나갈 수 없다 - 돌아가야 한다

광석을 화로로 보내려는데 길이 없었다.

    y=58 급전줄이 x=-81~-15 를 «끊김 없이» 가로막는다
    지하벨트는 아직 연구 전이다 (recipe.enabled = false)

밑으로 못 지나면 위로 돌아야 하는데, 밭은 x=-86~-73 의 y=51~54 가
«전부» 채굴기였다. 밭 한가운데를 뚫는 길은 없다.

답은 밭 «동쪽»이었다. 수집줄을 동쪽으로 다섯 칸 더 뽑아 밭을 벗어난
다음 북으로 올렸다. 아홉 칸으로 채굴기 열 대의 행선지가 바뀌었다.

    가로지를 수 없으면, 가로지를 «필요가 없는» 자리를 찾는다.

y=50 수집줄이 이미 y=58 보다 북쪽이었다는 것이 열쇠였다. 그 줄에서
북으로 올리면 급전줄을 한 번도 안 건넌다.

## 길을 아무리 잘 놔도 캐는 것이 없으면 빈 벨트다

구리를 화로로 직행시키라는 지시를 받고 길부터 팠다. y=58 급전줄과
y=62 배출줄이 «두 겹»으로 가로막고 있어서 지하벨트 두 쌍으로 밑을
지났고, 포탑 한 대를 걷고 열두 칸을 새로 깔아 기둥을 화로까지 이었다.

그리고 구리는 한 톨도 안 왔다.

    구리 채굴기 1대 · 상태 no_fuel · 연료 0

캐는 것이 한 대도 안 돌고 있었다. 스무 칸 넘게 길을 내는 동안 그것을
한 번도 안 물어봤다.

    «나르는 길»을 고치기 전에 «날 것이 있나»를 먼저 물었어야 했다.

`lines.py` 의 덩어리 표에 「채굴기」 칸이 이미 있었는데, 그 값이 0인
것과 「그 채굴기가 돌고 있나」는 다른 질문이다. 세어지는 것과 도는
것은 같지 않다.

## 지하벨트는 「연구가 필요한 것」이 아니라 «지금 없는 것»이다

y=58 은 x=-81~-15 를 끊김 없이 가로막는다. 밑으로 지나려 했더니

    recipe "underground-belt" enabled = false

연구가 필요했고, 연구는 `military` 에 걸려 있었고, 빨간 과학은 여덟
순번 동안 «넣었다고 찍히면서» 한 개도 안 들어갔다.

    {'status': 'failed', 'error': 'bag is full - nowhere to put what I make'}

가방에 철광 1442 + 탄약 1407 + 철상자 244 가 든 알파에게 계속 시켰다.
가방이 가벼운 사람 하나를 고르자 한 번에 됐다.

    막힌 것이 세 겹이면 «가장 안쪽»을 먼저 봐야 한다.
    바깥 두 겹은 안쪽이 풀리기 전에는 몇 번을 고쳐도 같다.

## 벨트가 «있다»와 벨트가 «나른다»는 다른 말이다 - unbox 가 석탄을 말렸다

사용자가 시켰다 - "현재전체상황체크하고 문제가있을만한구석 있는지 봐바"

    석탄   상자 10,878 -> 64        (에이전트 가방에 1,193 이 따로 묶여 있었다)
    석탄 채굴기 6대 중 4대 "둘 곳 없음"

범인은 며칠 전에 내가 만든 `unbox.py` 였다. 기준이 「채굴기가 벨트에
떨구면 곁의 상자는 임시 출구다」였는데, 석탄 밭의 벨트는 한 칸에서 일곱
칸짜리 «토막»이었다. 어디로도 안 간다. 상자를 걷자 채굴기는 토막을
채우고 섰고 운반 당번은 집을 상자가 없어졌다.

고장은 조용했다. 석탄은 서서히 줄었고 어느 검사에도 「석탄이 준다」는
없었다. 재고 «수준»은 찍혔지만 «기울기»는 아무도 안 봤다.

- unbox: lines.py 에 물어 «빼는 팔이 붙은 덩어리»에 떨구는 채굴기만 본다
- 석탄 밭 -> 석탄 선반까지 전용 간선 41칸 + 선반 밑 받는 팔

## 검수에서 같이 나온 것들

**화로 아랫줄에는 넣어 주는 팔이 0개였다.** `feed_line` 은 윗줄(y=36)만
먹인다. 아랫줄(y=41) 열두 대는 그동안 운반 당번이 «손으로» 먹였고,
광석을 벨트로 직행시키자 창고 광석이 말라 손 급식이 끊겼다.

    working  y36: 10/12   y41: 2/12

하나를 직행으로 바꾸면 «그 옆에서 손으로 하던 일»이 같이 끊긴다.

**지하벨트를 모르는 검수는 제 손으로 간선을 끊을 뻔했다.** `lines.py` 가
입구 앞 칸을 「막다른 끝」으로 읽었고 잇기 고리가 그 칸을 돌리려 했다.
길이 막혀 실패했을 뿐이다. 새 부품을 들이면 그것을 «보는 눈»도 같이
들여야 한다.

**만들기는 늘 성공하고 세우기는 조용히 실패하면, 가방이 창고가 된다.**
철상자 683 + 포탑 244 = 철판 만오천 장이 가방에 있었다. 순번마다
「필요한 만큼」을 새로 만들어 더했다. 만들기 전에 가방부터 본다.

**고친 자리가 한 시간 뒤에 되살아난다.** 모드의 얼린 계획이 손으로 고친
«꺾이는 칸»을 순번마다 되돌렸다. `in_a_run` 은 곧은 줄만 지킨다.
`linked` - 먹여 주는 것도 있고 내보낼 데도 있는 벨트는 안 돌린다.

    흐르고 있는 것은 계획보다 옳다. 계획은 흐르라고 만든 것이다.

## 하나를 직행으로 바꾸면 «그 옆에서 손으로 하던 일»이 같이 끊긴다

화로 아랫줄(y=41) 열두 대에는 넣어 주는 팔이 0개였다. 모드의
`feed_line` 은 윗줄만 먹인다. 아랫줄은 운반 당번이 창고 광석을 «손으로»
날라 먹이고 있었고, 아무도 그것을 구조라고 생각하지 않았다.

광석을 벨트로 화로에 직행시키자 창고로 가던 광석이 끊겼다. 손 급식도
같이 끊겼다.

    working  y36: 10/12   y41: 2/12

y=43 에 아랫줄 전용 급전줄 33칸과 팔 열 개를 놓고, 남쪽에서 올라오는
구리 기둥을 (-55,43) 에서 동쪽으로 꺾어 물렸다. 윗줄은 철, 아랫줄은
구리가 된다. 꺾은 뒤 스물네 대가 전부 돌았다.

    자동화한 것 옆에 손으로 돌던 것이 있었는지, 끊기 전에 세어 본다.

## 저장은 「버스 + 디멀티플렉서 + 수위」로 짠다

사용자가 시켰다 - "물류도 구리판 / 철판 기준 나눠서 저장되도록 회로처럼
짜봐", 그리고 "상자가 한쪽에만 모든 물류가 저장되고있으니까 분산되서
저장되도록 하고".

    화로 윗줄(철)  -+
                    +- 판금 간선 -> [분배기: 구리판 -> 오른쪽] -+- y=7 구리 줄 -> 구리판 상자 (y=5)
    화로 아랫줄(구리)-+                                          +- y=8 철 줄   -> 철판 상자   (y=10)

**갈라 담기.** 2.0 의 분배기(splitter)는 제 몸에 필터가 있다. 전기도
회로망도 필요 없다 - `splitter_filter` 와 `splitter_output_priority` 두
값이면 한 줄이 둘로 갈린다. 버너 팔은 필터를 못 쓰고, 전기 팔은 발전소가
110칸 밖이라 못 쓴다. 남은 것 중에 «수동 부품 하나»로 되는 답이 있었다.

**고르게 담기.** 벨트가 상자 열셋 앞을 지나가면 맨 앞 팔이 다 집는다.
재 보니 판금 줄은 찬 칸이 3~32 (차이 29) 였다. 틀린 데가 없는 배치인데
결과는 「상자 하나짜리 창고」다.

`scripts/level.py` 는 상자의 «칸 제한»(빨간 X)을 수위로 쓴다.

    매 순번:  제한 = (가장 덜 찬 상자의 찬 칸 수) + 1

제한에 닿은 상자에는 팔이 더 못 넣고, 못 넣은 것은 벨트를 타고 다음
팔로 간다. 물을 붓는 것과 같다 - 어디에 붓든 수면은 같이 오른다.

    줄을 세우지 말고 «수위»를 정한다.

**문을 아무 데나 내면 안 된다.** `bank.py` 는 「꽉 찬 채 뺄 데 없는 줄」에
상자+팔을 붙였는데, 그 기준에 광석 간선도 걸렸다. 구리 기둥에 문 여섯
개가 났고 구리광이 화로 대신 그 상자들로 들어갔다. 그리고 사용자 말대로
판금은 화로 옆이 아니라 «저장구역»에 모여야 한다 - 쓰는 사람이 찾으러
가는 곳은 한 군데여야 하기 때문이다. `bank.py` 는 세웠다.

## 가방에 든 것은 창고에 없는 것이다

사용자가 시켰다 - "캐릭터가 가지고있는 자원은 바로 제작할게 아니라면
상자에 저장해야함."

그 말이 나오기 직전에 기지가 통째로 멎어 있었다.

    채굴기 25대 중 23대 연료 없음 · 창고 석탄 8
    golf 가방 석탄 542 · hotel 가방 석탄 353

석탄이 900개 가까이 «있었다». 팔에 넣을 연료로 70개씩 꺼내라고 시킨
것이 그보다 훨씬 많이 들려 나갔고, 남은 것은 가방에 그대로 있었다.
재고를 세는 검사는 상자만 본다 - 가방 속 석탄은 없는 석탄이다.

버너 기지에서 이것은 교착이다. 석탄 채굴기도 석탄으로 돈다. 한 번
꺼지면 누가 손으로 넣어 주기 전에는 스스로 못 살아난다.

- `scripts/stow.py`: 한가한 사람은 가방을 비운다. 세우려고 만든 것도
  넣는다 - 들고 다닌다고 세워지지 않는다. 남기는 것은 석탄 열 개뿐
- 부품 선반(y=18)을 따로 세웠다. 판금.석탄 줄은 수위 제한(level.py)이
  걸려 있어 부품이 들어갈 빈 칸이 없다
- health.py: 석탄이 300 밑이면 경보. 수준이 아니라 «바닥»을 본다

## 빈 손이 돌아오지 않는 고리는 돌고 있어도 안 도는 것이다

`lines.py --prune` 을 고리로 띄워 놓고 「걷는 중」이라고 보고했다. 한
시간 뒤에도 쓸모없는 벨트는 284칸 그대로였다. 로그에는 목록만 찍히고
「걷기」는 한 줄도 없었다.

정리 고리는 40초마다, 운반.방어.보급 고리는 10~25초마다 빈 손을 찾는다.
빈 손은 늘 빠른 고리가 먼저 채갔다. 오류도 없고 멈춘 것도 아니다 -
그냥 한 번도 차례가 안 왔다.

    같은 사람들을 여러 고리가 나눠 쓰면, 느린 고리는 굶는다.

전담을 붙였다. 고리가 «도는지»가 아니라 «일을 했는지»를 봐야 한다.

## 손으로 먹이는 기지는 커질수록 굶는다

21회차에 연료 교착이 «두 번» 왔다. 채굴기 25대 중 23대, 그다음 33대 중
22대가 연료 없음. 두 번 다 가방의 석탄으로 살렸고, 두 번 다 곧 되돌아왔다.

    버너 채굴기 150kW · 석탄 1개 4MJ  ->  석탄 20개가 9분
    33대 x 150kW = 4.95MW 를 전부 «손으로» 급유
    보급 고리: "61대 모자란 것 중 2대"

일꾼을 늘려도 소용없다. 채굴기를 늘리면 먹일 입도 같이 는다. 손 급유는
규모에 «비례»해서 일이 늘고, 일꾼은 여덟 명에서 안 는다.

    규모에 비례하는 손일은, 규모가 커지면 반드시 진다.

답은 연료를 «벨트가» 나르는 구조다.

    석탄 밭 채굴기 3대 -동향-> x=-64 기둥 -> y=-20 을 따라 150칸 -> 보일러 앞
    버너 팔 하나가 벨트에서 집어 보일러에 넣는다 (팔은 제가 나르는 석탄으로 돈다)
    보일러 1.8MW -> 전봇대 -> 전기 채굴기 (급유가 없다)

보일러 연료칸은 석탄 50개, 1.8MW 에서 111초분이다. 걸어서는 못 먹인다 -
발전소가 석탄 밭에서 120칸이다. 그래서 물이 있는 데까지 «석탄이 간다».

## 정리는 고리로 돌리는 일이 아니다

석탄 벨트 150칸을 다섯이 나눠 깔았다. 다 끝난 뒤에 세어 보니 0칸이었다.
오류는 어디에도 없었다.

옆에서 `lines.py --prune` 고리가 돌고 있었다. 갓 깐 줄은 아직 아무것도
안 받으므로 「영영 아무것도 안 받는 칸」과 구별이 안 된다. 다섯이 까는
동안 한 명이 따라다니며 도로 걷었다.

이 위험은 --spare 를 만들 때 이미 알고 있었다 («짓고 있는 줄은 상자로
지킨다»). 알고 있던 것과 막아 둔 것은 다르다 - 새 공사를 시작하면서
상자를 안 넓혔다.

    사람이 기억해야만 안전한 도구는 안전한 도구가 아니다.

`--prune` 과 `--every` 를 같이 주면 이제 거절한다. 정리는 짓기가 끝난
것을 확인한 뒤 한 번 부르는 일이다.

## 증상을 세 번 고쳤으면 원인을 안 잰 것이다

21회차에 석탄이 세 번 바닥났다. 세 번 다 「채굴기가 굶는다」로 읽고
가방의 석탄을 손으로 넣었다. 네 번째에는 구조를 바꿨다 - 전봇대를 석탄밭까지
끌고 전기 채굴기 넉 대를 창고행 간선 옆에 세웠다. 넉 대는 세우자마자 섰다.

    electric-mining-drill  waiting_for_space_in_destination  x4

간선이 꽉 차 있었다. 끝의 팔 여섯은 연료가 20~38 씩 있는데도 「놓을 데
없음」이었다. 석탄 선반 상자 여덟 개는 **빈 칸 0, 석탄 0** 이었다.

    y=14 (석탄 줄): iron-plate 17,900 · copper-plate 5,700 · 탄창 605 · 포탑 30

넣은 것은 내 코드다. `haul.where()` 는 제자리가 차면 `shelf.spare()` 로,
`stow.home_for()` 는 「이미 든 상자 먼저, 아니면 가까운 빈 상자」로 보냈다.
가장 가까운 빈 상자가 벨트가 채울 상자였고, 한 번 들어간 철판이 「이미 든
상자」 규칙으로 다음 철판을 불렀다.

    벨트는 다른 데로 못 간다. 사람은 간다. 양보는 사람 쪽이 한다.

- `shelf.BELT_ROWS` / `shelf.fits()` - 벨트가 채우는 줄은 제 물건만 받는다.
  규칙은 이 한 곳에만 있고 `spare()`, `stow.py`, `sortrows.py` 가 따른다.
- `sortrows.py` - 이미 들어간 것을 제 줄로 옮긴다. 다 옮기면 스스로 끝난다.
- `health.py` - 「석탄이 바닥이다」 옆에 「벨트 선반에 남의 물건」을 같이 잰다.

## 세운 수가 아니라 망의 수를 센다

전봇대 서른두 자리, 빠진 자리 0. 전기가 닿은 것은 스물두 개.
나무와 채굴기를 피해 한두 칸씩 민 자리끼리 전선 길이(7.5칸)를 넘었다.

    net 1 = 22   net 3 = 2   net 4 = 9   net 5 = 2

`wire.py` 는 발전기가 붙은 망을 본망으로 보고 섬마다 이을 자리를 고른다.
`health.py` 는 망이 둘 이상이면 경고한다. 덤으로 배운 것: 전봇대에게
`is_connected_to_electric_network()` 를 물으면 늘 거짓이다.
`electric_network_id` 를 발전기의 것과 견준다.

## 채굴기 자리는 광석이 아니라 떨어지는 칸에서 센다

`grow.py` 의 파종은 광석이 많은 칸을 골랐고 떨어지는 데는 안 봤다. 그래서
벨트를 깐 뒤에도 새 채굴기는 상자를 끼고 앉았다. `edrill.py` 는 벨트 칸에서
시작한다 - 전기 채굴기(3x3)는 벨트 칸 중심에서 옆으로 2칸이 중심이고 벨트
쪽을 본다. 벨트의 옆에만 앉힌다(머리와 꼬리는 벨트가 자랄 칸). 다 캔 버너
채굴기가 앉은 자리는 빈 자리로 치고 걷어낸 뒤 세운다.

    전기 채굴기 한 대: 90 kW 를 쓰고 석탄 0.5개/초(= 2 MW 어치)를 낸다.

## 손이 하나면 고리 둘이 그 손을 두고 싸운다

`charlie` 에게 전기 채굴기 넉 대를 시켰다. 아무것도 안 섰고 가방에는 석탄
열 개뿐이었다. 그 사이 `stow.py` 가 «한가한 사람»으로 보고 가방을 비웠다 -
재료로 챙겨 둔 채굴기 둘까지 창고로 갔다. 지시가 큐에 들어가기 «전»의 한
순번이 빈 손이었다.

    한 사람을 두 고리에 넣으면 고리끼리 상대의 재료를 치운다.

한 번 쓰는 지시를 내릴 사람은 고리에서 뺀다. 그리고 지시 안에서 재료를
«창고에서 챙기게» 한다 - 가방에 든 것을 전제로 하지 않는다.

같은 날 배운 것 둘:
- `demolish` 는 반지름 1.5 안에서 먼저 찾은 것을 걷는다. 벨트 줄에서는
  옆 칸을 걷는다 (보일러 석탄길이 두 번 끊겼다). `search_radius: 0.4`.
- `can_place_entity` 는 `build_check_type` 을 안 주면 바닥에 떨어진 물건
  하나에도 못 놓는다고 한다. 사람이 놓는 기준(`manual`)으로 묻는다.

## 석탄밭의 «옆»이 다 같은 옆이 아니다

전기 채굴기 넉 대를 석탄 간선 옆에 세웠다. 둘은 40분 만에 캘 것이 없어졌다.
5x5 안의 매장량을 재긴 했는데, 그 5x5 가 이웃 채굴기의 5x5 와 겹쳐서
같은 광석을 두 번 셌다. 밭의 부자 구역은 북서쪽(y -19..-8) 이었고 간선은
남동쪽 꼬리를 지나고 있었다.

    벨트가 «있는» 자리가 아니라 광석이 «있는» 자리로 벨트를 가져간다.

y=-9 에 수집 벨트를 새로 내고(x -76..-68, 기둥 x=-67 로 합류) 넉 대를
옮겨 앉혔다. 석탄 상자 재고 13 -> 4,599.

## 벨트가 «있는» 데가 아니라 광석이 «있는» 데로 - 심시티

사용자: "전기채굴기가 되니까 이제 화력채광드릴+채굴지상자들은 정리해도
되겠다. 정리하면서 전기채굴기 심시티좀 효율좋게 진행해봐"

버너 20대와 출구 상자를 걷었다(`remine.py --strip`). 밭마다 줄을 미리 재서
적고(`remine.LINES`) 깔았다: coal-2(y=-16), iron-2(x=-79), iron-3(x=-86).
줄 양옆에 3칸 간격으로 전기 채굴기(`edrill.py`). 전기 채굴기 20 -> 45대.

배운 것:
- 돌밭이 철밭 서쪽에 «붙어» 있다. 5x5 에 남의 광석이 한 칸이라도 있으면
  그 자리는 뺀다 - 돌이 철 줄에 오르면 화로가 벽돌을 굽고 벽돌이 선반에
  섞인다. 돌은 벨트에 안 올린다: 채굴기가 상자에 바로 떨군다(`quarry.py`).
- `lines.py` 는 분배기를 몰랐다. 필터 분배기 뒤의 선반 줄 80칸이 「들어오는
  것 없는 잔해」로 찍혔다. 분배기는 두 칸짜리 벨트로 읽는다(FAN).
  옛 제련구역 잔해 48칸은 걷었다.
- 선반 «빈 칸 수»는 틀린 잣대다. 벨트 앞의 팔은 제 상자에만 넣으므로 받는
  속도는 「빈 상자 수」다. 78상자가 다 찼을 때(판금 25만) 벨트 앞 자리는
  없었다 - 뒤 줄(상자 -> 팔 -> 상자)로 늘린다 (`racks.BACK`).
- 판이 쌓이기만 하면 창고가 아니라 병목이다. 간선 옆에 조립기 셋(톱니 1 +
  빨간 과학 2)을 세워 판을 팩으로 바꾼다(`assembly.py`). 섞인 간선이 오히려
  맞다 - 과학은 철과 구리 둘 다 든다. science.py 는 출구 상자에서 집어 간다.
