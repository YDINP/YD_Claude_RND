# @tgslot/slot-engine

순수 수학 엔진. DOM도 네트워크도 쓰지 않으며 서버와 클라이언트가 같은 코드를 공유한다.

```ts
import { parseGameMath, spin, evaluate, computeExactRtp, createSeededRng } from '@tgslot/slot-engine'
import { createCryptoRng } from '@tgslot/slot-engine/crypto-rng' // 서버 전용
```

| export | 하는 일 |
|---|---|
| `parseGameMath(json)` | `math.json` 검증. 스트립·페이라인·페이테이블 정합성까지 확인 |
| `spin(math, bet, rng, state?)` | 스핀 1회. 같은 시드 → 같은 결과. **베팅 레벨을 강제한다**. `state`가 있으면 프리스핀 |
| `assertBetLevel(math, totalBet)` | 총 베팅액이 `betLevels`에 있는 값인지 확인 |
| `evaluate(grid, math, betPerLine)` | 화면 심볼 → 승리 라인. 렌더러가 연출용으로 재계산할 때 |
| `getBetPerLine(math, totalBet)` | 총 베팅액 ÷ 라인 수 |
| `evaluateScatter(grid, math, totalBet)` | 화면 전체 스캐터를 세고 배당을 계산 |
| `evaluateWays(grid, math, betPerWay)` | ways 평가. 인접 릴 매칭 칸 수의 곱이 경로 수 |
| `applyMutations(math, grid, rng)` | 평가 직전 그리드 변형 파이프라인 |
| `getBetUnit(math, totalBet)` | 라인 게임은 라인당, ways 게임은 웨이당 베팅액 |
| `spinUnchecked(math, totalBet, rng, state?)` | 베팅 레벨 검사만 건너뛴 스핀. **RTP·감사 도구 전용** |
| `computeExactRtp(math, totalBet, opts?)` | 정확한 RTP. 조합 수를 보고 전수 조사와 해석적 계산을 **자동으로 고른다** |
| `computeAnalyticRtp(math, totalBet)` | 전수 조사 없이 닫힌 식으로 구한 정확한 RTP |
| `simulate(math, totalBet, spins, rng)` | 몬테카를로. 큰 모델과 회귀 검증용 |
| `createSeededRng(seed)` | xoshiro128**. 결정론. 테스트·시뮬·provably fair |
| `createCryptoRng()` | `node:crypto` 원시 난수. 실제 스핀은 라운드마다 crypto로 만든 256비트 시드를 `createSeededRng(`${seed}:${nonce}`)`에 넣어 돌린다(provably fair). 이 함수는 검증이 필요 없는 호출자용 |

`createCryptoRng`는 브라우저 번들에 `node:crypto`가 딸려오지 않도록
`@tgslot/slot-engine/crypto-rng` 서브패스로만 노출한다.

## 규칙

- 배수의 기준은 **라인당 베팅액**이다. 총 베팅액은 `paylines.length`로 나누어떨어져야 한다.
- 승리는 왼쪽 릴부터 연속 매치만 인정한다. 라인당 한 번만 지급한다.
- **긴 연속이 이긴다.** 연속 길이 k에서는 k 이하 중 배당이 정의된 가장 긴 개수로 지급한다.
  스키마가 배수의 단조증가(짧은 연속이 긴 연속보다 많이 줄 수 없음)를 강제하므로
  이 규칙은 "가장 비싼 해석"과 항상 같은 결과를 낸다.
- **매치 개수 1**은 릴 0만 맞으면 지급한다는 뜻이다. 나머지 릴은 무엇이든 상관없다.
  클래식 슬롯의 "체리 1개" 배당이 이것이다.
- 와일드는 스캐터와 다른 와일드를 대체하지 않는다. 스캐터는 페이라인 페이테이블을 가질 수 없다.
- **지급액은 항상 정수 코인이다.** 스키마가 모든 `betLevels`에 대해
  `라인당 베팅액 x 배수`가 정수임을 강제한다. 코드의 `Math.round`는 부동소수 안전망일 뿐이며,
  라운딩이 RTP를 위로 밀어 올리는 일은 일어나지 않는다.
- `grid`는 `grid[row][reel]` 순서이고 `positions`는 `[reel, row]` 좌표다.
- `Math.random`은 쓰지 않는다.

## 심볼 그룹 (믹스 배당)

"아무 BAR 3개"처럼 종류가 섞여도 지급하는 배당은 `groups`로 만든다.

```json
"groups": {
  "anybar": { "name": { "en": "Any BAR", "ko": "아무 BAR" }, "members": ["bar1", "bar2", "bar3"] }
},
"paytable": { "bar1": { "3": 15 }, "anybar": { "3": 5 } }
```

- 그룹 연속은 왼쪽부터 **모든 심볼이 멤버인** 구간이다. 와일드는 멤버 하나라도 대체할 수 있으면 낀다.
- 라인당 지급은 여전히 한 번이다. 심볼 해석과 그룹 해석을 모두 따져 배수가 큰 쪽을 고른다.
- 배수가 같으면 **순수 심볼 해석이 이긴다**. 화면에 "Any BAR"보다 "Single BAR"가 뜨는 편이 자연스럽다.
- 그룹 지급이면 `WinLine.symbol`이 그룹 id가 되고 `WinLine.group`에도 같은 값이 들어간다.
  클라이언트는 `group`이 있는지로 라벨을 고르면 된다.
- 그룹 id는 심볼 id와 겹칠 수 없고, 멤버는 선언된 심볼이면서 최소 한 릴의 스트립에 있어야 한다.
  스캐터는 멤버가 될 수 없다.

## 뮤테이션 파이프라인

정지 그리드를 **평가 직전에** 변형한다. `math.mutations`에 선언한 순서대로 적용되고,
각 단계는 앞 단계의 결과 위에서 동작한다.

| type | 하는 일 | RNG |
|---|---|---|
| `mystery` | 화면의 미스터리 칸 전부를 가중 추첨한 **하나의** 심볼로 교체 | 스핀당 1회 |
| `expandWild` | 지정 릴에 와일드가 `minCount` 이상이면 그 릴 전체를 와일드로 | 안 씀 |
| `expandWild` + `onlyIfWin` | 확장해도 지급이 **늘지 않으면** 확장을 되돌린다 | 안 씀 |
| `upgrade` | `from`이 `minCount` 이상이면 `to`로 승급 (`chance`로 확률형 가능) | chance일 때만 |
| `randomWild` | 확률 `chance`로 와일드 k개를 빈 칸에 낙하 (`countWeights` 가중) | 매 스핀 |

**RNG 소비 순서가 계약이다.**

```
릴 정지 (릴 수만큼) -> 뮤테이션 (선언 순서) -> 스캐터·프리스핀 판정 (추첨 없음)
```

스캐터 집계와 프리스핀 트리거는 **확정된 그리드의 함수**라 난수를 한 번도 쓰지 않는다.
잭팟은 엔진 밖(API)에서 스핀이 끝난 뒤에 판정한다.
같은 시드를 재생하면 정지 위치도 변형도 그대로 재현되므로 provably fair 검증이 성립한다.
`mutations.test.ts`의 "RNG 소비 순서 계약" 절이 뽑기 횟수까지 고정해 둔다.

`SpinResult`가 렌더러에 주는 것:

```ts
gridBefore: SymbolId[][]   // 뮤테이션 전, 릴이 그대로 멈춘 그리드 (연출 시작 프레임)
grid: SymbolId[][]         // 평가에 쓰인 그리드 (연출 종료 프레임)
mutations: MutationEvent[] // 실제로 무언가 바꾼 단계만, 선언 순서대로

interface MutationEvent {
  type: 'mystery' | 'expandWild' | 'upgrade' | 'randomWild'
  symbol?: SymbolId          // mystery는 공개된 심볼, upgrade는 승급 결과
  reels?: number[]           // expandWild가 덮은 릴
  cells: { position: [reel, row]; from: SymbolId; to: SymbolId }[]
}
```

뮤테이션이 없으면 `grid === gridBefore`이고 `mutations`는 빈 배열이다.

### `onlyIfWin`

`expandWild.onlyIfWin: true`면 확장을 일단 적용해 보고 **지급이 늘지 않았으면 통째로 되돌린다.**
"승리가 없으면"이 아니라 "**늘지 않으면**"인 이유는, 확장 전에 이미 있던 승리는 확장의 성과가
아니기 때문이다. 확장 전 지급이 0인 흔한 경우에는 두 규칙이 같은 뜻이 된다.
비교는 라인(또는 ways) 지급과 스캐터 지급의 합으로 하고, 라운딩이 판정을 뒤집지 않도록
충분히 큰 단위로 잰다. **되돌리든 말든 난수는 한 번도 쓰지 않으므로 RNG 소비 순서는 그대로다.**

되돌려진 확장은 `mutations` 배열에 아예 나타나지 않는다. 렌더러는 "확장이 없었던 스핀"으로 그린다.

### 가중 추첨의 정밀도

`nextInt`는 정수만 주므로 가중치를 정수 눈금으로 바꿔 쓴다.
**가중치가 전부 정수면 그대로 쓰기 때문에 추첨 확률이 해석식과 정확히 같다.**
소수 가중치가 섞이면 100만 눈금으로 반올림하며, 이때 항목당 확률 오차는 1e-6 이하다.
해석적 RTP는 선언된 가중치를 그대로 쓰므로 그만큼 어긋난다. 게임 팩이 정수 가중치만 쓰는 이유다.

### 스키마가 막는 것

- 미스터리 심볼은 페이테이블을 가질 수 없고, 공개 풀에 와일드·스캐터를 넣을 수 없다
  (공개 후 스캐터가 늘면 프리스핀 트리거가 흔들린다).
- **미스터리 심볼 자체가 와일드나 스캐터일 수 없다.** 대체 규칙과 트리거 확률이 스핀마다 달라진다.
- 확장·드롭 대상은 `wild: true`여야 한다.
- **두 뮤테이션이 같은 심볼을 읽을 수 없다.** 앞 단계가 그 심볼을 화면에서 지워 버리므로
  뒤 단계는 사실상 죽은 규칙이 되고, 결과가 선언 순서에 통째로 좌우된다.
  읽기 대상은 `mystery.symbol`·`expandWild.symbol`·`upgrade.from`이다.
  `randomWild.symbol`은 **놓는** 심볼이라 읽기 대상이 아니므로,
  랜덤 와일드로 뿌린 뒤 확장 와일드로 늘리는 조합은 허용한다.

## ways 페이 모델

```json
"payModel": "ways",
"ways": { "base": 243, "bothWays": false, "betDivisor": 25 }
```

- 페이라인이 없다. 왼쪽 릴부터 매칭이 이어지는 동안 **릴별 매칭 칸 수를 곱한** 것이 경로 수다.
- 지급액 = `경로 수 x 배수 x 웨이당 베팅액`. 와일드는 릴 카운트에 합산된다.
- 배수 기준은 **웨이당 베팅액 = 총 베팅액 / betDivisor**다. 총 베팅액이 아니다.
  라인 게임의 "라인당 베팅액"에 해당하는 단위이고 기본값은 업계 관례대로 25다.
- `ways.base`는 `rows^reels`와 같아야 한다 (5x3 = 243, 5x4 = 1024). 스키마가 강제한다.
- `bothWays`면 오른쪽에서도 읽는다. **지급 칸이 전 릴을 덮으면 왼쪽에서 한 번만 센다** (이중 지급 금지).
  판정 기준은 연속 길이가 아니라 **지급 길이**다. 5연속이어도 배당이 3개까지뿐이면 좌우의 지급 칸이
  서로 다르므로 각각 센다.
- 지급 길이가 연속 길이보다 짧으면 곱도 지급 길이까지만 센다.
  4연속인데 3개까지만 배당이 있으면 3릴 곱이다.
- **지급 칸이 전부 와일드인 해석은 후보 하나로만 지급한다.** 와일드는 거의 모든 후보를 대체하므로,
  와일드 3개짜리 줄은 시바·판다·카피… 모든 후보에 동시에 성립한다. 페이라인 평가기는 라인당 최고
  해석 하나만 고르지만 ways 평가기는 후보별로 더하기 때문에, 접지 않으면 같은 경로를 후보 수만큼
  지급하게 된다. 길이별 "챔피언"을 배당표만 보고 미리 정해 두고(`getWildChampions`), 와일드로만
  채워진 지급 칸은 챔피언만 지급한다. 우선순위는 페이라인 평가기와 **같다**:
  배수 > 순수 심볼 > 긴 연속 > 선언 순서.
- `WinLine`에 `ways`와 `direction: 'ltr' | 'rtl'`이 실리고 `line`은 -1이다.
  클라이언트는 `ways !== undefined`로 라인 승리와 구분한다.

**해석적으로 정확하다.** 릴이 독립이므로 곱의 기대값이 기대값의 곱으로 인수분해된다.

```
E[s] = Sum_k 배수(k) x (Prod_{i<j} E[c_i]) x (Prod_{j<=i<k} P(c_i>0)) x P(c_k=0)
```

`E[c_i] = rows x 스트립 빈도`이고 `P(c_i=0)`은 스트립을 한 바퀴 훑어 정확히 센다.
와일드 접기도 닫힌 식 안에 들어간다. 챔피언이 아닌 후보에서는 "지급 칸이 전부 와일드"인 몫을
빼는데, 그 몫도 릴별 인수 `E[매치 수 x 1{창에 와일드 아닌 매치 없음}]`의 곱으로 갈라지기 때문이다.
챔피언을 그리드가 아니라 **배당표만 보고** 정하는 이유가 이것이다.
`ways.test.ts`가 이 값이 전수 조사와 소수점 12자리까지 일치하는지 고정해 둔다
(짧은 배당표 + `bothWays` + 와일드가 섞인 모델까지 포함).

**남는 근사 하나.** 후보의 지급 창에 와일드와 일반 심볼이 섞여 있으면, 그 후보의 곱은 와일드로만
이뤄진 경로까지 함께 센다. 경로마다 최선의 해석을 고르는 이상적인 모델보다 조금 후하다.
업계 표준인 곱 모델의 성질이고, 엔진과 해석식이 **같은** 규칙을 쓰므로 RTP 수치에는 반영돼 있다.

## RTP 산출 경로 세 가지

`computeExactRtp`가 모델을 보고 알아서 고른다. 결과의 `method`로 어느 경로였는지 알 수 있다.

| method | 언제 | 정확도 |
|---|---|---|
| `enumerate` | 뮤테이션 없음 + 조합 수 <= 500만 | 정확값 |
| `analytic` | 뮤테이션 없음, 또는 `mystery`만 (ways 아님) | 정확값 (닫힌 식) |
| `monte-carlo` | 그 밖 전부 (확장·드롭·ways+뮤테이션) | 표본 추정 + 신뢰구간 |

`mystery`가 해석 경로에 남는 이유는 공개 심볼로 조건부화하면 릴 독립이 복원되기 때문이다.
`expandWild`는 확장 여부가 릴 창에 의존해 **행마다** 조건부 분포가 달라지므로,
페이라인별로 따로 계산해야 하고 "모든 라인이 동일"이라는 전제가 깨진다. 그래서 몬테카를로로 보낸다.

몬테카를로 결과에는 감사에 필요한 값이 함께 실린다.

```ts
monteCarlo?: { spins: number; seed: string; stdErr: number; ci95: [number, number] }
```

`mcSpins`·`mcSeed` 옵션으로 조절한다. 시드가 고정이라 CI에서 그대로 재현된다.
표준오차는 라운드 지급 배수의 표본표준편차 / sqrt(n)이다.

## 갬블 (검증만)

```json
"gamble": { "type": "coin-flip", "chance": 0.5, "payout": 2, "maxSteps": 5 }
```

엔진은 이 블록을 **검증만** 하고 추첨은 API가 한다. `GambleConfig` 타입을 내보내므로
`apps/api`가 자체 파서를 두지 않아도 된다.

스키마가 막는 것: `0 < chance < 1`, `payout > 1`, `1 <= maxSteps <= 10`, 그리고
**`chance x payout <= 1`**이다. 기대값이 1을 넘으면 갬블만 반복해 하우스 엣지가 사라진다.
`maxWinCap`(총 베팅액 배수)은 선택이고 자동 회수 상한으로 쓴다.

## 기본 RTP와 체감 RTP

엔진이 재는 것은 **기본 게임 RTP**뿐이다. `math.rtpTarget`도 기본 게임의 목표값이다.

허브가 얹어 주는 잭팟처럼 수학 모델 밖에서 돌아오는 몫은 `computeExactRtp`에 잡히지 않는다.
그 값은 manifest의 `jackpotContribution`에 적고, 둘을 더한 것이 플레이어 체감 RTP(`rtpTotalTarget`)다.
페이테이블만으로 목표 체감 RTP를 맞추면 허브 기여분만큼 하우스 엣지가 사라진다.

## 스캐터와 프리스핀

```json
"scatter": {
  "symbol": "scatter",
  "pays": { "3": 2, "4": 10, "5": 50 },
  "freeSpins": { "trigger": 3, "count": 10, "multiplier": 2, "retrigger": true }
}
```

- 스캐터는 페이라인과 무관하게 **화면에 보이는 칸 전부**를 센다. 한 릴에 2개가 보이면 2개다.
- 배수의 기준이 **총 베팅액**이다. 페이테이블(라인당 베팅액)과 다르니 주의할 것.
- 와일드는 스캐터를 절대 대체하지 않는다. 스캐터는 페이라인 페이테이블을 가질 수 없다.
- `spin(math, bet, rng, state)`에 `state`를 주면 프리스핀으로 처리한다.
  승리에 `state.multiplier`가 곱해지고 `state.freeSpinsLeft`가 1 줄어든다.
  0이 되면 `nextState`가 없다. 리트리거가 켜져 있고 다시 트리거되면 `count`회가 더 붙는다.
- `wins[].win`, `lineWin`, `scatterWin`은 **배수를 곱하기 전** 값이다.
  `totalWin = (lineWin + scatterWin) x multiplier` 하나만 배수가 적용된 값이다.

### 라운드 상한

한 라운드(유료 스핀 1회 + 거기서 파생된 프리스핀 전부)의 프리스핀은
`MAX_FREE_SPINS_PER_ROUND`(10,000)회를 넘지 못한다. **엔진이 캡으로 자른다.**
상한을 넘기는 리트리거는 남은 만큼만 부여하고, 잘렸다는 사실을 피처로 남긴다.

```ts
{ type: 'freeSpinsCapped', requested: 8, granted: 2, cap: 10_000 }
```

예외를 던지지 않는 이유는, 실제 스핀 경로에서 예외는 곧 유저의 라운드가 통째로 날아간다는
뜻이기 때문이다. 라운드를 끝낼 수 있게 자르고 사실을 기록하는 쪽이 안전하다.
이 상수는 `limits.ts` **한 곳에서만** 내보낸다. 시뮬레이터와 감사 도구도 같은 값을 import해서,
루프가 캡을 넘겼는지 확인하는 방어적 단언에만 쓴다(엔진이 캡을 지키면 도달할 수 없다).

## 해석적 RTP

5릴 게임은 정지 조합이 수억 개라 전수 조사가 불가능하다. 대신 닫힌 식으로 정확한 값을 구한다.
`computeExactRtp`가 조합 수를 보고 `MAX_ENUMERATION_COMBOS`(500만) 이하면 전수 조사를,
넘으면 `computeAnalyticRtp`를 쓴다. 결과의 `method`로 어느 경로였는지 알 수 있다.

**1. 페이라인.** 릴이 서로 독립이고 정지 위치가 균등하므로, 어떤 페이라인이든 릴 r에서 보는
심볼의 주변분포는 릴 r의 스트립 빈도와 같다. 기대값은 선형이라 라인끼리의 상관은 상관없다.
라인 수 x 라인당 베팅액 = 총 베팅액이므로, **라인 1개의 기대 배수가 곧 총 베팅액 기준 라인 RTP**다.
계산은 릴을 왼쪽부터 훑는 DFS다. 후보는 매치 집합에 없는 심볼을 만나면 죽고 그 시점의 연속 길이로
배당이 확정된다. 살아남은 후보가 없으면 남은 릴이 결과를 바꾸지 못하므로 거기서 가지를 자른다.

**2. 스캐터.** 릴 하나의 보이는 창(rows칸)에 스캐터가 k개 들어갈 확률은 스트립을 한 바퀴
훑으면 정확히 나온다. 릴이 독립이므로 화면 전체 개수 분포는 그 합성곱이다.

**3. 프리스핀.** 프리스핀은 유료 스핀과 같은 스트립을 돌리므로 한 회당 기대값이
`(라인 + 스캐터) x multiplier`다. 남은 것은 기대 횟수다. 부여된 스핀 1회가 스스로를 포함해
낳는 기대 스핀 수를 g라 하면, 그 스핀에서 확률 p로 count회가 더 부여되므로

```
g = 1 + p * count * g        =>   g = 1 / (1 - count * p)
기대 총 횟수 = count * g     =    count / (1 - count * p)
```

`count * p >= 1`이면 발산한다. 그런 모델은 만들면 안 되므로 예외로 막는다.
리트리거가 없으면 기대 횟수는 그냥 `count`다. 최종적으로

```
RTP = base + p * (count / (1 - count * p)) * multiplier * base       (base = 라인 + 스캐터)
```

`breakdown`에 이 세 조각이 그대로 들어가고 합이 `rtp`다.

**검증.** 3릴 + 스캐터 + 프리스핀 모델에서 전수 조사와 해석값이 소수점 12자리까지 일치하는지
테스트로 고정해 뒀다(`analytic.test.ts`). 닫힌 식 자체는 2릴 1행짜리 손계산 픽스처로 따로 잡는다.
그 테스트는 조각(라인 0.25, 스캐터 0.125, p = 1/16)을 손으로 세어 확인하고,
기대 프리스핀 횟수는 급수로 다시 더하며, **닫힌 식을 전혀 쓰지 않는 경로**로 한 번 더 검증한다:
모든 정지 조합을 엔진으로 정산해 표를 만든 뒤 "남은 프리스핀 k회" 상태 위의 확률 질량을 앞으로
굴려 기대 지급을 그냥 더한다. 두 값이 소수점 12자리까지 같다. `fruit-fiesta`는 500만 라운드 몬테카를로와
0.07 표준오차 안에서 일치한다.

**한계.** 적중률·최대 배수·배수 분포는 라인끼리 상관이 있어 닫힌 식이 없다.
해석 모드에서는 그 셋만 고정 시드 몬테카를로로 추정하고 `distributionIsExact: false`로 표시한다.
`sampleSpins: 0`을 주면 표본을 뽑지 않고 RTP만 낸다.

## 베팅액 검사

`spin()`은 `assertBetLevel`로 총 베팅액이 `math.betLevels`에 선언된 값인지 확인한다.
클라이언트가 임의 금액을 보내 페이테이블의 빈틈을 노리는 것을 막는 서버 측 관문이다.

`computeExactRtp`와 `simulate`는 튜닝 편의를 위해 이 검사를 하지 않는다.
라인 수로 나누어떨어지는 값이면 무엇이든 받는다. 둘 다 실제 스핀 경로가 아니다.

## Provably fair

엔진은 `Rng` 인터페이스만 받는다. 같은 시드를 넣으면 같은 결과가 나오므로
라운드 전에 serverSeed 해시를 공개하고 라운드 후 seed를 공개하면 유저가 결과를 검증할 수 있다.

**시드와 시드 해시는 `SpinResult`에 넣지 않는다.** 그것은 API의 라운드 레코드(`rounds` 테이블)가
소유하는 정보이고 Phase 2에서 붙인다. 엔진은 난수의 출처를 알 필요가 없고,
`SpinResult`는 "이번 스핀에 무슨 일이 일어났는가"만 담는다.

`SpinResult.nextState`(`RoundState`)는 프리스핀 잔여 횟수처럼 다음 스핀으로 넘길 상태를 위한
자리다. Phase 1 엔진은 채우지 않는다.
