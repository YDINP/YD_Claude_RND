# 웨이브 2 설계 — 5×3을 벗어난 그리드와 페이 모델

작성일: 2026-09-03 · 작성자: game-system-designer · 상태: 초안(엔진/렌더러/허브/API/아트 착수 대기)
참조: `docs/GAME_CATALOG.md` §2 #6–#8 · §3 · §4 · §6 · `docs/FEATURE_RESEARCH.md`(2026-09-03 반영 완료) · `packages/slot-engine/README.md` · `packages/renderer/README.md` · `docs/ART_DIRECTION.md` §5 v3 · `tools/rtp-sim/README.md` · `games/_template/HOWTO.md`

> §9는 `FEATURE_RESEARCH.md`의 피처 28종·컨셉 5종을 카탈로그 #3–#12와 대조해 최종 로드맵으로 정리한 것이고,
> §10은 리서치에 없는 **자체 추론 아이디어 5종**이다. 리서처가 카탈로그 원문을 읽지 못한 채 쓴 §4·§6 매핑은
> 여기서 대체된다.

## 0. 이 문서가 정하는 것

웨이브 1은 5×3 라인/ways만 다뤘다. 웨이브 2는 **그리드 모양과 페이 규칙 자체가 달라진다**. 그래서
"게임 3종을 더 만든다"가 아니라 **엔진의 페이 모델 축을 하나 더 여는 작업**이다. 축이 열리면 그 위의
게임은 데이터 팩으로 늘어난다.

| 축 | 웨이브 1 | 웨이브 2 |
|---|---|---|
| 그리드 | 5×3 고정 | 6×5 · 5×4 · 6릴 가변 행 · 3×1 |
| 페이 | `lines` · `ways` | + `cluster` · `anywhere` |
| 라운드 | 1스핀 = 1평가 | 1스핀 = **N회 평가**(연쇄) |
| 스핀 간 상태 | 프리스핀 잔여만 | + 스티키 좌표 · 누적 배수 |

**이름 결정 하나** — 지시는 `payMode`였으나 **기존 `payModel`을 그대로 두고 값만 늘린다.**
`payModel`은 `schema.ts:154`·`getBetUnit`·`ways.ts`·렌더러 `isWaysGame`·`rtp-sim` 분기까지
5개 패키지가 이미 읽는다. 개명은 마이그레이션 비용만 있고, 값만 늘리면 기존 팩 5종은 안 바뀐다.

## 1. 웨이브 2 라인업

카탈로그 #6·#7·#8을 **확정**하고, 구조적 다양성을 위해 2종을 **추가 제안**한다.

| # | id | 이름 (en / ko) | 스타일 | 그리드 | 페이 | 변동성 | 헤드라인 | RTP 산출 |
|---|---|---|---|---|---|---|---|---|
| 6 | `candy-cluster-pop` | Candy Cluster Pop / 캔디 클러스터 팝 | 캔디 글로스 | 6×5 | 클러스터 5+ | high | 클러스터 + 텀블 배수 사다리 | MC |
| 7 | `olympus-nectar` | Olympus Nectar / 올림포스의 신주 | 스타일라이즈드 3D | 6×5 | 아무 위치 8+ | high | 텀블 + 누적 배수 오브 | MC |
| 8 | `magi-stella` | Magi Stella / 마기 스텔라 | 애니 셀셰이딩 | 5×4 | 1024 ways | high | 프리스핀 스티키 와일드 | MC |
| **13** | `origami-realm` | Origami Realm / 접히는 왕국 | **페이퍼크래프트** | **6릴 × 2~5행 가변** | 최대 15,625 ways | high | 릴마다 행 수가 매번 바뀐다 | MC |
| **14** | `pixel-bar-blitz` | Pixel Bar Blitz / 픽셀 바 블리츠 | **픽셀 레트로** | **3×1** | 1 페이라인 | low | 30초 한 판, 미스터리 리빌 + 트윈 릴 | enumerate |

### 왜 이 둘인가, 그리고 7×7을 왜 뺐는가

**#13 가변 행**은 유일하게 *판 자체가 스핀마다 달라지는* 게임이다. 클러스터 2종이 평가 규칙을
바꿨다면 이쪽은 격자를 바꾼다. 인지도도 가장 높고(메가웨이즈 계열), 엔진은 `ways` 평가기를
릴별 행 수로 일반화하는 것이 전부다.

**#14 3×1**은 반대쪽 극단이다. 허브가 5릴 중변동으로 쏠려 있어 **한 손 30초** 자리가 비어 있다.
RTP가 전수 조사 정확값이라 몬테카를로 4종 사이의 회귀 기준점이 된다. (§9-1에서 리서치의 트윈 릴을
흡수해 엔진 작업이 0에서 6h로 늘었으나, 전수 조사 경로는 그대로 유지된다.)

**7×7은 제외한다.** (1) 430px에서 셀이 61.4px로 `ART_DIRECTION.md` §1 판독 기준선 64px 아래다. (2) 7×7에서 할 수
있는 것은 클러스터 아니면 pay-anywhere인데 둘 다 #6·#7이 이미 쓴다 — 판만 커지고 규칙이 같다.

**프리미티브 예산.** 카탈로그 규칙은 웨이브당 2개인데 #13이 3번째(P7 가변 행)를 요구한다. 그래서
**#6·#7·#8은 웨이브 2 본편, #13·#14는 웨이브 2.5**로 분리한다. P3·P4가 게이트를 통과한 뒤
P7(가변 행)과 P8(트윈 릴)을 연다. 둘 다 서로 독립이라 순서는 상관없다.

### #6 `candy-cluster-pop` — 캔디 클러스터 팝

> 사탕 다섯 개가 붙기만 하면 터지고, 터질 때마다 배수가 올라간다.

| 항목 | 값 |
|---|---|
| 그리드 / 페이 | 6×5 / 직교 인접 클러스터 5+ · 배수 기준 **총 베팅액** |
| 변동성 | `high` · 최초 클러스터 발생률 목표 32% · 평균 연쇄 1.6 · 3연쇄 이상 6% |
| RTP 94.5 구성 | 1차 클러스터 62.0 + 2차 이상 연쇄 24.0 + 프리스핀 8.5 |
| 베팅 레벨 | 20 / 40 / 100 / 200 / 500 / 1000 (총 베팅 기준 배수라 20의 배수로 고정) |
| 공수 (엔진/렌더/허브/API/아트) | 20 / 14 / 3 / 2 / 11 h |

**메커닉** — `DROP → FLOOD_FILL(≥5?) → PAY → REMOVE → GRAVITY → REFILL(strip-pull) → LADDER++ → FLOOD_FILL → …(그룹 없음) END`.
배수 사다리 `[1, 2, 3, 5, 8, 12, 20]`는 연쇄 인덱스로 인덱싱하고 마지막 값에서 고정한다.
스핀 시작 시 1로 리셋한다. 프리스핀은 스캐터 4+로 열리고 사다리가 **스핀 간 유지**된다(리셋 없음)
— 이것이 프리스핀 8.5%p의 실체다.

**엣지** — 한 셀은 정확히 한 그룹에만 속한다(방문 마킹). `maxCascades = 12`. 사다리는 유한 배열.
클러스터 5개짜리가 그리드 전체를 도미노로 밀지 않도록 저배당 심볼 3종의 밀도를 릴별로 비대칭 배치한다.

```json
"payModel": "cluster",
"cluster": { "minCluster": 5, "adjacency": "orthogonal", "wildJoins": true, "payUnitDivisor": 20 },
"cascade": { "enabled": true, "maxCascades": 12, "refill": "gravity", "source": "strip-pull",
             "resetOn": "spin", "multiplierLadder": [1, 2, 3, 5, 8, 12, 20],
             "ladderPersistIn": "freespins" },
"paytable": { "drop_red": { "5": 0.5, "8": 2, "12": 10, "20": 60 } }
```

심볼(10): `wild` `scatter` `heart` `star` `bean` `drop_red` `drop_blue` `drop_green` `drop_purple` `drop_yellow`

### #7 `olympus-nectar` — 올림포스의 신주

> 같은 심볼 여덟 개면 어디에 있든 터지고, 하늘에서 떨어진 배수 오브가 전부 합쳐진다.

| 항목 | 값 |
|---|---|
| 그리드 / 페이 | 6×5 / `anywhere` 8+ · 배수 기준 **총 베팅액** |
| 변동성 | `high` · 적중률 목표 22% · 오브 등장 스핀 비율 목표 45% |
| RTP 94.5 구성 | anywhere 60.0 + 배수 오브 24.5 + 프리스핀 10.0 |
| 베팅 레벨 | 20 / 40 / 100 / 200 / 500 / 1000 |
| 공수 | 14 / 12 / 3 / 2 / 12 h |

**메커닉** — `DROP → COUNT_ANY(≥8?) → PAY → REMOVE(해당 심볼 전부) → GRAVITY → REFILL → ORB_SPAWN(리필된 칸만) → COUNT_ANY → …(없음) ORB_COLLECT(Σorb × 누적 승리) → END`.

**오브는 리필된 칸에서만 스폰한다.** 매 연쇄마다 그리드 30칸을 전부 굴리면 RNG 소비 횟수가
그리드 내용에 따라 달라져 재생 계약이 지저분해진다. 리필 칸만 굴리면 소비 횟수 = 빈칸 수로
결정론적이고, "터진 자리에서 오브가 올라온다"는 연출과도 맞는다.

**엣지** — 오브는 자체 지급이 없고 승리가 있을 때만 회수한다. `combine: "sum"` 고정(곱하면 꼬리가
발산한다), 합 상한 `orbCap = 300`. 카탈로그의 `100:1` 가중은 **뺀다** — §3에서 계산하듯 100× 꼬리
하나가 감사에 필요한 스핀 수를 4배로 밀어 올린다. 최고값을 50으로 낮추고 가중을 올려 같은 기대값을
만든다. 프리스핀 누적 배수는 세션 종료 시 강제로 1로 리셋한다.

```json
"payModel": "anywhere",
"anywhere": { "minCount": 8, "removeAll": true, "payUnitDivisor": 20 },
"cascade": { "enabled": true, "maxCascades": 12, "refill": "gravity", "source": "strip-pull",
  "resetOn": "spin",
  "multiplierSpots": { "chance": 0.05, "spawnOn": "refill",
    "valueWeights": { "2": 50, "3": 30, "5": 15, "10": 6, "25": 3, "50": 1 },
    "combine": "sum", "cap": 300, "persistIn": "freespins" } },
"paytable": { "gem_red": { "8": 0.5, "10": 1.5, "12": 6, "20": 40 } }
```

심볼(11): `wild` `scatter` `zeus` `crown` `hourglass` `ring` `chalice` `gem_red` `gem_blue` `gem_green` `gem_purple`

### #8 `magi-stella` — 마기 스텔라

> 변신한 순간 화면에 박힌 별 와일드는 프리스핀이 끝날 때까지 사라지지 않는다.

| 항목 | 값 |
|---|---|
| 그리드 / 페이 | 5×4 / 1024 ways · 배수 기준 웨이당 베팅액(`betDivisor` 25) |
| 변동성 | `high` · 적중률 목표 28% · 프리스핀 진입 `p ≈ 0.008` |
| RTP 94.5 구성 | base ways 76.0 + 프리스핀(스티키) 18.5 |
| 베팅 레벨 | 25 / 50 / 100 / 250 / 500 / 1000 |
| 공수 | 10 / 8 / 3 / 4 / 12 h |

**메커닉** — 스캐터 3+ → 프리스핀 12회. 프리스핀 중 등장한 와일드는 잔여 스핀 동안 좌표에 고정된다.
리트리거 스캐터 2+ → +5회.

**엣지** — `maxStickyCells = 12`(20칸 중), 포화 시 신규 와일드 무시. 스티키 셀은 스트립을 돌리지
않으므로 ways 카운트에 항상 포함된다. 스캐터는 스티키 셀에 착지할 수 없다 → **스티키가 늘수록
리트리거 확률이 단조 감소**해 §3-4의 `r` 단조 비증가 조건이 구조적으로 성립한다. 세션 종료 시
`stickyCells`를 null로 강제한다.

```json
"payModel": "ways",
"ways": { "base": 1024, "bothWays": false, "betDivisor": 25 },
"scatter": { "symbol": "scatter", "pays": { "3": 2, "4": 8, "5": 40 },
             "freeSpins": { "trigger": 3, "count": 12, "multiplier": 1, "retrigger": true } },
"mutations": [ { "type": "stickyWild", "symbol": "wild", "phase": "freespins", "maxCells": 12 } ]
```

심볼(11): `wild` `scatter` `stella` `luna` `noir` `familiar` `heart_gem` `moon_gem` `star_gem` `clover_gem` `ribbon`

### #13 `origami-realm` — 접히는 왕국 (신규 제안)

> 종이가 접힌 만큼만 칸이 생긴다. 여섯 릴이 전부 펼쳐지면 15,625갈래다.

| 항목 | 값 |
|---|---|
| 그리드 / 페이 | 6릴 × **행 수 2~5 가변** / ways = Π(릴별 행 수), 최대 15,625 |
| 변동성 | `high` · 적중률 목표 25% · 평균 웨이즈 수 목표 2,900 (평균 행 3.78 → 3.78⁶) |
| RTP 94.5 구성 | ways 70.0 + 텀블 16.0 + 프리스핀(무한 사다리) 8.5 |
| 베팅 레벨 | 20 / 40 / 100 / 200 / 500 / 1000 (`betDivisor` 20) |
| 공수 | 16 / 12 / 4 / 2 / 12 h |

**메커닉** — 릴마다 행 수를 먼저 뽑고(가중 `{2:12, 3:26, 4:34, 5:28}`, 릴별 독립), 그 높이만큼
스트립 창을 연다. ways 수 = 행 수의 곱이라 스핀마다 달라진다. 승리 후 텀블은 **그 스핀의 행 수를
유지한 채** 돈다(연쇄 중에 판이 다시 접히지 않는다 — 접히면 종료 척도가 무너진다).
프리스핀은 사다리 상한이 없는 대신 `maxCascades`가 실질 상한이고, **최소 행 수가 2에서 3으로 올라가
평균 웨이즈가 커진다**(리서치 5.1 각색 흡수).

프리스핀에는 미스터리 변신도 얹는다. **초기 그리드에만** 적용하고 연쇄 중에는 돌리지 않는다 —
연쇄마다 리빌하면 사다리와 리빌이 서로를 증폭해 튜닝 감도가 통제를 벗어난다.

**엣지** — 행 수 가중은 정수. **최대 행을 5로 묶는 이유는 판독성이다**(§4-4). 정사각 캔버스에서
6행이면 세로가 먼저 묶여 셀이 57.9px로 64px 기준 아래로 떨어진다. `ways.base` 검증(`rows^reels`)은
가변 행 모델에서 성립하지 않으므로 스키마가 `variableRows`가 있으면 그 검사를 건너뛰고 대신
`maxWays = Π maxRows`를 기록한다. **스트립 길이 검사도 `variableRows.max` 기준이어야 한다**(검수 8).

```json
"payModel": "ways",
"variableRows": { "min": 2, "max": 5, "weights": { "2": 12, "3": 26, "4": 34, "5": 28 },
                  "freeSpinsMin": 3 },
"ways": { "maxWays": 15625, "bothWays": false, "betDivisor": 20 },
"cascade": { "enabled": true, "maxCascades": 10, "refill": "gravity", "source": "strip-pull",
             "resetOn": "spin", "multiplierLadder": [1, 2, 3, 5], "ladderPersistIn": "freespins" }
```

심볼(11): `wild` `scatter` `crane` `fox_mask` `paper_dragon` `lantern` `koi_paper` `fan` `gem_indigo` `gem_ruby` `gem_jade`

### #14 `pixel-bar-blitz` — 픽셀 바 블리츠 (신규 제안)

> 세 칸, 한 줄, 3초. 물음표가 뒤집히면 그게 전부다.

| 항목 | 값 |
|---|---|
| 그리드 / 페이 | 3×1 / 1 페이라인 · 배수 기준 라인당 베팅액(= 총 베팅액) |
| 변동성 | `low` · 적중률 목표 42% · 최대 배수 250x |
| RTP 94.5 구성 | 라인 78.0 + 미스터리 9.5 + **트윈 릴 7.0** |
| 베팅 레벨 | 10 / 20 / 50 / 100 / 200 / 500 |
| RTP 산출 | **enumerate** — 스트립 40칸 3릴 = 64,000 조합 × 링크 상태 3가지, 전수 조사 정확값 |
| 공수 | 4 / 6 / 2 / 0 / 9 h |

**메커닉** — 매치 개수 1·2·3을 전부 쓴다. 체리 1개(릴 0만) 배당이 적중률을 만들고, 세븐 3개가
최대 배수를 만든다. 미스터리 타일은 스핀당 1회 추첨으로 일괄 리빌한다(기존 `mystery` 그대로).

**트윈 릴(리서치 5.3 흡수).** 스핀마다 `chance = 0.25`로 인접 두 릴이 같은 심볼로 링크된다
(어느 쌍인지는 `{01: 50, 12: 50}` 가중). 릴 독립이 깨지지만 3릴 모델이라 **링크 상태까지 포함해
전수 조사가 그대로 돈다** — 조합이 64,000 × 3이라 해석식이 필요 없다. RNG 순서는
`링크 판정 1회 → (링크면) 쌍 추첨 1회 → 릴 정지 → 뮤테이션`이고, 링크된 쌍은 정지를 한 번만 뽑는다.

```json
"mutations": [ { "type": "mystery", "symbol": "mystery", "weights": { "seven": 3, "bell": 9, "cherry": 22 } } ],
"twinReel": { "chance": 0.25, "pairWeights": { "01": 50, "12": 50 } }
```

**엔진 신규 작업 0.** 렌더러만 `rows = 1` 레이아웃과 **nearest 스케일 모드**가 필요하다(픽셀 아트를
bilinear로 늘리면 뭉갠다). 이 게임의 존재 이유 절반이 "몬테카를로 4종 사이의 정확값 기준점"이다.

심볼(8): `wild` `mystery` `seven` `bar3` `bar2` `bar1` `bell` `cherry`

## 3. 엔진 설계

### 3-1. 스키마 확장

```ts
payModel: z.enum(['lines', 'ways', 'cluster', 'anywhere']).default('lines')
```

| 블록 | 필드 | 검증 |
|---|---|---|
| `cluster` | `minCluster`(3..cells) · `adjacency`('orthogonal'\|'diagonal') · `wildJoins` · `payUnitDivisor` | `payModel==='cluster'`일 때 필수, `paylines` 비어야 함 |
| `anywhere` | `minCount`(2..cells) · `removeAll` · `payUnitDivisor` | 위와 동일 |
| `cascade` | `enabled` · `maxCascades`(1..20, **필수**) · `refill`('gravity') · `source`('strip-pull'\|'rng-draw') · `resetOn` · `multiplierLadder` · `ladderPersistIn` · `multiplierSpots` | `maxCascades` 없으면 `parseGameMath` 실패 |
| `variableRows` | `min` · `max`(≤5) · `weights`(정수) | 있으면 `ways.base` 검사 대신 `maxWays` 검사. **스트립 길이 검사(`schema.ts:204`)도 `rows`가 아니라 `variableRows.max` 기준으로 바꾼다**(검수 8) — 안 그러면 최대 높이가 열렸을 때 스트립이 모자라 창을 못 채운다 |
| `twinReel` | `chance` · `pairWeights` | 링크 쌍이 인접 릴인지 검사. `payModel: 'lines'` 전용 |
| `mutations[].stickyWild` | `symbol`(wild:true) · `phase`('freespins'\|'always') · `maxCells` | `maxCells ≤ reels*rows` |

**페이테이블 재해석.** `cluster`/`anywhere`에서 페이룰의 키는 "연속 길이"가 아니라 **그룹 크기 /
그리드 전체 개수**다. 기존 `PayruleSchema`의 상한 검사(`count ≤ math.reels`)를 페이 모델별로 갈라야
한다 — 라인/ways는 `reels`, 클러스터/애니웨어는 `reels*rows`. 단조증가 검사와 "정의된 키 중 이하
최대값으로 지급"하는 규칙은 **그대로 재사용**한다. 크기 7짜리 그룹은 `5` 티어로 지급된다.

**배당 단위.** 클러스터·애니웨어는 라인도 웨이도 없으므로 **총 베팅액 기준**이다. 스캐터와 같은
규칙이고 정수 지급 검증도 스캐터 경로를 그대로 쓴다(`betLevel × multiplier`가 정수). `payUnitDivisor`는
설계자가 0.05 눈금까지 쓸 수 있게 `betLevels`가 그 값의 배수임을 강제하는 안전장치일 뿐, 나눗셈에
쓰이지 않는다.

**0으로 나누기가 네 곳에 있다(검수 2).** `getBetUnit`(`spin.ts:43`)은 ways가 아니면 무조건
`getBetPerLine`으로 보내고, 그 안(`evaluate.ts:209-217`)은 `totalBet % math.paylines.length`를 한다.
클러스터 게임은 `paylines`가 비어 있으므로 **`totalBet % 0 = NaN`으로 RangeError가 난다.** 같은 가정이
세 곳에 더 있다.

| 파일 | 위치 | 고칠 것 |
|---|---|---|
| `packages/slot-engine/src/spin.ts` | `getBetUnit` 43행 | `payModel` 3분기로: ways→`getBetPerWay`, cluster/anywhere→`totalBet`, lines→`getBetPerLine` |
| `packages/slot-engine/src/analytic.ts` | 216행 | 클러스터/애니웨어는 해석 경로에 들어오지 않으므로 **진입 전에 차단**(`isAnalytic`이 false) |
| `tools/rtp-sim/src/audit/compute.ts` | 98·115행 | 배당 단위 산출을 `getBetUnit`에 위임하고 자체 나눗셈 제거 |
| `packages/renderer/src/ways.ts` | 19행 | `betUnitCount`에 cluster/anywhere 분기 추가(승리 등급 유도용) |

네 곳이 각자 나눗셈을 들고 있는 것이 원인이므로, **E1은 `getBetUnit` 하나로 창구를 좁히는 일까지
포함한다.** 그러지 않으면 다음 페이 모델에서 같은 버그가 또 네 번 난다.

### 3-2. RNG 소비 순서 계약

**이것이 provably fair의 전부다.** 웨이브 1 계약(`릴 정지 → 뮤테이션 → 판정`)을 연쇄로 늘린다.

```
[가변 행] 릴별 행 수 추첨          (reels회, variableRows 있을 때만)
릴 정지                            (reels회)
뮤테이션                           (선언 순서, 웨이브 1과 동일)
연쇄 0: 평가 → 제거 → 중력 → 리필   (source='strip-pull'이면 0회 / 'rng-draw'면 빈칸 수만큼)
        오브 스폰                  (리필 칸마다 rollChance 1회 + 맞은 칸마다 값 추첨 1회)
연쇄 1: …                          (그룹이 없을 때까지, maxCascades에서 강제 종료)
스캐터·프리스핀 판정                (추첨 없음)
```

**리필은 기본이 `strip-pull`이다.** 릴별 포인터를 `stops[reel] - 1`에서 시작해 위로 올라가며
순환한다. 새 심볼이 난수를 안 쓰므로 **#6·#13은 `stops`만으로 연쇄 전체가 재생된다.**
다만 **#7은 오브 스폰이 난수를 쓰므로 `stops`만으로는 부족하고 `시드 + stateBefore`가 필요하다**
(검수 4). 재생 계약의 공식 문구는 §6과 같이 "`seedInput` + `stateBefore` + `totalBet`"이고,
`stops`만으로 되는 것은 오브가 없는 게임에 한한 부수 효과다. `rng-draw`는 스키마에만 두고 5종 다 쓰지 않는다. 카탈로그의 `strip-pull`과 지시의 `gravity`는 다른 축이라 둘 다 남겼다 —
`refill`은 **기존 심볼이 어떻게 움직이는가**, `source`는 **새 심볼이 어디서 오는가**다.
`cascade.test.ts`가 `mutations.test.ts`와 같은 방식으로 뽑기 횟수를 고정한다.

### 3-3. `RoundState` 확장

현재 `RoundState`는 세 필드가 **필수**다(`freeSpinsLeft`/`freeSpinsTotal`/`multiplier`).
신규 필드는 전부 선택으로 붙인다.

```ts
export interface RoundState {
  freeSpinsLeft: number
  freeSpinsTotal: number
  multiplier: number
  /** 연쇄 진행 상태. 스핀 안에서만 살고 응답에는 요약만 실린다. */
  cascade?: { step: number; multiplier: number; totalCascades: number }
  /** 프리스핀 동안 이월되는 사다리/오브 누적 배수. 세션 종료 시 1로 강제. */
  persistMultiplier?: number
  /** 이번 스핀에서 모인 오브 합. 회수 후 0. */
  orbSum?: number
  /** 스티키 와일드 좌표 [reel, row]. 세션 종료 시 null 강제. */
  stickyCells?: [number, number][]
  maxStickyCells?: number
}
```

### 3-4. 종료·발산 방지 (카탈로그 §4 규칙 적용)

| 피처 | 하드 캡 | 단조 감소 척도 | `r < 1` 근거 |
|---|---|---|---|
| 텀블(#6 #7 #13) | `maxCascades` 10~12 | `maxCascades − totalCascades` | 정적으로 못 구한다. **하드 캡이 유일한 보장**이고, `P(연쇄 지속) ≤ 0.55`·`평균 연쇄 ≤ 2.5`를 감사 항목으로 계측한다 |
| 배수 사다리 | 배열 길이(마지막 값 고정) | 연쇄 척도와 동일 | 유한 배열이라 발산 불가 |
| 오브(#7) | `orbCap = 300` | 연쇄 척도와 동일 | 합 상한이 곧 캡 |
| 스티키(#8) | `maxStickyCells = 12` | 프리스핀 `freeSpinsLeft` | 스티키가 늘수록 스캐터 착지 칸 감소 → `r` **단조 비증가** |
| 프리스핀 리트리거 | `MAX_FREE_SPINS_PER_ROUND` | `freeSpinsLeft` | 기존 `count × p < 1` 검사 그대로 |

**기존 `count × p < 1` 검사는 고치지 않는다(검수 9).** #8의 스티키는 리트리거 확률을 **낮추기만**
하므로, 스티키가 없는 상태로 잰 `p`가 언제나 실제보다 크다. 즉 지금 검사는 **보수적인 상한**이고
통과하면 실제 모델도 수렴한다. 스티키 때문에 검사식을 일반화할 필요가 없다는 뜻이다.

**`round.maxWinCap` = 총 베팅 5,000×를 연쇄 루프 안에서 검사한다.** 이름에 `round.`를 붙이는 이유는
**`gamble.maxWinCap`이 이미 있고 뜻이 다르기 때문이다**(검수 7) — 그쪽은 더블업 자동 회수 상한이다.
같은 이름을 두 층위에 쓰면 스키마를 읽는 사람이 매번 어느 쪽인지 되짚어야 한다.

캡에 닿으면 그 자리에서 연쇄를 끊고 캡 금액으로 지급하며 `{ type: 'winCapped', requested, granted, cap }`
피처를 남긴다. 프리스핀 상한과 같은 처리(예외를 던지지 않고 자르고 기록)다. **캡은 RTP 계산에도
똑같이 물린다** — 캡 없이 튜닝하고 캡 있게 서비스하면 실 RTP가 목표보다 낮아진다.

**전역 캡은 웨이브 1 재감사를 부른다(검수 7).** 5,000×를 전 게임 공통으로 켜면 기존 5종의 실 RTP가
바뀔 수 있다. 그래서 E6 게이트에 **"웨이브 1 5종의 캡 on/off RTP 차이가 측정 오차 안"**을 넣는다.
차이가 나오면 그 게임은 캡을 켜기 전에 재튜닝한다.

```ts
interface CascadeStep {

  removed: [number, number][]                      // 제거된 칸 [reel, row]

```

`SpinResult`에 `cascades: CascadeStep[]`(연쇄가 없으면 빈 배열)과 `rowsPerReel?: number[]`를 더한다.

**중간 그리드는 싣지 않는다.** 12연쇄 × 30칸 × 2장이면 응답이 부풀고 화면과 배당이 갈라질 여지가
생긴다. 웨이브 1의 `applyMutationEventsToGrid` 패턴대로 순수 함수 하나가 등식을 책임진다.
`gridBefore` = 최초 착지, `grid` = **마지막 연쇄가 평가한 그리드**다.

```ts
foldCascades(gridAfterMutations, cascades) === result.grid   // 테스트가 실제 스핀 수백 회로 고정
```

**`WinLine`에 `payKind`를 추가한다.** `packages/shared/src/schemas.ts:154`의 refine이
`(line === -1) === (ways !== undefined)`라 클러스터 승리가 **지금 스키마를 통과하지 못한다.**
웨이브 2의 첫 블로커다.

**단 기본값을 `'line'`으로 두면 안 된다(검수 1).** 이미 저장된 shiba-shrine 라운드는 `line: -1`에
`ways`만 있고 `payKind`가 없다. 기본값 `'line'`이 채워지면 새 refine이 `line === -1`인데
`payKind === 'line'`인 상태를 거부해서, **리빌(`/rounds/:id/seed`)과 멱등 재전송이 과거 라운드에서
통째로 터진다.** optional로 두고 preprocess로 추론한다.

```ts
payKind: z.enum(['line', 'ways', 'cluster', 'anywhere']).optional()
// preprocess: payKind ?? (ways !== undefined ? 'ways' : 'line')
// refine:     (line === -1) === (추론된 payKind !== 'line')
// cluster/anywhere는 count = 그룹 크기 / 그리드 전체 개수, ways는 undefined
```

추론을 preprocess에 두는 이유는 refine이 보기 전에 값이 채워져야 하기 때문이다. 역호환 파싱은
§8-3의 신규 테스트가 실제 저장 포맷으로 고정한다.

프리스핀 요약(`freeSpinsSummary`)에 `maxCascades`·`bestMultiplier`·`orbTotal`을 더해 종료 화면이
"이번 세션에서 무슨 일이 있었는지"를 말할 수 있게 한다.

### 3-6. RTP 산출과 시뮬레이터 — 25M으로는 모자란다

#6·#7·#8·#13은 **몬테카를로 전용**이다. 연쇄가 그리드 전체 상태에 의존해 닫힌 식이 없다.
`isAnalytic`이 `payModel ∈ {cluster, anywhere}` 또는 `cascade.enabled` 또는 `variableRows`이면
false를 돌려주게 한다(도구가 목록을 따로 들지 않는다).

문제는 정밀도다. 정식 감사 기준은 `ci95 반폭 ≤ 0.2%p`이고 반폭 = `1.96σ/√n`이다.

| 게임 | 예상 σ(라운드 배수) | 반폭 0.2%p에 필요한 n | 25M에서의 반폭 |
|---|---:|---:|---:|
| shiba-shrine (실측) | 4.41 | 18.7M | 0.173%p ✅ |
| magi-stella | 6.5 | 40.6M | 0.255%p ❌ |
| candy-cluster-pop | 9.0 | 77.8M | 0.353%p ❌ |
| olympus-nectar (오브 100× 포함) | 14.0 | 188M | 0.549%p ❌ |
| olympus-nectar (오브 상한 50×) | 8.5 | 69.4M | 0.333%p ❌ |

**웨이브 2 관행값 2천5백만 스핀으로는 네 종 모두 `표본 부족` FAIL이다.** (CLI의 `--spins` 기본값은
2,000,000이고 25M은 웨이브 1이 감사에서 실제로 쓴 값이다 — 검수 11. 어느 쪽이든 부족한 것은 같다.)
대응 넷:

1. **파일럿으로 필요 스핀 수를 먼저 구한다.** 100만 스핀으로 σ를 재고 `n* = (1.96σ / 0.002)²`를
   리포트 머리에 찍는다. 감사를 돌리기 전에 몇 분이 걸릴지 알 수 있어야 한다.
2. **분산을 설계로 깎는다.** #7의 오브 최고값을 100→50으로 내리면 필요 스핀이 188M→69M으로
   2.7배 줄어든다. 꼬리 하나가 감사 시간을 지배한다.
3. **시드 샤딩으로 병렬 측정한다. 합산기는 이미 있다** — `tools/rtp-sim/src/audit/mc.ts:10`의
   `mergeSimulations`가 청크별 평균·제곱합을 복원해 더하므로 한 번에 돌린 것과 같은 값을 낸다
   (검수 12). T1은 합산기를 새로 만드는 일이 아니라 **서로 다른 시드 K개로 `simulate`를 돌려
   `mergeSimulations`에 넣는 드라이버**를 붙이는 일이다. 합산 뒤 `stdDev`는 **모분산 추정치**이므로
   `SE = stdDev / √(총 스핀)`으로 쓰고, 리포트에는 샤드별 시드를 전부 남긴다.
4. **게임마다 필요한 스핀 수를 팩이 들고 있게 한다(검수 14).** `manifest.json`에 `auditSpins`를 두고
   감사 CLI가 그 값을 기본으로 쓴다. `readManifestExtras`에 필드 하나를 더하는 수준이라 이 넷 중
   가장 싸다. **정밀도 기준(0.2%p)을 완화하는 방향은 반대한다** — 반폭은 1/√n로만 줄어들어
   기준을 늘리는 순간 "RTP를 맞췄다"는 문장이 근거를 잃는다.

**카탈로그 §4도 같은 커밋에서 고쳐야 한다(검수 13).** 지금 카탈로그는 P3·P4에 대해
`monte-carlo SE ≤ 0.05%p (20M)`라고 적었는데, §3-6의 계산은 6×5 텀블에서 20M이면 SE가 0.18~0.28%p임을
보인다. 개정 문구는 §11에 그대로 옮겨 쓸 수 있게 따로 뒀다.

CI 게이트(40만 스핀)는 **그대로 둔다.** `max(0.5%p, 3·SE)` 규칙이 분산에 따라 자동으로 넓어지므로
고변동 모델에서도 깜빡이지 않는다. 다만 40만 스핀에서 반폭이 2%p를 넘으므로 **CI 통과를 "RTP가
맞다"로 읽으면 안 된다**는 기존 경고가 웨이브 2에서 특히 중요하다.

**`rtp-sim` 리포트 신규 절:**

| 절 | 내용 |
|---|---|
| 연쇄 깊이 분포 | 깊이 0~12별 발생 확률 · RTP 기여 · 평균 배수 |
| 배수 사다리 기여 | 사다리 단계별 지급 코인과 RTP 몫 |
| 오브 기여 | 스폰율 · 값 분포 실측 · 회수 성공률(승리 있는 연쇄에서만 회수) · RTP 몫 |
| 클러스터 크기 분포 | 크기 5..30별 발생 빈도와 티어별 지급 |
| 가변 행 분포 | 릴별 행 수 실측 분포 · 웨이즈 수 분포 · 평균 웨이즈 |
| 필요 스핀 수 | 파일럿 σ에서 유도한 `n*`와 실제 사용한 `n` |

## 4. 렌더러 설계

### 4-1. 연쇄 연출과 시간 예산

한 연쇄는 세 박자다. `팝/제거 → 중력 낙하 → 상단 리필`.

| 단계 | 기본 | 터보 | 모션 축소 |
|---|---:|---:|---:|
| 팝(제거 심볼 스케일 아웃 + 파열 파티클) | 220ms | 120ms | 60ms |
| 중력 낙하(거리 비례, 칸당 +40ms, 상한 380ms) | 260ms | 140ms | 60ms |
| 리필(상단에서 낙하, 릴별 40ms 스태거) | 260ms | 140ms | 60ms |
| **연쇄 1회 합계** | **740ms** | **400ms** | **180ms** |

12연쇄면 기본 8.9초로 **너무 길다.** 3회차부터 단계 길이에 0.78배를 누적 적용한다.

**하한은 절대값이 아니라 속도 상대값이다(검수 17).** 하한을 200ms로 고정하면 터보에서 8개 단계가
전부 200ms에 붙어 총합이 **2.96초로 게이트(2.6초)를 넘는다.** 하한을 `0.27 × 그 모드의 기본 단계
길이`로 두면 모드마다 같은 비율로 접힌다(기본 200ms · 터보 108ms · 모션 축소 49ms).

| 모드 | 단계 기본 | 하한 | 12연쇄 총합 | 게이트 |
|---|---:|---:|---:|---:|
| 기본 | 740ms | 200ms | **4.35초** | ≤ 4.5초 ✅ |
| 터보 | 400ms | 108ms | **2.35초** | ≤ 2.6초 ✅ |
| 모션 축소 | 180ms | 49ms | **1.06초** | ≤ 2.4초 ✅ |

감쇠와 하한은 **단계마다** 적용하고 총합에는 적용하지 않는다(총합에 걸면 어느 단계를 줄일지가
불확정이다). `cascadeStepDurations(count, opts)` 순수 함수가 단계별 배열을 돌려주고, 테스트가
배열의 합으로 위 세 상한을 고정한다.

연쇄가 끝난 **뒤에** `spinEnd`가 나간다(변형 연출과 같은 규칙). `skip()`은 연쇄 중에도 듣는다 —
남은 연쇄를 접고 화면을 `result.grid`로 확정하되 **누적 배수와 총 지급은 그대로**다.

### 4-2. 강조 — 선도 라인도 없다

| 페이 모델 | 강조 방식 |
|---|---|
| `cluster` | 그룹 셀 합집합의 **외곽선 한 겹**(marching squares) + 내부 심볼 fx. 그룹마다 `palette.winLine`을 그룹 인덱스로 순환 |
| `anywhere` | 해당 심볼 전 좌표에 고정 광채. **좌표를 잇는 선을 그리지 않는다** — 흩어진 8개를 선으로 이으면 거미줄이 된다. 대신 창 상단에 `×N` 카운트 뱃지 |
| `ways`(5×4, 가변 행) | 웨이브 1 규칙 그대로 |

### 4-3. 배수 오브 — 옆 칸이 아니라 그 자리에

카탈로그는 오브를 "릴 좌측 여백 폭 10%에 세로 스택"으로 뒀다. **바꾼다.** 6×5에서 폭 10%를
떼면 430px에서 셀이 65.5px → 59.0px, 390px에서는 53.5px까지 내려간다(§4-4 기준으로 재계산).
6릴은 이미 판독선 경계라 여백을 뗄 여유가 없다.

- 오브는 **놓인 칸 위에 배지**로 그린다(셀 크기의 42%, 우상단 정렬).
- 총합은 **릴 창 위 슬림 미터**(높이 8%) 하나에 숫자로만 표시한다. 문구는 롱프레스 툴팁.
- 회수 순간에만 오브가 미터로 빨려 들어가는 트윈 400ms.

같은 미터 컴포넌트(`PersistentMeterBar`)를 #6 배수 사다리, #13 프리스핀 사다리가 공유한다.

### 4-4. 가변 그리드와 셀 크기 (430px 세로 기준)

**앞선 초안의 표는 틀렸다(검수 15).** 심볼 간격(`constants.ts:7`의 `SYMBOL_GAP_RATIO = 0.06`)과
창 폭 비율을 빼먹고 `컨테이너 폭 ÷ 릴 수`로 계산했다. 실제 식은 이렇다.

```
셀 = min( 창 폭 / (reels + (reels-1)×0.06),  창 높이 / (rows + (rows-1)×0.06) )
창 폭 = window.w × 프레임 표시 폭
```

**`overflowX`로 푸는 길은 막혔다(15번 정정).** 사용자 요구가 "프레임 좌우 잘림 금지"라 렌더러가
`DEFAULT_OVERFLOW_X = 0`을 전 게임에 고정했다(`constants.ts:155`, `layout.test.ts:355`·`699`가 값까지
잠근다). 대신 **아트 규칙 v4**가 창을 `x 2–98%`(`window.w = 0.96`)까지 넓혀 해결한다.

`window.x = 0.02, w = 0.96`이면 `sideMargin = 0.02`, `footprint = 1.00`이므로 `byWidth`가 최소가 되어
프레임 폭 = 컨테이너 폭이고 **창 폭 = 컨테이너 폭 × 0.96**이다. 잘리는 것은 없다.

| 게임 | 격자 | 캔버스 | 릴 창 (x, y) | 셀 @430px | 셀 @390px | 묶이는 축 |
|---|---|---|---|---:|---:|---|
| #6 #7 | 6×5 | **1024×1024** | x 2–98%, y 10–90% | **65.5px** ✅ | 59.4px ⚠ | 폭 |
| #8 | 5×4 | **1024×1024** | x 2–98%, y 11–88% | **78.8px** ✅ | 71.5px ✅ | 폭 |
| #13 | 6릴 × 최대 5행 | **1024×1024** | x 2–98%, y 10–90% | **65.5px** ✅ | 59.4px ⚠ | 폭 |
| #14 | 3×1 | **1024×1024** | x 2–98%, y 34–65% | **132.3px** ✅ | 120.0px ✅ | 폭 |
| (기각) 7×7 | 7×7 | — | — | 56.1px ❌ | 50.9px ❌ | — |

창 높이는 "폭이 묶이는" 최소값에서 정했다. 6×5는 `h ≥ 0.799`라 0.80(y 10–90%), 5×4는 `h ≥ 0.766`라
0.77, 3×1은 `h ≥ 0.308`이라 0.31이다. 남는 세로는 마퀴와 받침이 쓴다.

**430px에서는 네 격자 모두 64px를 넘는다. 390px에서는 6릴 두 종이 못 넘는다(59.4px).**
이건 대응책으로 메울 수 있는 종류의 미달이 아니다 — 6릴이 64px를 채우려면 창 폭이 `64 × 6.30 = 403px`
이상이어야 하는데, 390px 기기에서는 **창을 100%로 열어도 불가능**하다. 그래서 이렇게 정리한다.

| 대응책 | 6×5 @390px | 판정 |
|---|---:|---|
| 간격 비율 `SYMBOL_GAP_RATIO` 0.06 → 0.04 (6릴 팩 한정) | 60.4px | **채택.** 코드 레버는 이것뿐이고 1px라도 벌어 준다 |
| 행 수 상한 하향 | 변화 없음 | **무효.** 6×5는 **폭**에 묶여 있어 행을 줄여도 셀이 안 커진다 |
| 창 폭 100%까지 확장 | 61.9px | 기각. 프레임 베젤이 사라져 아트가 성립하지 않는다 |
| 6릴 팩의 심볼 판독 기준을 58px로 명시 | — | **채택.** `ART_DIRECTION.md` §1의 64px는 5릴 이하 전제였다. 6릴 팩은 **58px 실루엣 판독**을 QA 기준으로 두고 내부 디테일을 줄여 외곽 대비를 키운다 |

즉 6릴 게임은 **작은 기기에서 심볼이 작아지는 것을 설계로 인정하고 아트로 방어한다.** 이 사실을
숨기고 64px를 적어 두면 아트가 QA에서 떨어진다.

- **#13의 캔버스는 1024×1536이 아니라 1024×1024다(검수 16).** 세로로 긴 캔버스는
  `layout.ts:311-312`의 `byHeight`가 스케일을 눌러 ART_DIRECTION v3가 고친 버그를 그대로 되돌린다.
  정사각 캔버스를 쓰고 **프레임 위아래 남는 영역은 배경(bg)이 채운다.**
- **그래서 #13의 최대 행은 6이 아니라 5다.** 창 높이 0.80에서 6행이면 세로가 먼저 묶여
  셀이 54.6px(@430px)로 내려간다. 6행을 쓰려면 `window.h ≥ 0.96`이어야 해서 마퀴가 사라진다.
  5행이면 폭이 묶여 65.5px가 유지된다.
  **최대 웨이즈는 46,656에서 15,625(5⁶)로 줄어든다.** 헤드라인 숫자를 잃는 대신 판독성과
  프레임 규격 공유(#6·#7과 같은 창 좌표)를 얻는다.
- **가변 행은 셀 크기를 고정하고 릴 높이를 바꾼다.** 셀 크기는 최대 행(5행) 기준으로 한 번 정하고,
  행이 적은 릴은 창 안에서 세로 가운데 정렬한다. 접힌 종이가 짧아지는 연출이라 테마와도 맞는다.
- 캔버스 크기는 `gpt-image-1`이 허용하는 세 값(1024×1024 / 1024×1536 / 1536×1024)만 쓴다.
  결과적으로 웨이브 2 다섯 종이 **전부 1024×1024**를 쓰고, 그중 셋(#6·#7·#13)은 창 좌표까지 같다.
- **#14는 nearest 스케일 모드가 필수다.** 픽셀 아트를 기본 필터로 늘리면 뭉갠다.
  `Theme`에 `textureScaleMode?: 'linear' | 'nearest'`(기본 linear)를 더한다.

### 4-5. 신규 이벤트

```ts
| { type: 'cascadeStep'; index: number; total: number; stepWin: number; multiplier: number
    removed: number; phase: 'start' | 'end' }
| { type: 'multiplierMeter'; total: number; added: number; reason: 'ladder' | 'orb' }
```

**`clusterWin` 이벤트는 만들지 않는다(검수 18).** `winLine`이 이미 `symbol`·`count`·`win`·
`index`·`total`·`cycle`을 싣고 있어 필드가 전부 겹친다. **`winLine`에 `payKind`를 더하는 것으로 끝낸다** —
허브는 `payKind === 'cluster'`일 때 `count`를 그룹 크기로 읽어 `심볼 ×N개 · 금액`을 그리면 된다.
이벤트를 하나 더 두면 허브가 같은 문구를 두 경로로 그리게 되고, 어느 쪽이 왔는지에 따라 순환
카운터가 어긋난다.

`cascadeStep`은 연쇄마다 `start`/`end` 한 쌍씩 정확히 나간다(변형 이벤트와 같은 계약). 건너뛴
연쇄는 둘 다 내지 않는다.

### 4-6. 연쇄 게임에서 `showWins`는 무엇을 받는가

지금까지 이 문서는 정하지 않았다(검수 19). 확정한다.

| 항목 | 계약 |
|---|---|
| 호출 시점 | 연쇄 재생이 **전부 끝난 뒤 한 번** 호출한다. 연쇄마다 부르지 않는다 |
| `wins` 인자 | **모든 연쇄의 승리를 이어 붙인 배열**(`cascades.flatMap(c => c.wins)`). 같은 심볼이 여러 연쇄에서 이겼으면 각각 별개 항목으로 남는다 — 합치면 어느 연쇄의 배수가 곱해졌는지 사라진다 |
| A단계 `totalWin` | 라운드 총 지급(배수 적용 후). 즉 `SpinResponse.totalWin` |
| A단계 등급(`tier`) | 같은 총 지급 기준. `winTier(wins, math, totalBet)`가 아니라 **`totalWin / totalBet`으로 직접** 판정한다. 연쇄 게임은 `wins`의 배수 합이 사다리·오브를 반영하지 않아 등급이 낮게 나온다 |
| B단계 | 연쇄 순서대로, 한 연쇄 안에서는 배당이 큰 심볼부터. `winLine.index/total`은 이어 붙인 배열 기준 |
| 강조 좌표 | 그 승리가 성립한 **연쇄 시점의 그리드** 좌표다. 최종 그리드에는 그 심볼이 없을 수 있으므로, B단계가 연쇄 인덱스에 맞는 중간 그리드를 `foldCascades`로 되짚어 그린다 |

마지막 항이 이 계약에서 가장 조심할 곳이다. 최종 그리드 위에 초기 연쇄의 좌표를 칠하면
**엉뚱한 심볼이 이긴 것처럼 보인다.**

## 5. 허브 설계

### 5-1. 도움말 페이지 변형

현재 탭은 `paytable | paylines | features | fairness`다. `paylines` 탭을 **페이 모델별로 치환**한다.

| `payModel` | 2번 탭 | 내용 |
|---|---|---|
| `lines` | 페이라인 | 지금 그대로 |
| `ways` | 웨이즈 | 인접 릴 곱 설명 + `betDivisor` 안내 (+ #13은 행 수 가중표) |
| `cluster` | 클러스터 | 인접 정의 그림 · 최소 크기 · **크기 티어 표** · 한 셀은 한 그룹 |
| `anywhere` | 아무 위치 | 위치 무관 카운트 · 최소 개수 · **개수 티어 표** |

`paytable` 탭의 열 머리는 페이 모델을 따른다 — 라인/ways는 `3개 / 4개 / 5개`, 클러스터는
`5+ / 8+ / 12+ / 20+`, 애니웨어는 `8+ / 10+ / 12+ / 20+`. 배수 기준 문구도 갈라진다
("라인당 베팅액" / "웨이당 베팅액" / "**총 베팅액**").

`features` 탭에 연쇄·사다리·오브 절을 추가한다. 오브 규칙은 **세 문장으로 못 박는다**:
오브는 스스로 지급하지 않는다 · 승리가 있는 연쇄에서만 합쳐진다 · 합은 300배에서 멈춘다.

### 5-2. WinStrip

| 상황 | 라벨 | 금액 줄 아래 |
|---|---|---|
| 클러스터 승리 | `WIN` | `젤리 ×7개 · 1,200` |
| 애니웨어 승리 | `WIN` | `루비 ×9개 · 4,500` |
| 연쇄 진행 중 | `CHAIN 3` | `×5 배수 · 누적 8,200` |
| 오브 회수 | `ORB` | `+×24 적용` |

`lineLabel.key`가 바뀔 때마다 팝하는 기존 동작을 그대로 쓴다. 연쇄 카운터는 `cascadeStep` 이벤트로
갱신하고, 총 배당 롤업은 **연쇄가 전부 끝난 뒤 한 번만** 굴린다(연쇄마다 굴리면 숫자가 요동친다).

### 5-3. 디버그 프리셋 3종 추가

`SpinDebugPresetSchema`(shared) → `matchesDebugPreset`(api) → `DEBUG_PRESETS`(hub) 세 곳을 함께
늘린다.

| 프리셋 | 판정 | 예상 탐색 비용 |
|---|---|---|
| `cascade3` | `result.cascades.length >= 3` | 발생률 ≈ 6% → 5,000 시도로 충분 |
| `orb` | `cascades.some(c => c.orbs?.length)` **그리고** `totalWin > 0` | 발생률 ≈ 20% |
| `stickyWild` | `nextState.stickyCells.length >= 3` | **프리스핀 중에만 성립** |

`stickyWild`는 기본 스핀에서 절대 매칭되지 않는다. 디버그 패널이 이 프리셋을 고르면 "먼저
`freeSpins`로 진입한 뒤 사용" 안내를 띄우고, 프리스핀 세션이 없으면 버튼을 비활성화한다.
해당 게임이 그 피처를 갖지 않으면 프리셋 자체를 목록에서 숨긴다(`math`를 보고 판정).

**탐색 예산을 그대로 두면 스핀 락이 막힌다(검수 20).** `findDebugSeed`는 조건을 만족할 때까지
`spinWithState`를 최대 5,000회 재실행하는데, 연쇄 게임의 스핀 한 번은 평가를 최대 12회 돌리므로
라인 게임보다 한 자릿수 비싸다. 그 루프가 지금은 **유저별 스핀 락 안에서** 돈다. 둘 중 하나를 한다.

1. **연쇄 게임의 `maxTries` 상한을 500으로 낮춘다.** `cascade3`·`orb`의 발생률이 6~20%라 500회면
   실패 확률이 사실상 0이고, 최악 지연이 12분의 1로 줄어든다. (기본값 5,000은 라인 게임용으로 유지)
2. 또는 **탐색을 락 밖으로 뺀다.** 시드 탐색은 지갑·원장·라운드를 건드리지 않는 순수 dry-run이므로
   락이 필요 없다. 매칭된 시드를 들고 들어와서 락 안에서는 확정만 한다.

1번이 싸고 2번이 옳다. **1번을 웨이브 2에 넣고 2번을 백로그에 남긴다.** 어느 쪽이든 §8-3의
"디버그 탐색 지연 상한" 테스트가 회귀를 잡는다.

## 6. API 설계

| 항목 | 변경 |
|---|---|
| 상태 저장 | `game_states`에 컬럼을 피처마다 늘리지 않는다. **`featureState` JSON 한 칸**에 `RoundState`의 선택 필드를 통째로 담고 zod로 검증한다. 스티키 좌표·누적 배수·오브 합이 전부 여기 들어간다 |
| 복원 | 새로고침·앱 재시작 후 재개는 **서버 재조회만** 인정한다. 클라 로컬 복원 금지 |
| 세션 종료 | 프리스핀이 끝나면 `stickyCells = null`, `persistMultiplier = 1`을 **서버가 강제**한다. 정상 소진과 **`expiresAt` 만료가 같은 정리 경로를 타야 한다**(검수 21) — 만료로 사라진 세션의 스티키가 남으면 다음 세션이 남의 와일드를 물려받는다 |
| 재생(reveal) | `GET /rounds/:id/seed`에 **`stateBefore: RoundState \| null`**을 더한다. **저장 위치가 지금 없다**(검수 6) — `game_states`는 *현재* 상태만 들고 있어 과거 라운드의 진입 시점 상태를 복원할 수 없다. **라운드 레코드에 컬럼을 추가**해 스핀 직전 상태를 함께 적는다 |
| 연쇄 재생 | `seedInput` + `stateBefore` + `totalBet`이면 검증자가 `spinWithState`로 연쇄 전체를 되짚는다(§3-2) |
| 멱등 재전송 | **변경 있음**(검수 5). `routes/games.ts:215-224`는 저장된 `stops`에서 응답을 **재조립**하는데, 연쇄·오브는 `stops`만으로 복원되지 않는다(#7은 난수를 쓴다). 둘 중 하나를 골라야 한다 — (a) 라운드 레코드에 `cascades`를 통째로 저장하거나, (b) 저장된 `seed`·`nonce`·`stateBefore`로 **결정론 재실행**해 응답을 다시 만든다. **(b)를 택한다**: 저장 용량이 늘지 않고, `foldCascades` 등식이 이미 재실행 결과를 보증한다 |
| 응답 크기 | 12연쇄 최악에서 `cascades`가 약 6KB. 중간 그리드를 싣지 않기로 한 §3-5 결정이 여기서 값을 한다. §8-3에 실측 상한 테스트를 둔다 |

**`manifest.lines: 0`은 지금 스키마가 거부한다(검수 3).** `packages/game-sdk/src/manifest.ts:17`과
`packages/shared/src/schemas.ts:71`이 둘 다 `z.number().int().min(1)`이다. 셋을 함께 고친다.

1. 두 스키마의 `lines`를 **`.min(0)`**으로 완화한다.
2. `manifest.json`에 **`payModel`을 싣는다.** 지금 게이트는 `lines` 값만 보고 라인/ways를 구분하는데,
   그 방식으로는 `0`이 "클러스터"인지 "빠뜨린 값"인지 알 수 없다.
3. 게이트가 `payModel`로 비교 대상을 고른다 — 라인은 `paylines.length`, ways는 `ways.base`(가변 행이면
   `maxWays`), 클러스터/애니웨어는 `0`.

## 10. 자체 추론 아이디어 5종 (리서치에 없는 것)

업계 관행을 옮기지 않고 **우리 엔진 제약에서 역으로 유도한** 것들이다. 판단 기준은 셋이다 —
카탈로그 §4 종료 규칙을 구조적으로 만족하는가, 몬테카를로 감사 비용을 늘리지 않는가,
세로 430px에서 읽히는가.

### I1. 「비대칭 고정 그리드」 — 릴 높이가 다르되 변하지 않는다

**규칙.** 릴별 행 수를 `3-4-5-4-3`처럼 **고정된 비대칭 실루엣**으로 두고 ways로 평가한다.
경로 수는 항상 `3×4×5×4×3 = 720`이다. #13의 가변 행과 정반대다 — 저쪽은 매 스핀 달라지고
이쪽은 절대 안 변한다.

| 항목 | 내용 |
|---|---|
| 종료·발산 | **루프 자체가 없다.** 하드 캡·단조 척도가 필요 없는 유일한 아이디어다 |
| RNG 소비 | 추가 0회. 릴 정지 5회 그대로 |
| RTP 산출 | **analytic 정확값.** 릴 독립이 유지되므로 기존 ways 닫힌 식의 `rows`만 릴별로 바꾸면 된다 |
| 렌더러 | §4-4 레이아웃 일반화(릴별 높이 배열)로 커버. #13 작업(R1)에 이미 포함 |
| 허브 | 도움말 ways 탭에 실루엣 그림 1장 |
| 리스크 | 낮음. 아트 프레임 창이 직사각형이 아니라 **다이아몬드 실루엣**이라 크로마키 영역이 복잡해진다 |

**판정: 웨이브 2.5 채택 후보 (강함).** #13의 렌더러 작업을 그대로 재사용하면서 RTP는 정확값으로
나오는 유일한 조합이다. 감사 부담이 0인 신규 그리드는 이것뿐이다.

### I2. 「운명 릴」 — 작은 판이 큰 판의 배당표를 스핀마다 바꾼다

**규칙.** 메인 5×4 위에 3칸짜리 미니 릴을 얹는다. 미니 릴에서 같은 심볼이 2개면 그 심볼이 이번 스핀
**총아**가 되어 배당 ×2, 3개면 ×3이 된다. 총아는 스핀마다 새로 뽑히고 이월되지 않는다.

| 항목 | 내용 |
|---|---|
| 종료·발산 | 루프 없음. 스핀당 1회 판정 |
| RNG 소비 | `미니 릴 3회 → 메인 릴 5회 → 뮤테이션`. 미니를 먼저 뽑는 이유는 총아가 뮤테이션 대상 선정에 쓰일 여지를 남겨서다 |
| RTP 산출 | **analytic 가능.** 총아 심볼로 조건부화하면 릴 독립이 복원된다 — `mystery`가 해석 경로에 남는 것과 같은 논리다 |
| 구현 비용 | **앞선 초안이 과소평가했다(검수 27).** 총아는 그냥 배수 하나가 아니라 **페이테이블을 바꾼다.** 라인 후보 표(`getLineCandidates`)와 와일드 챔피언 표(`getWildChampions`)가 배당 값에 의존하므로 **총아 × 배수 조합마다 다시 만들어야 하고**, 해석식 DFS도 조건부 분기가 심볼 수만큼 늘어 대략 2배가 된다. 캐시 키에 총아를 넣어 조합당 한 번만 만들도록 설계해야 한다 |
| 렌더러 | 메인 창 위 미니 창(창 높이 12%). 5×4 셀이 78.8px → 71px로 줄지만 판독선 위 |
| 허브 | 총아 심볼을 페이테이블 상단에 강조 표시. WinStrip에 `총아 ×2` 뱃지 |
| 리스크 | 중. 화면 요소가 하나 늘어 6릴 게임에는 못 쓴다(5×4 이하 전용). "미니 릴이 결과를 정한다"는 오해를 도움말로 막아야 한다 |

**판정: 웨이브 3 채택 후보.** 두 그리드 연동을 해석적 RTP를 지키면서 하는 방법이고,
"이번 스핀은 뭐가 총아지"라는 **스핀 전 기대**를 만든다. 대부분의 피처가 스핀 후 서스펜스인 것과 다르다.
다만 비용은 "배수 하나 곱하기"가 아니라 **후보·챔피언 표 재생성**이므로 I1보다 확실히 무겁다.

### I3. 「각인」 — 진 스핀의 심볼이 다음 스핀으로 넘어간다

**규칙.** 스핀이 꽝이면 화면의 상위 티어 심볼 1개를 골라 그 좌표에 각인하고, 다음 유료 스핀에서
그 칸을 강제로 그 심볼로 채운다. 최대 3개까지 쌓이고 **승리가 나오는 순간 전부 소멸**한다.

| 항목 | 내용 |
|---|---|
| 종료·발산 | **앞선 초안의 논거는 무효였다(검수 28).** `3 − 각인 수`는 승리가 나면 3으로 되돌아가므로 **단조 감소 척도가 아니고**, 카탈로그 §4 규칙 3을 만족하지 못한다. 실제 안전 근거는 다른 데 있다 — **라운드 안에 루프가 없다.** 각인은 스핀 안에서 반복을 만들지 않고, 상태는 **과금되는 라운드 사이로만** 이월된다. 즉 종료는 "유저가 베팅을 멈추면"이고, 이는 프리스핀·리스핀과 달리 규칙 3의 적용 대상이 아니다. 대신 `maxEngravings = 3`이 **상태 크기 상한**으로 남는다 |
| 상태 만료 | 루프가 아니라 **영속 상태**이므로 만료 정책이 필수다. (1) `expiresAt` 24시간, (2) 베팅 레벨 변경 시 즉시 소멸, (3) 다른 게임 진입 시 유지(게임별 독립 상태), (4) 승리 시 즉시 소멸. 넷 다 서버가 강제하고 클라이언트 값은 신뢰하지 않는다 |
| RNG 소비 | `릴 정지 → 각인 덮어쓰기(추첨 0회) → 평가 → (꽝이면) 각인 대상 추첨 1회` |
| RTP 산출 | **monte-carlo 필수.** 유료 스핀 간 상태가 이월되므로 정상분포가 필요하다 |
| API | **base 게임 상태 영속이 처음으로 필요해진다.** 지금 `game_states`는 프리스핀 세션만 산다. `featureState`에 각인을 담고 세션 만료 정책을 새로 정해야 한다 |
| 허브 | 각인 칸에 고정 프레임 + "연패 보상" 문구. 소셜 카지노 리텐션 장치로 강력하다 |
| 리스크 | **높음. 차익 거래가 열린다** — 최소 베팅으로 각인 3개를 쌓고 최대 베팅으로 터뜨리면 기대값이 베팅 레벨에 따라 달라진다. 완화: 각인을 **베팅 레벨에 묶고 레벨이 바뀌면 소멸**시킨다. 이 규칙을 서버가 강제하지 않으면 RTP 모델이 통째로 무너진다 |

**판정: 웨이브 3 조건부 후보.** 아이디어 자체는 이 문서에서 가장 리텐션 값이 크지만, 베팅 레벨
차익과 base 상태 영속이라는 두 가지 새 부담을 진다. **먼저 붙일 곳은 신규 게임이 아니라 기존 저변동
게임의 A/B 실험**이다. 거기서 차익 방어가 검증된 뒤에 게임 헤드라인으로 올린다.

### I4. 「스핀 성향」 — 플레이어가 배당 구조를 고른다 (RTP는 그대로)

**규칙.** 스핀 전 3택 1이다. 「넓게」(적중률 ↑ · 최대 배수 ↓), 「고르게」(기본), 「깊게」(적중률 ↓ ·
최대 배수 ↑). 셋은 **서로 다른 스트립 세트**를 쓰고 **RTP는 셋 다 정확히 94.5%로 튜닝**한다.
추가 비용이 없다는 점에서 앤티 베트와 다르고, RTP 차익이 없다는 점에서 바이 피처와 다르다.

| 항목 | 내용 |
|---|---|
| 종료·발산 | 루프 없음 |
| RNG 소비 | 선택은 클라가 스핀 요청에 싣고 **서버가 허용된 3값인지 검증**한다. 그 뒤 RNG 순서는 기존과 동일하고 스트립만 갈린다 |
| RTP 산출 | 모드별로 **따로** 낸다. 게이트가 **세 값 전부** `±0.5%p`를 요구한다 |
| 검증 위치 | `stakeShaping`의 "세 모드 RTP 일치" 검사는 **`parseGameMath` 안에 넣지 않는다**(검수 29). 스키마가 해석 모듈(`analytic.ts`)을 부르면 순환 의존이 생긴다. `validateStakeShaping(math)`를 감사 도구 쪽 별도 함수로 두고 게이트가 부른다 |
| 렌더러 | 없음. 스트립이 바뀔 뿐이다 |
| 허브 | 스핀 버튼 위 3분할 세그먼트 + "세 모드의 RTP는 같습니다" 고지 |
| 리스크 | 중. **해석적 게임이라도 비용이 0은 아니다(검수 29 정정).** RTP 자체는 닫힌 식이라 세 번 재도 싸지만, **적중률·최대 배수·배수 분포는 어느 모델에서든 표본이라 3배**가 된다. 그래도 몬테카를로 게임에 얹는 것(감사 시간 3배)보다는 훨씬 싸므로 **해석적 게임 전용**이라는 제약은 유지한다 |

**판정: 웨이브 3 채택 후보 (강함).** 소셜 카지노에서 "내가 게임의 성격을 고른다"는 주체감은
픽미보다 강하고 비용은 훨씬 싸다. **해석적 RTP 게임 전용**이라는 제약은 유지하되, 그 검사는
스키마가 아니라 `validateStakeShaping`이 맡는다(위 표 참고).

### I5. 「회전판」 — 심볼이 사라지지 않고 돌기만 한다

**규칙.** 5×5에서 바깥 링 16칸이 매 회전마다 시계 방향으로 `k`칸(1~4 추첨) 돌고 중앙 3×3은 고정된다.
회전 후 재평가하고 최대 3회 돈다. 텀블의 사촌이지만 심볼이 **소멸하지 않고 이동만** 한다.

| 항목 | 내용 |
|---|---|
| 종료·발산 | `maxRotations = 3` 하드 캡, 척도 `3 − rotations` |
| RNG 소비 | `릴 정지 → 회전량 추첨(회전마다 1회)` |
| RTP 산출 | **monte-carlo.** 심볼 집합이 보존돼 회전 간 상관이 매우 강하다 |
| 렌더러 | 링 회전 트윈. 5×5는 정사각 격자라 창 높이를 §4-4 방식으로 다시 재야 한다(6×5 좌표로는 세로가 묶인다) |
| 리스크 | **높음.** (1) 회전은 "왜 이겼는지"를 흐린다 — 텀블은 터진 자리가 근거로 남지만 회전은 판 전체가 움직여 인지 부담이 크다. (2) 같은 심볼 집합을 3번 재평가하므로 밀도 튜닝의 감도가 극단적으로 비선형이다 |

**판정: 장기 백로그.** 연출은 좋지만 인지 부담과 튜닝 난도를 정당화할 만큼 새로운 기대감을 만들지
못한다. I1~I4를 다 쓴 뒤에 재검토한다.

### 요약

이것이 이 다섯 개를 고른 기준이다.

## 11. GAME_CATALOG §4 개정안 (그대로 옮겨 쓰는 용도)

§3-6의 계산 결과를 카탈로그에 반영하기 위한 문구다. 카탈로그 소유자가 아래 두 블록을 그대로
복사하면 된다.

### 11-1. "프리미티브별 RTP 산출 방식" 표의 P3·P4 행 교체

| 프리미티브 | 방식 | 이유 |
|---|---|---|
| P3 cascade | **`monte-carlo`, 필요 스핀 수는 팩마다 산출** | 연쇄 길이와 배수가 그리드 전체 상태에 의존한다. **고정 스핀 수를 적지 않는 이유는 분산이 팩마다 3배 넘게 차이 나기 때문이다** — 오브 꼬리 하나로 필요 표본이 69M에서 188M으로 뛴다. 파일럿 100만 스핀으로 σ를 재고 `n* = (1.96σ / 0.002)²`로 정한다. 팩의 `manifest.auditSpins`가 SSOT다 |

### 11-2. §4 감사 게이트 확장 요구에 덧붙일 문단

> **정식 감사의 스핀 수는 고정값이 아니다.** 기준은 언제나 `|rtp − target| ≤ 0.5%p` **그리고**
> `95% CI 반폭 ≤ 0.2%p`이고, 반폭은 `1.96σ/√n`이므로 **필요한 n은 팩의 분산이 정한다.**
> 감사 리포트는 파일럿에서 잰 σ와 그것으로 유도한 `n*`, 실제로 쓴 `n`을 함께 남기고 `n ≥ n*`를 만족해야
> 한다. 정밀도 기준을 완화해 통과시키는 길은 없다 — 반폭은 1/√n로만 줄어들므로 기준을 늘리는 순간
> "목표를 맞췄다"는 문장이 근거를 잃는다.
>
> 표본이 클 때는 시드를 K개로 쪼개 병렬로 돌리고 `mergeSimulations`로 합친다. 합산 결과는 한 번에
> 돌린 것과 `rtp`·`stdDev`까지 같고, 리포트에는 샤드별 시드를 전부 남긴다.
