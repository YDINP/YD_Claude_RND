## 1. 재현한 로직

GachaSystem의 확률 로직을 그대로 이식했다 (Phaser/DOM 의존 제거, 값은 SSOT 주석과 일치):

```
RATES = { SSR: 0.015, SR: 0.085, R: 0.30, N: 0.60 }
PITY  = { softPity: 75, hardPity: 90, softPityBonus: 0.06, pickupPity: 180 }

determineRarity(currentPity):
  currentPity >= 90            -> SSR 확정
  ssrRate = 0.015 (+ (p-75)*0.06 if p>=75, cap 1.0)
  srRate  = 0.085 × 0.8        (p>=75 시)     # 소프트 피티 중 SR 축소
  rRate   = 0.30  × 0.9        (p>=75 시)     # 소프트 피티 중 R 축소
  순차 누적분포: SSR → SR → R → 나머지 N
pull 루프: currentPity++ 후 판정, SSR 시 피티 리셋
10연차: 결과에 SR/SSR이 없으면 마지막 1개를 SR로 교체 (피티 무영향)
픽업: pickupRate 0.5 (50/50), lost5050 캐리 또는 픽업피티 도달 시 확정
```

### 코드 감사에서 발견된 사양 불명확점 (시뮬 해석에 영향)

| # | 발견 | 영향 |
|---|------|------|
| B-1 | **`pickupPityCounter`는 어디서도 증가하지 않음** (`SaveManager.updateGachaCounter`는 pity/totalPulls만 갱신). `determinePickupCharacter`/`isPickupGuaranteed`는 읽기만 함 | 픽업 천장이 **현재 사실상 데드 코드**. 시뮬은 `_meta` 주석("180회 픽업 확정") 의도대로 **누적 뽑기 횟수 기반**으로 해석해 구현 |
| B-2 | `isPickupGuaranteed`는 `pickupPityCount >= pickupPity - 1`(179), `determinePickupCharacter`는 `>= 180` — off-by-one 불일치 | UI 표기와 실제 판정이 1회 어긋날 수 있음 |
| B-3 | `getPityInfo()`(:399)만 소프트 피티 증분을 `0.05`로 계산 (determineRarity는 `0.06`) | UI에 표시되는 "현재 SSR 확률"이 실제보다 낮게 나옴 |

## 2. 시뮬레이션 결과 (실측)

**조건**: 결정론적 시드(mulberry32), 100계정 × 10,000회 = 계정당 모드별 100만 회.

### 2-1. 이론 기대치 (해석해 — 편차 판정 기준선)

| 지표 | 값 |
|------|-----|
| SSR 사이클 길이 기대값 E[L] | **46.69연차** |
| 실효 SSR 출현율 (피티 포함) | **2.142%** (표기 1.5% 대비 +0.642%p) |
| 하드피티(90연차) 도달 확률/사이클 | **8.28×10⁻⁴ %** (≈ 12만 사이클당 1회) |

> 소프트 피티(+6%/회 × 15회) 때문에 실효 SSR율은 표기값보다 약 43% 높다. 이것은 오류가 아니라 설계된 천장 효과다. 따라서 "±0.5% 편차" 검증은 **이론 실효율 대비**로 수행한다.

### 2-2. 출현율 실측

| 모드 | SSR | SR | R | N | SSR 이론 대비 편차 | ±0.5%p 판정 |
|------|-----|----|----|----|------------------|------------|
| **10연차 모드** (SR 보장 적용, 실전형) | **2.147%** | **11.696%** | 29.846% | 56.312% | +0.005%p | **PASS** |
| 단발 모드 (대조군) | **2.153%** | 8.457% | 29.934% | 59.457% | +0.011%p | **PASS** |

- 10연차 모드의 SR +3.24%p는 **10연 SR 보장** 효과 (N→SR 1개 교체가 배치당 최대 1회 발동).
- R/N은 소프트 피티 구간 축소(×0.9/×0.8)와 보장 교체가 상쇄되어 명목치 부근 유지.

| 단발 | 45.7회 | 41.5회 | 80회 | 84회 |

### 2-4. 천장(hardPity 90) 검증

| 관측 최장 무SSR 간격 | 89연차 (10연차) / 88연차 (단발) |
| 하드피티 90에서 강제 획득한 건수 | 0건 — 이론 도달 확률이 너무 낮아(8.28e-4%/사이클, 100만 회 기대 ≈ 0.18건) 미관측. **보장 로직 자체는 `pity>=90 → SSR` 단순 분기로 정상이며, 실질적 천장은 소프트 피티가 담당** |

✅ **결론: hardPity 90은 "위반 0건"으로 보장됨을 확인.**

### 3-3. 가챠 지속 가능성

- 젬 수입 160/일 → 10연(2,700) 충족에 **약 16.9일**, 월 약 **1.8회 10연**.
- 신규 유저는 ch1 첫 클리어 점프(+620젬)로 초기 2~3회 10연 가능.
- **PRD-3 이중 비용 주의**: 가챠는 젬 외에 뽑기당 에너지 10을 소모 → 10연 1회 = 에너지 100 = 스테이지 16.7회 포기 ≈ **골드 25,000 기회비용**. 에너지가 병목인 성장기에는 가챠와 파밍이 직접 경쟁한다.
- 보석 에너지 충전(50젬→50에너지)은 골드 환산 12,500/50젬으로, 젬을 직접 10연에 쓰는 것(300젬=1뽑)보다 골드 수급 목적이라면 손해.

### 3-4. 밸런스 코멘트

1. **실효 SSR율 2.14% vs 표기 1.5%**: 확률 표기 고지 관점에서 표기값은 "기본 확률"임을 UI에 명시할 것 (소프트 피티 포함 안내). Genshin류 관행과 동일.

3. **B-1~B-3 버그 3건**은 밸런스 이전에 신뢰성 문제 → 우선 수정 권장.

## 5. BLK-03 전투력 통합 후 상한

> **작성일**: 2026-09-02
> **대상 이슈**: `docs/STORY_MODE_GDD.md` §7-1 BLK-03, `docs/story/LEVEL_STORY_PLACEMENT.md` LV-ISS-01
> **SSOT**: `src/systems/ProgressionSystem.js` `calculatePower()` / `getFinalStats()` (통합 후 단일 구현)
> **수치 출처**: 위 구현을 직접 호출해 산출했다. `src/data/index.ts::calculatePower()`는 이제 이 함수에 위임하는 래퍼다.

### 5-1. 통합된 공식

```
전투력 = floor( HP/10 + ATK + DEF + SPD + (스킬레벨 합 × 10) )

스탯 적용 순서:  기본(JSON stats + growthStats × (Lv−1))
              →  성급   × (1 + (성급−1)×5%)        [SPD는 절반]
              →  장비   + EquipmentSystem 합산치     [가산]
              →  컬렉션 × (1 + CollectionSystem 배율) [곱]
```

변경 전에는 `getStatsAtLevel()`이 `getCharacter()`만 조회해 `base_*` / `asc_*` ID가 전부 `undefined`로 떨어졌고, 그 결과 모든 기본·전직 영웅이 N등급 폴백 테이블(hp800/atk80/def40/spd95)로 계산됐다. 이제 `getCharacterOrHero()`를 거쳐 각 영웅의 JSON 스탯을 사용한다.

### 5-4. 5-5 잔여 격차의 원인

**성장 곡선이 아니라 장비 수치 부족이다.**

LV-ISS-01의 역산은 "장비 4슬롯 전투력 편입 = 인당 +2,400"을 전제했다. 실제 최대치는 **인당 +1,635**(컬렉션 반영 시 약 +1,757)로, 전제의 68% 수준이다. 부족분은 인당 약 765, 파티 기준 약 3,060이다.

원인은 `EquipmentSystem.generateBaseStats()`의 슬롯 기본값과 `EQUIPMENT_RARITY.SSR.multiplier = 2.0`, 그리고 강화 보너스가 **기본 스탯의 5% 고정 가산 × 최대 15회 = 기본의 75%**로 상한이 낮다는 데 있다. 반면 스테이지 요구 곡선(챕터 5: 8,000 → 15,000)은 등비수열로 채워져 있어 조정 여지가 크다.

### 5-6. 통합으로 해소된 것 / 남은 것

**해소됨**

| 항목 | 통합 전 | 통합 후 |
|---|---|---|
| `calculatePower` 구현 수 | 2개 (결과 불일치) | 1개 (`ProgressionSystem`, `data/index.ts`는 위임) |
| 전직영웅 스탯 출처 | N등급 폴백 테이블 (JSON 무시) | 각 영웅 JSON `stats` + `growthStats` |
| 장비 반영 | 없음 | 가산 항으로 편입 (파티의 49%) |
| `skillLevels` 누락 | 예외 발생 | 기본값 `[1, 1]` |
| `stars` 누락 | `NaN` 전파 | 등급에서 유도 |
| 4인 파티 상한 | 5,484 (4-3 이후 도달 불가) | 14,348 (5-5만 0.96× 미달) |
| 만렙 레거시 vs 만렙 전직영웅 | 레거시 우위 | `char_1` 1,117 < `asc_omar_valhalla` 1,369 (장비 포함 2,875 < 3,733) |

**남은 데이터 이슈 3건 — 공식이 아니라 `ascended-heroes.json` / `characters.json` 값의 문제다**

1. **등급이 전투력 순서와 어긋난다.** 동일 Lv40 기준 SSR 평균 733 < SR 평균 868이고, SR 최대 1,163이 SSR 최대 904를 넘는다. 최강 4인 중 3명이 SR이다. 등급 표기가 강함을 의미하지 않는다.
2. **각인 직후 전투력이 떨어진다.** 10계보 중 8계보에서 동일 Lv30 기준 기본영웅이 전직영웅보다 강하다(`base_iris` 661 > `asc_iris_olympus` 593). 전직영웅은 lv1 스탯이 낮고 성장률이 높은 구조라 만렙에서는 전부 역전된다(904~1,369 > 639~850). 온보딩에서 "각인했는데 약해졌다"는 체감이 남으므로 각인 직후 레벨 보정이나 UI 안내가 필요하다.
3. **레거시 `char_1~4`는 `growthStats`가 없어 레벨이 올라도 전투력이 고정된다**(`char_1` Lv1 = Lv30 = 682). 초반에는 여전히 최강이지만 상한이 낮아 장기적으로 전직영웅에 역전된다. 이는 `docs/story/SYSTEM_ONBOARDING_ECONOMY.md` §1-2가 명시한 의도된 설계와 일치한다.

### 5-7. 재현 방법

```bash
npx vitest run tests/systems/ProgressionSystem.test.js
```

`describe('BLK-03 전투력 통합')` 9개 케이스가 위 관계를 고정한다: 전직영웅 ID의 JSON 스탯 조회, 계보별 만렙 순서, 레거시 상한, 장비 합산(EquipmentSystem 경유 및 직접 주입), 강화·등급 배율, 적용 순서, `skillLevels`/`stars` 누락 처리.

파티 상한 재산출은 `ProgressionSystem.calculatePower()`에 다음 인자로 호출한 결과다.

```
{ ...ascendedHero, characterId: hero.id, level: hero.maxLevel, stars: 6,
  skillLevels: [10, 10, 10], equipmentStats: { HP: 3150, ATK: 750, DEF: 450, SPD: 120 } }
```

`equipmentStats`는 `EquipmentSystem.generateBaseStats(slot, 'SSR')` 4슬롯에 `getEnhanceStatBonus()` × 15를 더하고 `getEquipmentStats()`로 등급 배율을 적용해 합산한 값이다.
