## 0. 설계 기준선 검증 결과 [시스템 — game-system-designer]

설계에 들어가기 전에 코드에서 직접 확인한 사실이다. **이 절의 5개 발견이 이후 모든 수치 결정의 전제**이므로 먼저 기술한다.

### 0-2. 발견 A — 플레이어 레벨이 절대 오르지 않는다 (P0)

`player.level`을 증가시키는 코드가 저장소 전체에 **존재하지 않는다**. `EnergySystem.onLevelUp()`도 호출되지 않는다.

**영향**:
1. 최대 에너지가 영구히 `100 + 1×2 = 102`로 고정된다. 성장에 따른 에너지 확장이 없다.
2. **해금 조건에 "플레이어 레벨"을 사용할 수 없다.** → 4장의 해금 테이블은 전부 스테이지 진행도/튜토리얼 플래그 기준으로 설계했다.

### 0-3. 발견 B — 전투력 공식이 2개이고, 결과가 다르다 (P0)

| 공식 | 위치 | 스탯 출처 |
|------|------|----------|
| A | `ProgressionSystem.getStatsAtLevel()` | **등급별 하드코딩 테이블** (N/R/SR/SSR). JSON의 `stats`를 무시 |
| B | `data/index.ts::calculatePower()` | JSON의 `stats` + `growthStats` (실제 캐릭터 데이터) |

`MainMenuScene`(전투력 패널), `PartyEditScene`, `IdleProgressSystem`은 **공식 A**를 쓴다. 그런데 공식 A의 `getStatsAtLevel()`은 `getCharacter(id)` — 즉 `characters.json`만 조회한다. `base_*`/`asc_*` ID는 여기 없으므로 `charData = undefined`, 세이브 레코드에도 `rarity` 필드가 없어(`performAscension`은 `stars`만 기록) `getRarityKey(undefined) = 'N'`으로 떨어진다.

**결과: 모든 기본영웅/전직영웅이 N등급 기본 스탯(hp800/atk80/def40/spd95)으로 계산된다.**

| 캐릭터 | 공식 A 결과 (Lv1) | 공식 B 결과 (Lv1) |
|--------|------------------|------------------|
| `char_1` 가르디아 (레거시 SR) | 452 | 681 |
| `asc_iris_olympus` (SSR 전직영웅) | **374** | 310 |

SSR 전직영웅이 레거시 스타터보다 전투력이 낮게 표시된다. 온보딩에서 "각인했는데 약해졌다"를 유발한다.

**설계 기준 결정**: 이 문서의 모든 전투력 시뮬레이션은 **공식 B(JSON 스탯 기반)** 로 계산했다. 공식 A는 캐릭터 데이터를 반영하지 못하므로 밸런싱의 기준이 될 수 없다. **공식 통합은 온보딩 구현의 선행 조건(P0)이다.**

### 0-4. 발견 C — 레이어 2 재화는 소모처만 있고 획득처가 0이다 (P0)

`cultEssence` / `institutionSeal` / `awakeningFlame`을 **증가시키는 코드나 데이터가 저장소 전체에 없다.**

- `stages.json` 전 25스테이지 보상: gold / exp / gems / 소모템 / summon_ticket 뿐
- `quests.json` 전 13퀘스트 보상: gems / gold / 소모템 / summon_ticket 뿐
- `TowerSystem.js`: 해당 재화 언급 없음
- 유일한 참조는 `CollectionSystem.computeExtraRouteCost()`(**소모**)와 `ascended-heroes.json::acquisitionCost`(**소모 정의**)

즉 GDD §5-2 레이어 2는 **설계만 있고 경제가 없다**. 이 상태로는 GDD 기준 전직이 영구히 불가능하다.

### 0-5. 발견 D — 첫 각인의 실제 비용은 GDD와 다르다

| | GDD §2-2 / §2-3 | `SaveManager.performAscension()` 실제 구현 |
|---|---|---|
| 기본영웅 각성 | 조각 30 + 정령석 3 | (별도 단계 없음) |
| 전직 | 각인서 1 + 에센스 20~30 (+불꽃 3) | **조각 30 + 젬 3** 로 base→ascended 직행 |

구현은 **각성과 전직을 한 단계로 압축**했고, 정령석 대신 **젬을 소모**한다(`canAscend()`가 `data.resources.gems`를 검사). 레이어 2 재화는 차감하지 않는다.

### 0-6. 발견 E — 무과금 신규 유저는 첫 각성에 도달할 수 없다

`characterShards[baseHeroId]`를 증가시키는 유일한 경로는 `SaveManager.addCharacter()`의 **중복 소환 처리**뿐이다.

```
기본영웅은 CHARACTER_POOL의 R 등급에 편입 (rarity 필드 없음 → 기본값 'R')
R 풀 = ascended R 3종 + base hero 10종 = 13종
특정 기본영웅 1회 등장 확률 = 0.30 × (1/13) = 2.31% / pull
중복 1회당 조각 = getShardsForDuplicate(3성) = 20개
필요: 신규 1회 + 중복 2회 = 3회 등장  →  기댓값 3 ÷ 0.0231 ≈ 130 pulls
130 pulls × 300젬 = 39,000젬  (초기 지급 2,700젬의 14.4배)
```

**Pillar ④ "첫 세션 안에 첫 각성"은 현재 구조에서 수학적으로 불가능하다.** 이것이 1장에서 확정 지급을 선택하는 결정적 근거다.

## 1. 신규 계정 초기 상태 재설계 [시스템 — game-system-designer]

### 1-1. 핵심 모순에 대한 결정 — 옵션 B: 레거시 완전 대체

| 옵션 | 내용 | 판정 |
|------|------|------|
| A. 레거시 유지 | `char_1~4` 스타터 유지, 진화 시스템은 별도 트랙 | ❌ |
| **B. 완전 대체** | **기본영웅 확정 지급으로 교체, 레거시 신규 지급 중단** | ✅ **채택** |
| C. 병행 | 기본영웅 2 + 레거시 2 혼합 파티 | ❌ |

**A를 기각하는 이유**: `char_1~4`는 `ascensionRoutes`가 없어 각인 불가다. 신규 유저의 주력 4명이 전부 "코어 루프 바깥의 자산"이 된다. 플레이어는 20~30분을 투자한 뒤에야 "내가 키운 애들은 각성이 안 된다"를 알게 된다. Pillar ①(선택이 정체성이다)·③(유닛이 아니라 동행자)에 정면으로 반한다.

**C를 기각하는 이유**: 파티 4칸 중 2칸이 데드엔드라는 사실을 UI로 설명해야 한다. 온보딩 인지 부하를 2배로 만들면서 얻는 것은 "초반 전투력 숫자"뿐이다. 1-3의 전투력 시뮬레이션(1-4절)이 보여주듯 **레거시 없이도 챕터1은 통과 가능**하므로 유지할 실익이 없다.

**B의 구체안**:

```
신규 계정 파티 = base_iris 1명 (각성 완료 상태로 확정 지급), 슬롯 2~4 비어 있음
parties: [['base_iris', null, null, null]]
characters: [ base_iris 레코드 1건 ]
```

**1인 파티로 시작하는 것이 설계 의도다.** 1-3까지는 1인으로 클리어되고, 1-4(권장 500)에서 처음 막힌다. 이 "벽"이 2장의 첫 무료 10연 트리거가 된다. 자원을 먼저 주고 쓸 곳을 찾게 하는 대신, 결핍을 먼저 만들고 해결책을 준다.

### 1-2. 기존 세이브 유저 마이그레이션

**원칙: 이미 가진 것은 절대 회수하지 않는다.** 회수는 리텐션에 가장 치명적인 조작이다.

| 대상 | 처리 |
|------|------|
| `char_1~4` 보유 기존 유저 | **그대로 유지**. 각 레코드에 `legacyStarter: true` 태그 부여 |
| 레거시 캐릭터의 각인 UI | 각인 목록에서 제외하되, 도감 "초기 동행자" 섹션에 별도 보존 |
| `SaveManager.load()`의 스타터 마이그레이션 블록 (L114~123) | **제거**. "빈 세이브 + totalBattles 0"이면 신규 온보딩 경로로 진입 |
| 기존 유저 중 `baseHeroes: []` 이고 `totalBattles > 0` | 온보딩 미경험자로 판정 → `base_iris` + 오마르 조각 30 **소급 지급** 1회 (`onboarding.grantVersion` 플래그로 중복 방지) |
| 세이브 버전 | `SAVE_KEY` 유지, `VERSION: 1 → 2`. `migrate()`에서 위 처리 수행 |

레거시 캐릭터의 전투력이 공식 A로 인해 기본영웅보다 높게 표시되는 문제(0-3절)는 공식 통합으로 해소된다. 통합 후에는 `char_1`(681) > `base_iris`(403)이 되어 여전히 레거시가 강하지만, 레거시는 **성장 상한이 없고 각인이 불가**하므로 장기적으로는 전직영웅(Lv60 기준 1,059)에 역전된다. 이는 의도된 설계다.

### 1-3. 첫 기본영웅 확정 지급 — 아이리스 고정

**결정: `base_iris`(아이리스)를 고정 지급한다. 플레이어 선택권을 주지 않는다.**

| 판단 기준 | 아이리스가 충족하는 근거 |
|----------|----------------------|
| **서사 적합성** | 정체성이 *"내 힘은 내 것이다"*. High Concept *"신을 이기러 온 것이 아니다"* 와 직결된다. 첫 캐릭터가 곧 게임의 주제문이 된다 |
| **전직 루트 이해도** | 3루트(olympus 폭딜 / valhalla 역전 / chaos 고분산)의 전투 스타일이 가장 극명히 갈린다. "같은 캐릭터가 다르게 자란다"를 1회 노출로 학습시킬 수 있는 유일한 후보 |
| **첫 결정 스트레스 제거** | 3루트 **전부 SSR**이다. 어떤 선택도 등급 손해가 없다 → 신규 유저가 "잘못 골랐나" 불안 없이 첫 선택을 완료한다. 튜토리얼 완주율 ≥85% KPI에 직결 |
| **클래스 밸런스** | warrior/근접 단일딜. 초반 파티의 딜 축. 부족한 탱커·힐러는 10연과 두 번째 각성으로 채우게 설계 |
| **개발 비용** | 분기 없음 → 컷씬 1종, 각인 튜토리얼 스크립트 1종. narrative/UX 담당의 작업량이 1/10로 줄어든다 |

**선택권을 주지 않는 이유**: 10명 중 선택 UI를 첫 화면에 놓으면 (a) 정보가 없는 상태의 선택 = 무의미한 마찰, (b) 튜토리얼 분기 10종 필요, (c) 리롤 문화 유발. 선택의 즐거움은 **기관 선택(각인)** 이 담당하며, 그것이 이 게임의 정체성이다. 캐릭터 선택과 기관 선택을 둘 다 첫 세션에 넣으면 후자의 임팩트가 희석된다.

**두 번째 영웅(플레이어가 직접 각성시킬 대상): `base_omar`(오마르) 조각 30개 확정 지급.**

| 근거 | 내용 |
|------|------|
| 역할 보완 | 아이리스=딜러 → 파티에 탱커 부재. 오마르 HP1200 / DEF150(전 기본영웅 중 1위)이 1-4·1-5 보스전 생존을 담당 |
| 학습 효과 | 오마르의 2루트는 **둘 다 SR**(valhalla / avalon). 아이리스(전부 SSR)와 대비되어 "기관에 따라 결과 등급이 다르다"를 두 번째 각인에서 자연 학습시킨다 |
| 수치 안정성 | Lv1 전투력 486으로 기본영웅 중 최고. 1-4(권장 500) 돌파에 직접 기여 |

### 1-4. 초기 지급 재화 표

| 재화 | 현재값 | **제안값** | 근거 |
|------|-------|----------|------|
| gold | 10,000 | **10,000 (유지)** | 스킬강화 1회 = `1000 × lv²` (`getSkillEnhanceCost`). Lv1→2가 1,000골드. 10,000이면 초반 강화 6~8회분. 챕터1 골드 수입 1,270 + 일일퀘 1,800 = 충분한 흑자 |
| gems | 2,700 | **1,500** | 아래 별도 설명 |
| summonTickets | 10 | **10 (유지)** | `TICKET_MULTI = 10` — 정확히 첫 무료 10연 1회분. **신규 재화 추가 없이** 무료 10연을 성립시킨다 |
| **spiritStones** (신규 필드) | 없음 | **6** | 아래 별도 설명 |
| characterShards | `{}` | **`{ base_omar: 0 }`** | 초기 0. 1-3 클리어 보상으로 30 일괄 지급 (2-4절) |
| institutionSeal | 0 | **1** | 첫 각인 1회분. 두 번째부터는 정상 수급 |
| cultEssence | `{}` | **`{}` (유지)** | 첫 각인은 "첫 각인 보증"(1-6절)으로 처리. 사전 지급 시 12기관 중 무엇을 줄지 결정 불가 |
| awakeningFlame | 0 | **0 (유지)** | SSR 루트 선택 시 "첫 각인 보증"이 3개 자동 지급 |
| worldTreeSeeds | 0 | **0 (유지)** | 추가 루트 개방은 온보딩 범위 밖 (GDD 레이어 3) |

**gems 2,700 → 1,500 인하 근거 (수치 유도)**

`MULTI_COST = 2700`이므로 현행 2,700젬 + 티켓 10장 = **첫날 20연 가능**이다. 여기에 확정 지급 기본영웅 1명 + 조각 30개까지 얹으면 초반 재화가 명백히 과잉이며, Day2~3에 **뽑을 것이 남지 않는다**(D7 리텐션 ≥20% KPI에 역행).

목표를 이렇게 잡았다: **첫 10연은 Day1(티켓), 두 번째 10연은 Day3(젬 누적)**.

```
Day1 종료 시점 젬 = 초기 X + 챕터1 첫클리어 240 + 일일퀘 110 + 업적 300 (achieve_001/002/003)
Day2 종료 = Day1 + 챕터2 첫클리어 230(2-1~2-4) + 일일퀘 110
Day3 종료 = Day2 + 2-5 첫클리어 150 + 3-1 60 + 3-2 60 + 일일퀘 110

Day3 종료 누적 = X + 650 + 340 + 380 = X + 1,370
목표: Day3 종료 누적 ≥ 2,700 (10연 1회)  →  X ≥ 1,330
Day2 종료 누적 < 2,700 (Day2에는 못 뽑게)  →  X + 990 < 2,700  →  X < 1,710

### 1-7. 에너지 병목 검증

```
최대 에너지     = 100 + 1×2 = 102  (플레이어 레벨 고정, 발견 A)
회복 속도       = 1 / 5분 = 12/시간 = 288/일 (이론값)
실질 일일 수급  = min(288, 접속횟수 × 102)
                  1회 접속 → 102 / 2회 접속 → 204 / 3회 접속 → 288
```

| 검증 항목 | 소요 | 가용 | 판정 |
|----------|-----|-----|------|
| 1-1 ~ 1-5 완주 | 6+6+12+6+20 = **50** | 초기 102 | ✅ 여유 52 (2회 완주 가능) |
| 챕터2 완주 | 50 | 일일 102~204 | ✅ |
| 온보딩 10연 (에너지 부과 시) | **100** | 1-3까지 쓰고 남은 78 | ❌ **진행 불가** |
| 온보딩 10연 (면제 시) | 0 | 78 | ✅ |

**결론: 에너지는 스테이지 진행의 병목이 아니다. 병목은 오직 소환 에너지 비용이다.**

`ENERGY_COST_PER_PULL = 10`은 10연에 100 에너지 — **일일 탱크의 98%**를 소모한다. 첫 세션에서 1-3까지 24를 쓰면 잔여 78이므로 10연 자체가 실행 불가능하다.

> **[변경 제안 CH-04]** `GachaSystem.ENERGY_COST_PER_PULL`을 **0으로 변경(소환 에너지 비용 폐지)**.
> 근거: (1) 수집형 RPG 표준에서 소환에 스태미나를 부과하는 사례가 없다. (2) 젬/티켓이라는 명확한 소환 통화가 이미 있는데 2중 게이트는 유저에게 "왜 못 뽑는지"를 이해시키지 못한다. (3) 온보딩에서 물리적으로 진행이 차단된다.
> **차선책**: 폐지가 어렵다면 온보딩 10연만 `options.skipEnergyCheck = true`로 예외 처리. 단 유저가 두 번째 10연에서 동일한 벽에 부딪히므로 근본 해결이 아니다.
> **영향 범위**: `GachaSystem.pull()`, 해당 테스트.

### 2-1. 시행 여부와 시점

**시행한다. 시점은 1-3 클리어 직후.**

| 첫 전투(1-1) 직후 | ❌ | 전투 1회로는 파티 부족을 체감하지 못한다. 아이리스 단독으로 4.03× 여유 |
| **1-3 클리어 직후** | ✅ | 1-4(0.86×)의 벽을 **눈으로 확인한 직후**. 필요가 발생한 시점에 해결책이 도착한다 |

**세션 타이밍 검산**: 1-1~1-3 에너지 24, 전투 3회 + 컷씬 → **약 5~8분**. 10연 연출 1분, 오마르 각성 1분, 1-4/1-5 3분 → **첫 세션 총 12~15분에 첫 각성 + 첫 전직 도달**. Pillar ④ 충족.

### 2-2. 확정 결과 정책

**기존 `GachaSystem` 로직을 일절 수정하지 않는다.** RATES / `determineRarity()` / 소프트75·하드90·픽업180 피티 / 10연 SR확정 재추첨(`pull()` L267~287)을 그대로 통과시키고, **결과 위에 별도 확정 봉투를 얹는 방식**을 쓴다.

| 항목 | 정책 | 근거 |
|------|------|------|
| **리롤** | **불허**. 재시작 기능 제공하지 않음 | 리롤 문화는 D1 이탈(설치→삭제 루프)을 유발한다. 확정 지급 기본영웅 + 확정 조각 봉투로 **리롤 동기 자체를 제거**했다 |
| **배너** | `standard` 고정. 픽업 배너는 챕터1 클리어 후 해금 | 픽업/5050/픽업천장을 첫 소환에서 동시에 가르치면 인지 과부하. 천장 개념 1개만 학습시킨다 |
| **픽업 확정** | 없음 (standard에는 픽업이 없음) | `isPickupGuaranteed()`가 standard에서 `hasPickup: false` 반환 — 기존 로직과 정합 |
| **최소 보장** | 기존 **10연 SR 이상 1개 확정**만 적용 (수정 없음) | `pull()` 내장 로직. 별도 확정을 추가하면 RATES 검증 테스트가 깨진다 |
| **조각 최소 보장** | 10연 **결과와 무관하게** 결과 화면에서 "각성의 인도" 봉투 지급:<br>`characterShards.base_omar += 30`, `spiritStones += 0` (초기 6으로 충당) | 가챠 로직 외부의 **결정론적 보상**. 확률과 무관하므로 KPI 통제 가능 |
| **피티 카운터** | **정상 카운트**(pityCounter +10) | 무료라고 제외하면 유저가 "무료는 손해"로 인식한다. 90 하드피티까지의 진행도가 첫 소환부터 쌓인다는 감각이 D7 리텐션 훅 |
| **에너지** | 면제 (CH-04) | 1-7절 |

**기대값 검산 (standard 10연, N풀 문제 해결 후 기준)**

```
SSR 최소 1개 확률 = 1 − (1 − 0.015)^10 = 14.0%
SR 이상 최소 1개  = 100% (10연 확정 로직)
SR 이상 기대 개수 = 10 × 0.10 = 1.0개 + 확정 보정 → 실질 1.0~1.1개
```

10연 결과로 파티가 2~4명까지 늘어난다(중복 발생 시 조각 전환). **파티가 최소 2명은 되도록** 다음 안전장치를 둔다: 10연 후 보유 캐릭터가 2명 미만이면 (전부 중복인 극단 케이스) 봉투에서 `asc_lin_balance`(R, 서포터)를 추가 지급. 발생 확률은 극히 낮으나 진행 차단을 원천 봉쇄한다.

## 4. 온보딩 구간 시스템 해금 순서 [시스템 — game-system-designer]

**각인 시 레벨 승계 규칙 (필수)**

```

## 6. 스킵 정책의 시스템 측면 [시스템 — game-system-designer]

### 6-1. 스킵 시 보상·플래그 보장 규칙

**핵심 원칙: 보상과 플래그는 "컷씬 재생 완료"가 아니라 "스텝 완료 커밋"에 귀속된다.**

```
스텝 완료 커밋 (commitStep) 의사 규약
──────────────────────────────────────
입력:  stepId, completionMode ∈ { "played", "skipped" }

1. tutorial.completedSteps 에 stepId 존재 → 즉시 종료 (멱등)
2. stepId 의 보상 지급
3. tutorial.completedSteps.push(stepId)
4. completionMode === "skipped" → tutorial.skippedSteps.push(stepId)
5. 스텝에 연결된 컷씬이 있으면 story.viewedCutscenes.push(cutsceneId)
   (스킵이어도 "본 것"으로 기록 — 재노출 방지)
   completionMode === "skipped" → story.skippedCutscenes 에도 기록
6. 스텝에 연결된 메뉴 해금이 있으면 onboarding.unlockedMenus 갱신
7. tutorial.currentStep = 다음 스텝
8. SaveManager.save()
```

**보장되는 성질**

| 성질 | 보장 방법 |
|------|---------|
| **멱등성** | 1단계의 `completedSteps` 선검사. 중복 호출·재접속·클라우드 충돌 어느 경우에도 이중 지급 없음 |
| **스킵 무손실** | 스킵/재생 어느 경로든 2~7단계가 동일하게 실행됨 |
| **원자성** | 지급과 플래그 기록이 단일 `save()` 호출 안에서 완료. 중간 크래시 시 스텝 전체가 미완료로 남아 재시도 가능 |
| **재노출 방지** | 스킵도 `viewedCutscenes`에 기록 → 다음 접속 시 다시 뜨지 않음 |
| **분석 가능성** | `skippedSteps` / `skippedCutscenes` 분리 기록 → "어느 컷씬이 스킵되는가" 측정 가능 (완주율 ≥85% 개선의 데이터 근거) |

**금지 사항**
- 컷씬 재생 완료 콜백에서 보상을 지급하는 구현 (스킵 시 누락)
- 보상 지급을 씬 전환 이후로 미루는 구현 (전환 중 이탈 시 소실)
- `completedSteps` 없이 `currentStep`만으로 진행도를 판단하는 구현 (뒤로가기/재접속 시 중복 지급)

### 6-2. 강제 구간과 스킵 가능 구간의 경계 기준

UX 담당이 플로우를 설계할 때 적용할 **판정 규칙**이다. 아래 3조건 중 **하나라도** 해당하면 강제, 전부 미해당이면 스킵 가능.

| # | 강제 조건 | 이유 | 해당 스텝 |
|---|---------|------|---------|
| **F-1** | **플레이어의 물리적 입력이 상태를 변경하는 최초 조작** | 조작법을 손으로 익히지 않으면 이후 전부 막힌다. 눈으로 본 것은 기억되지 않는다 | `T-03`(첫 전투), `T-05`(소환 버튼), `T-07`(각성 버튼) |
| **F-2** | **되돌릴 수 없는 선택** | 결과를 이해하지 못한 채 확정되면 이탈로 직결. 반드시 선택지 설명을 읽게 해야 한다 | `T-09`(기관 선택) |
| **F-3** | **아직 해금되지 않은 UI를 여는 조작** | 해금 직후의 첫 진입은 시스템 위치를 각인시키는 유일한 기회 | (T-06은 안내만이므로 스킵 가능 — 각인 메뉴는 T-07에서 강제 진입) |

| # | 스킵 허용 조건 | 해당 스텝 |
|---|-------------|---------|
| **S-1** | 순수 내러티브(대사/연출)이며 조작을 요구하지 않음 | `T-01`, `T-02`, `T-12` |
| **S-2** | 동일 조작의 2회차 이상 반복 | `T-04`(1-2/1-3), `T-10`(1-4 재도전) |

**강제 구간 총량 상한**

```
강제 스텝 = T-03, T-05, T-07, T-09 → 4개
전체 스텝 12개 대비 33%
누적 강제 조작 시간 ≈ 2분 (전투 60초 + 버튼 탭 3회 + 선택 확정 30초)
```

**상한 근거**: 튜토리얼 완주율 ≥85%를 위한 업계 경험칙은 "강제 구간 누적 3분 이내, 강제 스텝 5개 이내"다. 4개/2분은 이 안에 있다. **강제 스텝을 5개 이상으로 늘리자는 제안이 오면 시스템 측에서 기각한다.**

**전체 스킵(Skip All) 정책**

| 항목 | 정책 |
|------|-----|
| 제공 여부 | **제공한다.** T-01 화면에 "튜토리얼 건너뛰기" 버튼 |
| 동작 | S-* 스텝 전량을 `commitStep(mode: "skipped")` 일괄 실행. **F-* 스텝(T-03/05/07/09)은 건너뛰지 않는다** |
