### 1-1. `tests/e2e/skip-path-parity.mjs` — T-Q6

**목적**: 게스트 계정 A(모든 컷씬 정상 시청, 대사 탭으로 진행)와 계정 B(모든 컷씬 Skip All)로 각각 1-1→1-5를 실제 UI로 클리어한 뒤 세이브를 비교. "시청/스킵 분류만 다르고 그 외 모든 상태는 동일해야 한다"는 GDD §9의 P2 필러를 검증한다.

**방법**:
- 두 계정 모두 `StageSelectScene.startBattle()` 실제 호출 → `BattleScene` 자동전투 → `BattleResultScene`까지 완주하는 실제 플레이 경로.

- `registry.battleSpeed`를 8배로 올려 자동전투 소요 시간을 단축했다(판정 로직에는 영향 없음, `BattleScene.js`가 이미 지원하는 속도 배율을 그대로 사용).

### 부차적 발견 (P2, 비차단) — DebugManager 치트 일부 미배선/스키마 불일치

전투 밸런스를 통제하려고 공식 디버그 치트(`window.debug.setInvincible(true)`)를 먼저 시도했으나 효과가 없었다. 확인 결과:
- `DebugManager.setInvincible()` / `setOneHitKill()`이 `this.invincible` / `this.oneHitKill` 플래그를 설정하지만 `BattleScene.js` 어디에서도 이 플래그를 읽지 않음(데드 코드).
- `DebugManager.autoOptimalParty()` / `clearParty()`는 `data.characters` / `data.parties`를 객체로 가정해 `Object.keys()`를 쓰지만, `SaveManager`의 실제 스키마는 둘 다 **배열**이라 정상 동작하지 않는다.

우회책으로 `unlockAllCharacters()` + `setCharacterLevel(id, 60)`(둘 다 정상 동작 확인)을 사용해 테스트를 완성했다. 이 항목은 QA 자동화 편의 도구의 문제라 유저 영향은 없지만, 실제 QA/개발 디버깅 시 혼란을 줄 수 있어 기록한다.

**의심 파일**: `src/systems/DebugManager.js:204-217`(invincible/oneHitKill 미배선), `src/systems/DebugManager.js:664-692`(characters/parties 배열-객체 불일치)

## 3. 테스트 설계 노트 (재현성을 위한 기록)

- **`LoginScene`이 `registry.autoBattle`을 `false`로 강제 설정한다**(`src/scenes/LoginScene.js:426`). 신규 전투는 기본적으로 수동 모드로 시작하므로, 자동전투 E2E는 `BattleScene` 진입 후 `registry.set('autoBattle', true)` + `waitingForManualInput` 상태를 폴링하며 `processTurn()`을 직접 호출해야 진행된다(단순히 `registry.set()`만으로는 이미 대기 중인 턴이 재개되지 않음).
- **승리 시 `BattleResultScene`이 `stage_clear`/`boss_after` 컷씬을 먼저 띄우고 자기 자신을 `scene.pause()`한다.** Phaser의 `isActive()`는 PAUSED 상태를 `false`로 보고하므로, "BattleResultScene이 active될 때까지 대기"만 하면 컷씬이 뜬 채로 영원히 대기하는 교착이 생긴다. 대기 루프 안에서 컷씬 존재 여부를 함께 폴링해야 한다.
- **대사 탭 진행은 좌표 클릭보다 `CutscenePlayer.handleTap()` 직접 호출이 안정적이다.** 좌표 클릭(`page.mouse.click`)은 씬 전환 직후 캔버스 scale/bounds가 안정화되기 전 타이밍에 클릭이 씹혀 무한 대기가 재현됐다. `handleTap()`은 탭존이 실제로 호출하는 함수이므로 좌표 의존성 없이 동일한 진행 로직을 결정적으로 재현한다.
- **1인 파티(초기 상태)로는 챕터1 조우도 패배할 수 있다.** 회귀 판정과 무관한 밸런스 변수를 제거하기 위해 `unlockAllCharacters()` + `setCharacterLevel(id, 60)`을 양쪽 비교 대상에 동일하게 적용했다(§1-1 참고).
- **T-08(파티 저장) 조건은 계정 생성 시점부터 이미 충족돼 있다.** 기본 세이브가 `parties[0] = [base_iris, null, null, null]`로 시작하므로 `completionCondition: party_saved`(`heroIds.filter(Boolean).length > 0`)가 처음부터 참이다. 그래서 온보딩 완주 시뮬레이션에서 T-07 커밋 직후 `evaluate()`가 T-08까지 연쇄로 자동 커밋하는 것이 관찰됐다(버그 아님, 의도된 재평가 로직의 부작용).
